Rise 5.99 AimAssist — Full Source Analysis

Overview

Rise 5.99's AimAssist is a mouse-delta assist that steers the player's real view rotation toward the nearest valid target. onPreMotion resolves the closest entity under the players, non-players, teams, invisibles and dead filters, computes the smoothed error to the target's interpolated position, divides it by a strength-derived step, and quantizes the result into whole mouse deltas using the sensitivity GCD. onRender3D applies those deltas through setAngles on every render frame while the left mouse button is down (onlyClick is on by default), so the rotation that reaches the server inside C03 is the player's own rotation, gently pulled toward the target in gcd-sized steps rather than snapped. The strength setting, the +1.0 jitter on the target angles, the fixed-rotation smoothing against Aura's last rotations and the pitch clamp all exist to make that pull look like mouse movement.

Rotation math

The step size comes from the strength setting: s = (strength maximum minus the value) plus one, and the per-tick correction is (target rotation minus current rotation) divided by max(2, s), so a low strength value produces a large divisor and a slow pull, and strength 50 (s = 1) still divides by at least 2. The target angles are jittered by a random double before the error is computed, and getRotations feeds the raw angles through RotationUtil.getFixedRotation against Aura's last rotations, which clamps the per-update change to the smoothed rate the aura machinery allows, before the pitch is clamped to plus or minus 90. The result is a rotation that approaches the target exponentially and never overshoots.

GCD quantization and application

The mouse sensitivity is folded into the classic 1.8 GCD formula: f = sensitivity times 0.6 plus 0.2, gcd = f cubed times 8. deltaX and deltaY are computed as round(niggaYaw / gcd) and round(niggaPitch / gcd), so every applied correction is a whole number of gcd steps. onRender3D then rebuilds the delta as (mouse delta plus the stored correction minus the mouse delta), multiplies back by the gcd, applies the invert-mouse sign to the pitch, and calls setAngles only while the left button is held and no screen is open (onlyClick), or unconditionally when onlyClick is off. Because setAngles modifies the real rotation, the C03 stream carries the corrected rotation, and because the correction is re-derived from the live mouse delta each frame, the module composes with the player's own mouse input rather than replacing it.

Targeting

getClosest walks the loaded entity list, keeping the nearest living entity within range that passes canAttack: players, animals, mobs and villagers are filtered by their toggles, invisibles and dead entities by theirs, team-mates are skipped when teams is on, AntiBot-listed entities are always skipped, entities younger than two ticks are ignored, friends are excluded by name, and the player itself is never a target. The target is a static field shared with the rest of the combat modules. onDisable zeroes the stored deltas so a disabled module leaves no pending correction.

What this file does

The module is two handlers and a target scan. onPreMotion resolves the closest valid target and computes the correction: the strength-derived divisor s, the jittered target angles, the fixed-rotation smoothing against Aura's stored rotations, and finally the GCD quantization that converts the floating-point error into whole mouse deltas (round(niggaYaw / gcd)). The wire presence of the module is the C03 rotation stream: gcd-quantized, smoothed steps toward a target while the button is held, with the rotation otherwise following the player's own mouse.

What this file does

getFixedRotation is the smoothing layer the assist leans on. It takes the desired rotation and the last rotation, computes the wrapped per-axis difference, and caps the change so the output never moves more than the allowed step per call; the assist feeds it the raw aim angles and Aura's previous rotations, so the per-tick rotation change is bounded before the GCD quantization ever sees it. The same utility serves the Kill Aura rotation system, which is why the assist and the aura share one smoothness budget: the assist's output is post-smoothed by the same function the aura uses for its own silent rotations, keeping the two on a consistent rate.

How it counteracts this module

AimbotConvergence builds a ray from each consecutive pair of head positions and directions, computes the closest point between the pre-move and post-move rays, and flags when that convergence point stays fixed across moves (squared distance under 1e-8), with teleport and early-tick exemptions. The comment in the check's source states the failure mode directly: 'You better turn off your aimbot when your opponent is standing still'. The assist's steady state is exactly that: the view is pulled toward the target's head on every frame, so the rays from the moving player converge on the target's head location and the convergence point does not move, which is a punishment. The assist cannot shed the signature by slowing down, because any nonzero pull keeps the convergence on the target; the only escape is a target that moves erratically enough to shift the convergence point every tick.

How it counteracts this module

NCP's fight.Angle analyzes the C02 attack stream rather than raw rotations: it accumulates the average move between hits (a violation component when the attacker stays within 0.2 blocks of the same spot), the average time between hits (a component when the interval is under 150ms), the average yaw difference (a component above 50 degrees), and the yaw change on target switches (above 30 degrees when the entity id changes). On servers running NCP the check is the constraint that turns the ghost module into a risk once attacks are layered on top of the aim pull.

How it counteracts this module

Hawk's EntityInteractDirection validates that an interaction points at the victim by ray-casting the reported direction against the victim's lag-compensated hitbox, expanded by the boxExpand setting, with the player's head position as the origin. The assist's purpose is keeping the facing inside that cone, so the check does not catch the module on its own; it constrains the combined aim-plus-attack behavior, punishing any assisted attack whose rotation drifts off the victim while the click lands. The lag compensation matters to the assist: the check evaluates the direction against the victim's position from ping milliseconds ago, the same history the assist's own client-side interpolation uses, so a fast-moving victim is where the cone check and the assist's smoothing can disagree.
