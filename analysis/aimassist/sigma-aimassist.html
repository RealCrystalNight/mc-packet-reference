Overview

Sigma 4.11's AimAssist is a rotation-only aim smoothing module that never sends an attack itself. It picks a target in the pre phase of EventUpdate, caches it, and in the post phase (only when no GUI screen is open and the player holds a sword, per the WEAPON toggle) steps the local yaw and pitch toward that target with a hard per-tick cap: the rotation moves by exactly SPEED-H (default 20) degrees of yaw and SPEED-V (default 15) degrees of pitch per tick, and when the remaining angle is within the cap it snaps the exact remainder, so the view converges on the target and parks. The aim point is jittered by randomNumber() (an integer -1, 0 or 1) times the RANDOM-XZ and RANDOM-Y settings around the target's position, the pitch target carries a hardcoded 2.5-degree undershoot bias from RotationUtils.getPitchChange, and target selection is gated by RANGE (default 4.5) plus a distance-scaled FOV check (FOVYAW/FOVPITCH default 45/25, widened as the target gets closer). There is no click gating and no attack packet: the module rotates every post-update tick a sword is held, so its rotations ride the player's normal C03 movement stream while the player's own clicks (or Killaura) provide the C02 attacks the assist lines up.

Because the rotation is written straight into mc.thePlayer.rotationYaw/rotationPitch after the pre-update, it lands in the next tick's movement packet, which is what makes the module's pattern visible to rotation analysis: fixed-magnitude per-tick deltas, exact-remainder snaps, and a view that converges on a single world point.

Architecture

The module hooks EventUpdate with pre and post phases split across two responsibilities. onEvent caches the target in pre via getBestEntity() so the selection runs on the server-facing update, then in post, guarded by mc.currentScreen == null, it runs the weapon gate (if WEAPON is on, the held item must be an ItemSword), the friend check and the alive check, and calls stepAngle(). The two-phase split means the target list is fresh for the tick while the actual rotation is applied after the movement update, so the assist's output shows up in the following packet rather than the current one.

State is a single target field; all parameters live in the settings map (WEAPON, RANGE, SPEED-H, SPEED-V, FOVYAW, FOVPITCH, RANDOM-XZ, RANDOM-Y). A quirk worth noting: the SPEED-H and SPEED-V defaults (20 and 15) sit above their declared slider maximum of 10, so a stock install rotates at the out-of-range values until the user moves the slider.

Rotation model (stepAngle)

stepAngle computes the signed yaw and pitch differences to the aim point through RotationUtils.getYawChange and getPitchChange, then applies a clamp-or-snap policy per axis. If the target yaw change is positive and larger than yawFactor the view advances exactly yawFactor; if negative and below -yawFactor it retreats exactly yawFactor; otherwise it adds the full remainder, which snaps the view precisely onto the target line. The pitch axis repeats the same policy with pitchFactor. The result is a piecewise-linear rotation: constant-magnitude steps while far off target, one exact-remainder snap on arrival, then zero movement while aligned.

The aim point itself is jittered: yaw aims at (target.posX + randomNumber()*xz, target.posZ + randomNumber()*xz) and pitch at target.posY + randomNumber()*y, where randomNumber() returns -1, 0 or 1, so the RANDOM-XZ and RANDOM-Y settings (default 0) define a +/-one-block box the aim point hops inside every tick. getPitchChange also bakes in a constant -2.5F offset, so the assist settles 2.5 degrees below the exact pitch line rather than on it.

Target selection (getBestEntity + fovCheck)

getBestEntity walks the loaded entity list and keeps EntityLivingBase entries that are alive EntityPlayers within RANGE and pass fovCheck. The FOV check is distance-scaled: the effective window is FOVYAW*3/dist and FOVPITCH*3/dist, so a nearby target is allowed a wider angular offset than a distant one. Killaura.vip short-circuits the entire selection: if the Killaura module's current VIP target is in range and inside the FOV, it is returned immediately. Otherwise the candidates are sorted by the summed yaw and pitch angular distance to the player's current rotation and the closest-to-crosshair entity wins, which biases the assist toward whatever the player is already facing.

There is no attack path anywhere in the module: no C02 packet is ever produced, no swing is faked, and no click requirement exists. The module's only output is the rotation mutation, which is precisely what makes it detectable by rotation-pattern checks rather than by attack-pattern checks.

What this file does

The whole module lives in this file. onEvent implements the pre/post EventUpdate split: pre caches the target, post (screen null, weapon check passed, target alive and not a friend) calls stepAngle. stepAngle implements the clamp-or-snap policy with the SPEED-H/SPEED-V factors and the RANDOM-XZ/RANDOM-Y jittered aim point. getBestEntity applies the RANGE gate, the fovCheck distance-scaled window, the Killaura.vip shortcut and the angular-distance sort. fovCheck computes yawDist and pitchDist with RotationUtils.getDistanceBetweenAngles against the distance-scaled FOV.

The file also shows what the module does not do: it never sends packets, never checks clicks, and mutates the player's rotation directly instead of writing into the EventUpdate's yaw/pitch fields, which is why its rotations appear one tick late (they are picked up by the next movement packet) and are not correlated with any outgoing C02. The settings block documents the defaults and ranges, including the SPEED-H/SPEED-V defaults (20/15) that exceed the slider max (10).

What this file does

RotationUtils is the aim math the module depends on. getYawChange computes the signed, wrapped yaw delta from the player to the aim point using quadrant-aware atan math and MathHelper.wrapAngleTo180_float. getPitchChange computes the pitch delta with a -2.2 eye-offset adjustment and a hardcoded -2.5F undershoot, which is why the assist always settles slightly below the exact aim line. getRotations (used by getBestEntity's sort) aims at posY + eyeHeight/2, and getDistanceBetweenAngles returns the wrapped angular distance used by both fovCheck and the candidate sort.

These helpers define the module's observable signature: per-tick deltas that are either exactly the configured factors or the exact float remainder of an atan2 computation, wrapped into [-180, 180). A real mouse at a fixed sensitivity produces deltas quantized to sensitivity steps; this stream produces fixed factors plus continuous remainders, which is the pattern the countering rotation checks below key on.

How it counteracts this module

Hawk's AimbotConvergence detects rotation that is aimed at a fixed point in space by intersecting sight lines. On every MoveEvent with a position delta it builds two rays: a pre-move ray from (from - velocity) plus the 1.62 eye height along the pre-move direction, and a post-move ray from (from) plus 1.62 along the post-move direction, computes closestPointsBetweenLines between them and takes the midpoint as the convergence point. If the convergence point moved less than 1e-8 (squared distance) between consecutive moves - and the player is older than 100 ticks and more than ping/50 + 10 ticks past the last accepted teleport - it punishes with 'failed aimbot (convergence)' at VL 5, otherwise it rewards. The class comment states the model outright: 'You better turn off your aimbot when your opponent is standing still!'

Sigma's AimAssist is a direct hit when RANDOM-XZ/RANDOM-Y are at their defaults (0): the aim point is exactly the target's posX/posZ/posY, so the pre-move and post-move sight lines intersect at the target and the convergence point is the target's position, which stays fixed while the target stands still (or moves smoothly), tripping the 1e-8 stability test on the following move. The weapon gate means the pattern only exists while a sword is held, and the module's rotations lag one tick behind motion, which is exactly the rotation-versus-motion relationship the check was built to expose.

Bypass surface: the RANDOM-XZ/RANDOM-Y jitter. randomNumber() is -1, 0 or 1, so each tick the aim point hops by up to +/-xz (and +/-y) blocks; the convergence point jumps with it and never satisfies the 1e-8 stability window. A target strafing at speed also moves the convergence point between ticks, which is why the check needs a fairly static target to fire at all.

How it counteracts this module

AimbotHeuristic analyzes mouse movement only inside a window around interactions. It records each move's yaw/pitch delta as a vector, records click ticks from InteractEntityEvent/InteractWorldEvent, and on every move where a click happened MOVES_AFTER_HIT (2) ticks ago it inspects the last 4 moves for three patterns. Branch C (jump discontinuity): speed drops by more than 30 between consecutive moves with an angle over 0.8 radians. It is a cancelless hint check (VL 5, 'failed aimbot (heuristic)').

Sigma's stepAngle produces exactly the branch A shape inside the click window: while far from the target the view advances at the constant SPEED-H/SPEED-V factor, then the exact-remainder snap parks it, so the sampled moves are a fixed-speed run followed by a stall (minSpeed < 0.01), all along the bearing to the target (maxAngle stays under 0.1 rad), with maxSpeed - minSpeed equal to the step factor (default 20 > 4). The module never clicks itself, but the WEAPON gate guarantees it runs while the player is attacking with the sword, so clicks are present in the window. Branch C can also fire when the target crosses the view line and the required delta reverses sign between ticks.

Bypass surface: the check only fires when a click lands in the 2-tick window, and branch A needs the speed spread. Lowering SPEED-H/SPEED-V to a few degrees per tick shrinks maxSpeed - minSpeed below 4 and keeps lastSpeed at or under 1, which defeats branch A; the module still assists, but the sample statistics fall inside human range.

How it counteracts this module

AimbotPrecision detects aim-bots by solving the greatest common divisor of pitch deltas. It collects |deltaPitch| values that are nonzero, at most PITCHRATE_LIMIT (config 'ignorePitchrateHigherThan', default 0.96 degrees) and not at +/-90 pitch; once 10 samples accumulate it computes the rational GCD, and if the new GCD differs from the previous batch by more than 0.001 it folds the previous GCD into the sample and recomputes. It then fails when the GCD is 'practically unsolvable' (below 1e-5) and rewards otherwise, keeping the GCD as the rolling baseline. The class comment explains the model: every legit pitch change is divisible by the constant determined by the in-game mouse sensitivity, so a stream of real deltas must share a GCD, while a stream of arbitrary deltas has none.

Sigma's default rotation is caught on its snap ticks, not its steps. The 15-degree pitch steps are above the 0.96 sampling cap, so the sustained rotation never enters the window. What does enter is the exact-remainder snap: when the pitch remainder falls below the cap, stepAngle adds the remainder - a float derived from atan2 of entity positions, effectively continuous precision. Once one such remainder joins the 10-sample window, the rational GCD of the batch collapses below 1e-5 and the check fails. Detection therefore lands on convergence episodes; a target that keeps moving keeps feeding fresh remainders and keeps the window failing.

Bypass surface: the check samples nothing while deltas are zero or above 0.96, so a stock module is invisible during the constant-speed phase and only exposed at the snap. Configuring SPEED-V to a value at or below 0.96 puts every step into the window, but then the stream is exact fixed factors plus exact remainders, and the GCD still collapses once a remainder joins; the only clean pass is a target that stays aligned long enough that no nonzero sub-0.96 delta is ever produced.

How it counteracts this module

Spartan embeds Millennium's SensitivityProcessor as the rotation layer its aim checks read. processSensitivity() takes the GCD of consecutive pitch deltas and maps it through the Minecraft sensitivity formula (modifier = cbrt(0.8333 * gcd), finalSensitivity = (1.666 * modifier - 0.3333) * 200). A strict path handles small deltas: for |deltaPitch| below 0.31 it scans the 200-entry SENSITIVITY_MCP_VALUES table (each entry is the per-pixel rotation of a sensitivity setting) and records an index when the table's gcdValue matches the delta within 1e-3. The mode of the last 40 samples becomes the player's sensitivity and is pushed into playerProfile.getSensitivity() for the rotation checks to consume; the same model appears in Spartan's utils/math/Sensitivity.calculateSensitivity (deltaYaw / gcdValue).

Sigma's rotation stream cannot be attributed to any sensitivity. At the default SPEED-V 15, consecutive pitch deltas have a GCD of 15, which the formula converts to roughly 706 - far beyond the 0-200 table, so no valid sensitivity is derived. The snap-phase remainders are position-derived continuous floats whose GCD is unsolvable, landing near index 0. Either way the processor reports an invalid or wildly unstable sensitivity, which is the exact signal the aim checks treat as non-human. Only a SPEED-V low enough that the gcd maps inside the table (steps below roughly half a degree per tick) produces a valid sensitivity, and then the whole stream collapses to one fixed value - the signature of a single mouse setting, which the strict path treats as normal, making that the one configuration that survives the grid.
