Rise 5.99 Stealer — Full Source Analysis

Rise 5.99's Stealer empties chests through the vanilla container protocol: it waits for the S30PacketWindowItems content refresh, pauses a randomized delay, then shift-clicks one item at a time with C0EPacketClickWindow (mode 1, button 0) against the chest window id. Overview

Rise 5.99's Stealer empties chests through the vanilla container protocol: it waits for the S30PacketWindowItems content refresh, pauses a randomized delay, then shift-clicks one item at a time with C0EPacketClickWindow (mode 1, button 0) against the chest window id. The delay is redrawn from the min/max settings after every steal, the whitelist keeps junk in the chest unless the trash toggle is on, and Auto Close releases the GUI once the client-side view is empty. The module also publishes three static flags that a GUI mixin consumes: hide the chest screen, allow mouse look inside the chest, and close after the container empties.

Steal loop and delay drawing

onRender2DEvent drives the loop. On the first frame inside a chest, decidedTimer is drawn with RandomUtils.nextInt(floor(min), ceil(max)); both delay settings default to 5ms over a 0-1000ms range with 25ms increments, so the stock configuration drains a double chest in under a second. When the timer has reached the draw, the module walks chest.inventorySlots in order and shift-clicks the first whitelisted stack via windowClick(chest.windowId, i, 0, 1), then resets the timer and redraws the delay from the same distribution. One item per draw, one C0E per item, and the draw is fresh for every steal, which is the module's answer to click-rate checks: the rate is bounded by the delay settings, not by the render loop.

Whitelist and the inverted trash toggle

itemWhitelisted accepts potions whose metadata effect id is in {6, 1, 5, 8, 14, 12, 10, 16} (instant health, speed, strength, jump boost, invisibility, fire resistance, regeneration, night vision), any block item except TNT, slime and falling blocks, plus anvils, swords, armor, tools, food, skulls and any stack whose display name contains a section-sign color code. A ten-entry material list adds ender pearls, iron and gold ingots, redstone, diamonds, emeralds, quartz, bows, arrows and fishing rods; the spider-eye exclusion only guards that list because && binds tighter than ||. The 'Steal trash items' toggle is inverted: the steal condition requires itemWhitelisted(stack) AND NOT the toggle, so enabling it makes the predicate false for every stack and the module stops stealing entirely.

GUI cooperation and close

onPreMotion recenters and re-grabs the mouse while a chest GUI is up (mouseInput and hideGui both default on), which releases the vanilla grab so the player can look around inside the chest; the static hideChestGui and allowMouseInput flags are consumed by code outside this file, and closeAfterContainer is declared but only ever cleared here. gotItems is armed by any S30PacketWindowItems and by every steal, ticksInChest counts time inside the GUI, and autoClose calls closeScreen() once the client-side view is empty (gotItems or more than 10 ticks). Both packet handlers and the steal loop bail for the first 60 ticks after spawn, and the world-change handler can auto-disable the module.

What this file does

The steal loop lives entirely in onRender2DEvent, with onPreMotion handling mouse release and the screen-fade counter, onPacketReceive arming gotItems from S30PacketWindowItems, and onWorldChanged providing the auto-disable. The container interaction is a single line: windowClick(chest.windowId, i, 0, 1) is the vanilla shift-click, which the server applies as a MOVE_TO_OTHER_INVENTORY action on the chest window. The whitelist is a mixture of item-class checks, potion metadata effects and display-name scans, all re-evaluated per candidate stack.

The static flags are the module's contract with the rest of the client: hideChestGui and allowMouseInput tell a mixin to suppress the chest screen and free the mouse, which is what makes the steal look like normal play instead of a locked GUI session. The inverted trash toggle is a genuine logic bug: with the setting on, the predicate (whitelisted AND NOT enabled) is always false, so nothing is ever stolen. The delay pair defaults to 5ms/5ms, which at stock settings turns a chest drain into a sub-second burst.

What this file does

TimeUtil is the module's timing backbone: lastMS anchors the window, reset() re-anchors it, and hasReached(milliseconds) compares the elapsed nanoTime-based time against the argument, so the steal pacing is monotonic and immune to wall-clock jumps. getCurrentMS reads System.nanoTime() divided by 1e6, the same basis as the module's RandomUtils delay draws.

Stealer uses two TimeUtil instances: timer gates the per-item delay and startTimer tracks how long the player has been inside the chest (reset on every frame where the chest was not open the previous frame). The decidedTimer value is drawn once per steal from RandomUtils.nextInt over the floor and ceiling of the two delay settings, so the actual pacing is a uniform random walk within the configured band, which spreads the C0E clicks across the window instead of firing them at a fixed interval.

How it counteracts this module

NoCheatPlus FastClick scores InventoryClickEvent traffic into an ActionFrequency with five 200ms buckets: the newest bucket is compared against the short-term limit of 4 and the full window against the normal limit of 15, with TickTask lag division before the comparison. A plain shift-click with an empty cursor counts 1.0 via getAmountWithAction; the legacy detectTweaks1_5 weighting only kicks in when the cursor already holds a stack, scaling the count down by stack size. The check also carries the container-interaction path: isContainerInteractionRecent compares the latest click against the container open time, and any click landing within the 155ms min-interaction-duration default adds a violation of (155 / duration) * 100.

Stealer's default 5ms delay puts roughly 200 C0E clicks per second into the buckets, or about 40 per bucket, so the short-term limit of 4 is exceeded by an order of magnitude on the first bucket and fastClickVL climbs past the cancel action at vl>150 within the first second of a drain. The randomized delays do not help: even at a generous 100ms average the module still lands 5 clicks per bucket. The interact_time path also fires because the first click usually lands well inside the 155ms window after the chest opens. The whitelist is irrelevant to the check, which is content-blind and counts every shift-click regardless of what was stolen.

NCP's Open check watches PlayerMoveEvent traffic while an inventory window is open. checkOnMove skips duplicate packets, vehicles, creative quickbar clicks, merchants and velocity-affected moves, then decides whether the move carries an impulse: with 1.21.1+ input it reads the WASD/jump bits directly, otherwise it falls back to the movement model's hasImpulse decision. An impulse while open feeds Improbable and returns true, and the caller force-closes the inventory, resetting inventoryOpenTime and containerInteractTime.

Stealer does not suppress movement: the module only manipulates the container, so any strafing or stepping while the chest GUI is open is visible to the check, and a single impulse move mid-steal closes the chest and aborts the drain. The practical tension is that stealers stand still, so a careful user never trips it; the check still matters because it converts a movement mistake into a lost window, and because it resets the timestamps that FastClick's interact_time path reads, wiping the open-time baseline the module's first-click timing is measured against.

How it counteracts this module

Hawk's InventoryActions punishes world interaction while a window is open and, more importantly for stealers, punishes ClickInventoryEvent packets when HawkPlayer.hasInventoryOpen() is zero. Hawk derives the open state from the S2D window-open, C16 inventory command and close packets, so it tracks the same window lifecycle the server sees, not the client's GUI state.

Stealer's Auto Close path calls closeScreen() client-side the moment the viewed contents look empty. If the server-side window close (C0D, or the server's own close) lags behind, or if the S30 refresh that armed gotItems arrived for a stale window id, the client can emit a C0E for a window Hawk already considers closed, and that click is punished with a resync. The world-interaction branch is the other edge: the module's mouse release makes it easy to swing or interact while the chest screen is hidden, and any InteractEntity, BlockDig, ArmSwing or InteractWorld event while the window flag is non-zero is punished and resynced. The check is content-blind and window-id aware, so randomized delays change nothing.

How it counteracts this module

Hawk's InventoryMove check runs on MoveEvent and punishes rotation updates, sprinting or sneaking while an inventory is open, with an explicit exclusion for teleport-accept moves. punishAndTryRubberband sends the player back on violation, and the VL decays via reward on clean moves.

This is a direct hit on Stealer's default configuration. The 'Move head in chest' feature (mouseInput) deliberately recenters and re-grabs the mouse every pre-motion so the player can look around inside the chest GUI, which produces exactly the isUpdateRot-with-open-inventory pattern the check is built for: every head turn while the chest is open scores a violation. Sprint and sneak states are equally visible because the module never sends C0B suppression. The check cannot be avoided by the randomized delays, since it keys on rotation and movement state, not click timing; the only safe configuration is mouseInput off and the player holding still.
