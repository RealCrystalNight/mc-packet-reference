Overview

LiquidSense Dev's ChestStealer drains chests from a Render3DEvent that fires every frame: while a GuiChest is open and the randomized delay has passed, it shift-clicks one slot through GuiContainer.handleMouseClick, which emits C0EPacketClickWindow mode-1 packets against the chest window. Filters gate the steal: NoCompass skips while holding a compass, ChestTitle requires the container name to contain Chest, OnlyItems skips block stacks, Useful runs every stack through InventoryCleaner.isUseful, and CloseOnFull stops when the player's 36 main-inventory slots are full. The close and the silent-stealer mode are keyed off the window id reported by S30PacketWindowItems so the GUI is only released for the window the server actually opened.

Frame-driven steal loop

onRender3D is a render-frame handler, not a tick handler, so the steal cadence is bounded by the delay gate rather than the frame rate. nextDelay is drawn from TimeUtils.randomDelay(minDelay, maxDelay), defaults 150-200ms over a clamped 0-400ms range with cross-clamping on either value changing. In the randomized mode the module collects every stealable slot, picks one with kotlin.random.Random, and moves it, repeating in a do-while as long as the delay keeps passing, so several slots can move within one frame when the delay is at the floor. The non-random mode walks the chest rows in order and moves every slot whose gate is open. Only the chest's own rows are scanned (inventoryRows times 9), never the player's bottom slots.

Filters

noCompass returns early while the held item's unlocalized name is item.compass; chestTitle requires the lower inventory's name to contain the display name of a minecraft:chest item stack; onlyItems skips ItemBlock stacks; useful runs InventoryCleaner.isUseful(stack, -1), which classifies swords and tools against the equipped slot and rejects junk; closeOnFull reads fullInventory, true when every one of the 36 main-inventory slots is non-null. isEmpty mirrors the useful filter over the chest rows and feeds the auto-close branch. The chestTitle filter reads lowerChestInventory, which in the chest screen is the player's own inventory section titled with the fixed container.inventory string, so the contains-Chest test effectively never matches and enabling that toggle stalls the stealer entirely.

Window id matching and silent close

onPacket stores the window id from every S30PacketWindowItems into contentReceived. The auto-close branch only fires when screen.inventorySlots.windowId equals contentReceived and the close delay has passed, so the GUI is released only after the server refreshed the very contents the client is looking at. The silent mode (spelled slientstealer in the source) closes the GUI as soon as that match holds, which drops the chest screen before the player presses a key; because the steal gate requires a live GuiChest, clicking stops at the close. The module imports C03PacketPlayer but never references it; the only packet it actually sends is the C0E generated inside handleMouseClick.

What this file does

The whole module is two event handlers and a move helper. onRender3D performs the steal: delay gate, filter chain, slot selection, then move() which calls screen.handleMouseClick(slot, slot.slotNumber, 0, 1); that is the vanilla shift-click path and the source of every C0EPacketClickWindow the module emits. onPacket consumes S30PacketWindowItems for the window-id match that guards the close branches. The value objects cross-clamp min/max on change and redraw nextDelay so the band never inverts.

The dead C03PacketPlayer import is a telling detail: the module is pure container manipulation and never touches movement packets, so its server-side signature is a stream of window clicks, not position changes. The ChestTitle filter reading lowerChestInventory (the player inventory section) instead of the upper chest section makes that toggle effectively inert, and the silent mode is simply an early close rather than a true continue-stealing-after-close, because every handler returns when the screen is no longer a GuiChest.

What this file does

InventoryCleaner is a sibling player module whose isUseful(itemStack, slot) method ChestStealer borrows as its junk classifier. The method accepts swords and tools only when they beat the equipped item (findBetterItem against the given slot), accepts armor by type and tier, and rejects consumables and materials it considers worthless; slot -1 means the stack is not in the player's inventory, which is the case for every chest slot. The module fetches the singleton through LiquidBounce.moduleManager and calls isUseful(stack, -1) both in the steal scan and in isEmpty.

This coupling means ChestStealer's stealable set is defined by another module's value system: enabling Useful keeps the chest's garbage in place and drains only what InventoryCleaner would keep, while disabling Useful steals every non-null stack the other filters allow. The same isUseful routine drives the InventoryCleaner module's own moving, so the two modules share one classification policy.

ChestStealer does nothing to hide these states: it never cancels movement packets and never suppresses rotation, so a player who opens the chest while holding W or sneaking, or who turns to check surroundings mid-steal, trips the check immediately. The vanilla chest GUI normally grabs the mouse and blocks look, which is the main reason rotation-while-open is rare in legit play, but the module offers no protection for the sprint and sneak flags, which persist from the moment of opening. The randomized steal delays are irrelevant to this check, which scores movement state, not click cadence.
