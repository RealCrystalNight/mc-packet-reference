Analysis

Overview

Sigma 4.11's NoRotate is a receive-side packet mutator that stops the server from rotating the player. It registers for EventPacket and, when an incoming S08PacketPlayerPosLook arrives, overwrites the packet's yaw and pitch with the client's current rotationYaw and rotationPitch before the packet is processed. The fork's NetworkManager fires the event in channelRead0 before packet.processPacket, so the mutation lands before NetHandlerPlayClient.handlePlayerPosLook runs: setPositionAndRotation then applies the server's position but the client's own angles, the camera never snaps, and the client's reply C06 echoes its own rotation unchanged. Position teleports still apply in full; only the rotation half of the S08 is discarded. The module sends no packets of its own and is invisible on the wire except for the C06 echo that disagrees with the S08 rotation the server just sent.

Interception point

NetworkManager.channelRead0 fires EventPacket with the outgoing flag false (line 151) before processPacket dispatches to the handler, and sendPacket fires it with true (line 207). NoRotate's isIncoming() guard therefore selects exactly the receive path, and the instanceof selects the S08. The rewrite happens in place on the single EventPacket instance, so when handlePlayerPosLook (NetHandlerPlayClient line 599) later reads packetIn.getYaw() and getPitch(), it reads the client's own angles, applies them via setPositionAndRotation (line 634), and echoes C06PacketPlayerPosLook with rotationYaw/rotationPitch (line 635) - which are the client's angles, because the rewrite already happened. The X_ROT/Y_ROT relative-flag accumulation (lines 626-632) is applied to the already-rewritten values, so relative teleports are handled consistently too.

What survives and what does not

Only the rotation is discarded. The x, y, z fields (and the X/Y/Z relative flags that add onto the current position) pass through untouched, so teleport-based position corrections, anti-phase set-backs and server-side position resyncs all still take effect; the module only cancels the visual and reported rotation change. The client's own rotation is what the C06 echo carries, which is what makes the module visible to a server that compares the rotation in the S08 it sent against the rotation in the subsequent C06: vanilla clients echo the S08 angles, a NoRotate client echoes its own.

Wire fingerprint

The module adds no packets. The observable is the C06 reply to each S08: the yaw and pitch fields carry the client's pre-teleport rotation instead of the teleport's angles, and the client's subsequent look updates continue from that rotation. Servers that enforce a teleport-rotation convergence window would see the gap; none of the anticheats in this reference set do, because none of them model S08 rotation compliance.

AimbotConvergence is Hawk's closest thing to a rotation-pattern check, and it is aimed at a different target entirely. How it counteracts this module

Arc v2's PacketListener is the complete list of packets the anticheat observes, and it is entirely serverbound. startListening registers ProtocolLib adapters for Play.Client.FLYING, POSITION and POSITION_LOOK (the movement layer), USE_ENTITY (fight data and KillAura), ARM_ANIMATION (swing timing), HELD_ITEM_SLOT (soup switching) and BLOCK_PLACE (the soup auto-heal branch). The consequence is total invisibility. Arc v2 never sees the S08 the module rewrites, never sees the C06 echo's rotation, and has no data structure that could hold a server-issued rotation to compare against. Its movement checks (Speed, Flight, MorePackets, NoFall) consume only the serverbound position stream, where the module's effect - an unchanged rotation echo - is indistinguishable from a vanilla client that happens to look the same way. This entry closes the gap: of the three anticheats, Arc v2 has the least surface for NoRotate, which is to say none.
