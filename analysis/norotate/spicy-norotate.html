Analysis

Overview

Spicy's NoRotate cancels the rotation half of server teleports. Its single event branch handles EventServerSetYawAndPitch, the wrapper around the yaw and pitch fields of an incoming S08PacketPlayerPosLook, and cancels it pre, with an optional Notify setting that surfaces a message when the server tries to rotate the player. The position half of the teleport still applies, so coordinates stay synchronized and only the aim is kept. The module sends no packets and produces no movement of its own; it exists to stop lag-back and checkpoint teleports from snapping the player's view.

Architecture

The module carries a single BooleanSetting (Notify, default false) and two empty lifecycle methods. All behavior lives in one event branch: when an EventServerSetYawAndPitch arrives in the pre phase, the handler calls event.setCanceled(true), which stops the client from applying the server's yaw and pitch, and optionally sets event.notify from the setting so the user sees a message when the server attempts a rotation. resetSettings re-registers the setting so config loads cannot add stale entries.

Key techniques

The effect is purely cosmetic control. After any server teleport with rotation, a lag-back, pearl, portal or checkpoint, the client keeps its own aim instead of snapping to the server's angles. The position half of the teleport still applies, so the player's coordinates stay synchronized and movement checks see no desync. The cancel happens before the rotation is written to the player, so no reverse-rotation packet is needed or sent; the module never constructs a packet and never touches position or velocity.

Detection surface

The module has no wire signature: it trims an inbound packet field, and the client's subsequent C03 stream carries whatever the player actually does. The S08/C03 listing reflects that stream: S08 is the teleport being trimmed, and C03 is the movement that continues from the retained rotation afterward. No server-side check can observe the cancel, because the rotation the server sent is never echoed back in comparable form; the enforcement that remains is the positional ledger and movement envelopes around the teleport.

How it counteracts this module

TeleportQueue implements NoCheatPlus's teleport acknowledgment contract: outgoing S08 teleport locations are queued, and further movement is cancelled until the client acknowledges the previous teleport, which is why the movement checks can trust post-teleport positions. The queue is the net-side state every S08-consuming check reads.

NoRotate cancels only the yaw and pitch application of the server teleport, and the position half still lands client-side, so the player's reported position remains synchronized with the server's expectation and the acknowledgment flow is unaffected. A NoRotate user who moves normally confirms teleports in order and the ledger is satisfied; the module's cancel is invisible to the queue because rotation is not part of the acknowledgment. The queue matters to a NoRotate setup only through the movement modules that typically accompany it: speed and phase desyncs generate lag-back S08s, and the client must confirm each one before further moves are processed, so unacknowledged teleports still snap the player back.

The boundary: the check never sees the rotation cancel, and no position-based check can, because the rotation data of S08 is not re-sent by the client in any comparable form. NoRotate is a display-side convenience that defeats only the cosmetic snap; every positional enforcement on the server continues to apply in full.

How it counteracts this module

Hawk's Speed check rebuilds the allowed horizontal motion per MoveEvent and punishes deltas that exceed the envelope for the player's movement mode, through the standard punish-and-rubberband path with reward decay. It is the horizontal speed bound for Hawk's movement package.

NoRotate changes no position data: it cancels the EventServerSetYawAndPitch handler, so the client keeps its own yaw and pitch after a server teleport, but the player's coordinates and velocity are exactly what the vanilla client would report. The horizontal deltas stay inside the envelope and the check passes regardless of the module's state. It remains in the countering set because rotation-cancel is commonly paired with movement cheats whose horizontal deltas do breach the envelope, and Hawk's rubberband then re-teleports the player through the very S08 stream NoRotate is trimming.

The boundary is the module's design: NoRotate defeats only the teleport rotation, never the teleport position, so a speed module running alongside still gets rubberbanded to the server's position on every violation. This check has no rotation-consistency component, so it cannot see the cancel either way.

How it counteracts this module

EntityActionAdapter is the ProtocolLib bridge in NCPCompatProtocolLib that converts serverbound C0BPacketEntityAction packets into the entity-action state the net checks consume: sprint and sneak toggles are validated and translated into player state before the movement pipeline reads them. It is part of the net package's packet handling rather than a standalone flagging check.

NoRotate never emits a C0B packet: the module's single event branch cancels EventServerSetYawAndPitch and touches nothing else, so the adapter's input stream is identical whether the module is on or off. The sneak and sprint state it maintains is therefore as trustworthy for a NoRotate user as for any other player, and the movement checks that read that state keep working.

The boundary: the adapter has no view of S08 rotation at all, because rotation is delivered through the position-look teleport, not through entity actions. It is included here as the net-side state feed that remains fully effective for the companion modules; the rotation cancel itself is outside every check in this entry list.
