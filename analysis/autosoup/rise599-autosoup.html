Overview

Rise 5.99's AutoSoup is a health-gated soup chugger that selects the stew hotbar slot with a C09 held-item change, fires a use with C08, and on the following tick sends the C07 release, an optional drop, and the switch back. The gate is ticksExisted greater than 10 and getHealth() below the Health setting (default 15), and the cycle repeats on a randomized delay between Min Delay and Max Delay (defaults 300-500ms). There are no window clicks anywhere: the entire mechanism is C09/C08/C07 slot traffic against the player's own hotbar, which is what separates this implementation from soup modules that shuffle inventory with C0E window clicks. The drop-bowl toggle additionally emits a C07 DROP_ITEM after the release, which discards the empty bowl from the held slot.

Two-tick eat cycle

The eat is split across two pre-motion events. The first tick, gated on ticksExisted > 10 and getHealth() below the threshold, locates soup with PlayerUtil.findSoup(), converts the container slot to a hotbar index (findSoup() - 36, with -37 as the not-found sentinel), and sends C09PacketHeldItemChange(soup) followed by C08PacketPlayerBlockPlacement with the soup stack, arming the switchBack flag. The next tick's switchBack branch sends C07PacketPlayerDigging RELEASE_USE_ITEM at BlockPos.ORIGIN facing down, then optionally a second C07 DROP_ITEM when dropBowl is enabled, then C09 back to the player's real held slot. The release and the slot restore are thus always one full tick after the use, never in the same tick as it.

Delay and sentinel handling

The cycle is clocked by a TimeUtil and a decidedTimer millisecond value. When the gate opens, the module computes delayFirst as floor of the lower bound and delaySecond as ceil of the upper bound, then picks RandomUtils.nextInt(delayFirst, delaySecond) and resets the timer, so the default 300-500ms settings yield roughly 2-3 eat cycles per second while health stays low. If findSoup() returns -1, soup stays at the -37 sentinel and the C09/C08 pair is skipped, but the delay is still re-rolled, so an empty hotbar does not accelerate the loop. The ticksExisted > 10 guard suppresses eating during the first half-second after spawn or respawn.

Wire fingerprint

Each successful cycle emits, across two ticks: C09(soup), C08(use with the soup stack), then C07 RELEASE_USE_ITEM, C07 DROP_ITEM (if enabled), C09(real slot). No C0E window clicks are ever sent, because the module only ever touches hotbar slots already selected by C09. The C08 payload is the itemstack constructor (use on air), and the C07s use BlockPos.ORIGIN with EnumFacing.DOWN, the canonical use/release positions. The release arriving one tick after the use is the module's defining timing property, and the drop makes the bowl disappear from the held slot in the same tick as the release.

What this file does

The module is one pre-motion handler with two phases. The switchBack branch (lines 40-47) fires first when the flag from the previous tick is set: it sends the C07 release, optionally the C07 drop, the C09 slot restore, and clears the flag, then returns so the eat tick cannot run in the same event. The gate (lines 49-64) only runs when the flag is clear: ticksExisted > 10 and health below the threshold, then findSoup() - 36 into the hotbar index, the C09 + C08 pair, and the delay re-roll with RandomUtils.nextInt over floor(min) to ceil(max) followed by timer.reset().\n\nThe -37 sentinel (findSoup returns -1 for no soup, minus 36 stays -37) is how the module distinguishes 'no soup found' from hotbar slot -1, which does not exist. The drop is a second C07 with Action.DROP_ITEM, thrown after RELEASE_USE_ITEM in the same tick, so the empty bowl leaves the hotbar slot while the release is being processed. onDisable clears both switchBack and the sentinel so a mid-cycle disable cannot leave the slot stuck on soup.

How it counteracts this module

NoCheatPlus FastClick counts inventory clicks into an ActionFrequency with five 200ms buckets, comparing the newest bucket against the short-term limit of 4 and the one-second window against the normal limit of 15, with lag division via TickTask. Only real window clicks (C0E) feed the ledger; each click adds a weighted amount via getAmountWithAction.\n\nThis module never sends a C0E packet. Slot selection is done with C09 held-item changes and the use with C08, so FastClick's ledger never increments regardless of eat rate; the counter that exists to stop autosteal-style click spam is structurally blind to a C09/C08/C07 implementation. The check matters here as the reason soup modules either shuffle inventory with window clicks (and get counted) or, like this one, restrict themselves to hotbar traffic (and stay invisible to the window-rate path). The consequence is that NCP's inventory countering for this module falls entirely on Open and the use-item adapters rather than FastClick.
