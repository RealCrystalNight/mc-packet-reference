Overview

Memeware 7.3's Anti Bot is a two-list filter that runs from a single UpdateEvent consumer and feeds a shared combat blacklist. Every tick it walks the loaded entity list, adds any EntityPlayer whose health attribute holds a real number to a private bad list and to the public static CombatUtil.botList, and removes players from botList as soon as their client-side onGround flag is true. The module registers ViperMC, Hypixel and Mineplex server presets, but the handler never reads the selected mode; the same health-and-ground rule runs for all three. Because CombatUtil.getTarget, getTargets and canBlock all skip entities in botList, the filter directly shapes what the Kill Aura module can attack and block against.

Architecture

The module is one Consumer<UpdateEvent> field named fard, annotated with LWJEB's @Handler, plus two static lists. bad is private to the module and accumulates every player that ever passes the health test; CombatUtil.botList is the shared public static list that the combat utilities consult, and every add to bad is mirrored into it. onEnable and onDisable both clear the two lists, so toggling the module rebuilds the filter from scratch. The addModes call registers the ViperMC, Hypixel and Mineplex presets, but the handler body has no switch on the mode setting; the preset selection is cosmetic and every mode executes the identical health-and-ground logic.

Bot detection heuristics

The filter's first rule is inverted relative to most bot filters: a player enters bad and botList when Float.isNaN(entityPlayer.getHealth()) is false, meaning the health attribute holds a real number. Entities whose data watcher never supplied health, which is the classic signature of server-side bots, read as Float.NaN and are never flagged. The second rule unflags: whenever entityPlayer.onGround is true and the player is in botList, the module removes it, so a grounded player is presumed real. The combined effect is that the blacklist holds players that are airborne at the moment of the tick, and the killaura stops attacking anything that is not on the ground, including falling players, flying players and hovering NPCs. The onGround value is the client's own simulated flag, so the filter trusts the target's reported ground state rather than checking the world.

Interaction with killaura targeting

CombatUtil.getTarget iterates mc.theWorld.loadedEntityList and returns the first EntityLivingBase within range that is alive, not invisible (unless allowed), not the local player and not contained in botList. getTargets applies the same skip for the multi-target path, and canBlock returns false when every candidate is in botList, which also disables the blockhit re-block. Because targeting is first-match-in-list with no sorting, filtering only removes candidates; it never reorders what remains. The UpdateEvent handler runs every tick, so a bot that lands is un-flagged and becomes attackable again, and a player that jumps becomes blacklisted for the duration of the jump.

CombatUtil owns the public static botList that AntiBot fills, and every targeting helper consults it. getTarget, getTargets and canBlock each short-circuit on botList.contains(o), so a flagged entity is invisible to the Single and Multi aura paths and never counts as a block target. How it counteracts this module

FightHitbox re-validates every player-versus-player attack on the server instead of trusting the client hit-scan. When an InteractEntityEvent arrives, Hawk stores it and waits for the next move packet, because in 1.8 the client computes the attack direction from the yaw and pitch of the frame, and the movement packet that carries them arrives after the use-entity packet. On the move it builds a ray from the attacker's eye position (y plus 1.62, minus 0.08 while sneaking) along that direction, expands the victim's hitbox by a 0.005 epsilon, and requires the ray to intersect the box within MAX_REACH, 3.1 blocks in survival and 5.0 in creative.

The victim position is rewound through the lag compensator to the ping-appropriate history location, so the box is checked where the attacker actually saw it. When the ray misses the box entirely and CHECK_BOX_INTERSECTION is on, Hawk punishes with 'Did not hit hitbox.'; when it intersects but the distance exceeds the reach, the violation reports the measured reach in meters. The optional CHECK_OCCLUSION path also walks a block iterator from the eye along the ray and flags any hit whose intersection with a solid block is closer than the victim, which catches through-wall attacks.

The Memeware killaura attacks without any line-of-sight test and aims from a fixed eye height of posY plus 1.2 at ent.posY plus half the eye height, with the yaw and pitch snapped into the UpdateEvent on the same tick the C02 is sent. The server-visible direction therefore points at the target's upper body, and the geometry must intersect the lag-compensated box within 3.1 blocks. An attack from the module's default 6-block range at a target standing further than 3.1 from the eye fails the distance test, and an attack aimed through a wall trips the occlusion path when enabled. The client-side bot filter does not matter to this check: it validates every C02 geometrically regardless of which entities the client decided to attack.

Arc's KillAura check runs five sub-checks over each attack. Direction computes the angle between the player's look vector and the vector to the attacked entity and flags when it exceeds max-direction-angle. The Memeware aura sends swingItem() before every C02, so NoSwing passes as long as the swing packet is not dropped. An attack at 4 or more blocks from the target is a direct violation, and the snap-aimed pitch makes the Direction angle small and constant, which is the one part of the check the module satisfies. How it counteracts this module

Grim's Reach check validates each attack against a server-reconstructed version of the target's hitbox. checkReach builds the possible look directions from the current yaw and pitch plus the last tick's yaw and pitch, extends the eye position along each direction to maxReach plus 3 blocks, and requires ReachUtils.calculateIntercept to find an intersection with the target box; the minimum distance to the box comes from ReachUtils.getMinReachToBox and the violation threshold is 0.0005. When the attack cannot have intersected the box at all, the check flags with the configured actions, and the Hitboxes check is invoked by Reach to describe the failure.

The reconstruction matters because Grim compensates for client-server position lag: PacketEntityReplication tracks spawned entities, their relative moves and teleports, and ReachInterpolationData keeps the possible box positions across ticks, so the hit is judged against every position the entity could have occupied. Movement allowance is added only when the last movement packet included a position, and the block-impossible-hits setting cancels attacks that no possible look direction could have landed.

The Memeware aura attacks through walls with no line-of-sight check and at ranges up to 8 blocks. For any such hit the reconstructed intercept either misses the box entirely or sits beyond the reach limit, and because the module aims at a fixed eye height while Grim measures from the true eye position, head-level aim against a moving target frequently fails the intersection test. The bot list on the client has no counterpart here: Grim validates whatever C02 arrives against its own entity replication, so filtering targets locally does not reduce the per-hit validation.
