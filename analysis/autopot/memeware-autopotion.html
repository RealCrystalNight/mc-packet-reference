Analysis

Overview

Memeware's Auto Potion is a health-gated splash-heal thrower driven by a two-phase UpdateEvent handler and a static doThrow flag. Below 9.0 health the pre phase scans the hotbar for a splash potion whose effects contain Instant Health; if the hotbar is empty it window-clicks one from the main inventory (C0E, mode 2 hotbar swap), then arms doThrow and forces the local pitch to 90 so the throw appears straight up. The post phase of the next event fires the actual throw as a three-packet burst in one tick: C09 to the pot slot, C08 with the held stack (the single-stack constructor, so block position ORIGIN and face 255 - the use-item form), then C09 back to the previous slot. A 500ms Timer with reset() on arming sets the cooldown. The module has no open-container guard on its window click and never sends a look packet with the pitch change, so the splash is thrown at the server's last-synced rotation while the client renders a straight-up lob - the visual and the wire disagree.

Two-phase throw cycle

The handler splits work across update phases. The pre phase gates on health < 9.0 and non-creative, then (if the 500ms timer has elapsed) locates a potion: hotbar scan 0-8 for an ItemPotion that isSplash() and whose effects list contains Potion.heal, falling back to a container scan 9-35 whose first hit is swapped into hotbar slot 1 with mc.playerController.windowClick(windowId, j, 1, 2) - mode 2 SWAP, button 1. It then re-scans the hotbar, remembers the first pot slot in the instance field slot, calls timer.reset() and sets the static doThrow, and finally event.setPitch(90.0f) - a local-only rotation change. The post phase consumes the flag: if doThrow, it queues C09(slot), C08(getStackInSlot(slot)) and C09(inventory.currentItem) back-to-back through addToSendQueue and clears doThrow. The static flag doubles as a public isPotting() query other modules can poll. Because the throw packets fire on the post of the same tick that armed them, the C09-C08-C09 triple is one 50ms window of traffic.

C08 use-item form and rotation split

The C08 is built with the one-argument constructor, which serializes BlockPos.ORIGIN (0, 0, 0) with face index 255 (-1) and the current stack. That face value is the protocol's 'use item in hand' marker: the server's processPlayerBlockPlacement routes it to ItemPotion.onItemRightClick, which spawns the splash entity for a splash potion. The packet carries the potion stack itself, so the server validates the throw against the item the client claims to hold - and because the module switched the held slot with C09 immediately before, the carried stack matches the announced slot. The pitch is applied only to the local player (event.setPitch) with no C05/C06 look packet, so the server processes the throw with the last rotation it received; the client meanwhile renders the potion lobbing straight up from the forced 90 pitch. That split - throw direction diverging from the synced rotation - is a local/remote desync a rotation-checking anticheat can measure, though the module never claims the 90-degree pitch on the wire.

Cooldown and window-click edge cases

The Timer here behaves as a real period, unlike Auto Armor's: arming calls timer.reset(), so delay(500f) gates the next search to 500ms after the previous arm. Two edge cases follow from the ordering: the window-click refill path uses mc.thePlayer.openContainer.windowId with no windowId != 0 guard, so with a chest open the swap click targets the chest window's slot j instead of the inventory (the container scan 9-35 also walks chest slots in that state), and the throw still fires regardless. And isValidPotion is called twice per candidate with an overload that re-casts the stack's item, a redundancy that costs nothing but signals the copy-paste origin. The health gate is a hard 9.0 (4.5 hearts) with no setting; the module only ever throws heal splash, so it is a pure panic-heal bot rather than a buff module.

How it counteracts this module

Hawk's ItemSwitchSpeed is the canonical check for the auto-pot slot dance - the source comment literally notes it 'might rename this to AutoUse'. The check maintains a per-player lastSwitchTick map and a usedSomething set: an InteractItemEvent or InteractWorldEvent adds the player to usedSomething, and the next ItemSwitchEvent then compares the tick delta against MIN_SWITCH_TICKS (default 1); a switch within that window of a use is a punish (1 VL, cancelless). Memeware's module produces the worst-case input: C09(pot slot), C08 (the use), C09(back) are all queued in the same post-update tick, so the switch-back ItemSwitchEvent arrives in the same or the immediately following tick as the InteractItemEvent generated by the C08 - well inside MIN_SWITCH_TICKS. Every throw is therefore a guaranteed violation, and because the module re-arms on a 500ms cooldown whenever health stays under 9, sustained low-health combat accumulates VL without human-like spacing. There is no randomization or delay setting to widen the gap; the only escape is throwing less often than the check's window, which defeats the module's purpose.

How it counteracts this module

NCP's ProtocolLib adapter is the layer that classifies C08 traffic into block places and item uses, and it is the C09-sensitive half of NCP's item-use state machine. handleBlockPlacePacket (line 382) reads the pre-1.9 C08 face index: a face <= 5 means a genuine block place and clears data.mightUseItem, while any other face - including the 255 the module's one-argument constructor serializes - sets mightUseItem = true, marking the player as possibly using an item. The subsequent PlayerInteractEvent (RIGHT_CLICK_AIR for the potion throw) then drives onItemInteract, which for splash potions hits the pre-1.9 durability guard (line 277, durability > 16384) and skips setItemInUse entirely - an accurate gap: NCP deliberately does not track splash throws as item-use. What the adapter does catch is the slot churn: the module's C09 to the pot slot and C09 back fire onChangeSlot (line 366), and any real slot change while an item use is in flight calls pData.requestItemUseResync(), forcibly releasing the server-side item-use state. The same-tick C09-C08-C09 cycle is exactly the sequence the adapter's state machine exists to reconcile, and the resync it triggers is the server reasserting its inventory/use state against the client's rapid manipulation.
