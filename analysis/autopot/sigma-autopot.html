Overview

Sigma 4.11's AutoPot is a three-effect potion bot - heal, regen and speed - with a spoof-slot design: getBestSpoofSlot picks an empty hotbar slot (or the first potion slot) as the routing target, and getBestPot swaps the best available splash of the wanted effect into that slot with a mode-2 window click before the throw. The throw itself is a four-packet burst in one pre-update tick: C09 to the spoof slot, C05 look at the throw rotation (pitch 90, or a PREDICT-computed aim at the player's position extrapolated 26 ticks ahead and 3.6 blocks down), C08 with the current stack, and C09 back to the old slot. A public static potting flag and a 200ms timer let other modules react, while the actual re-arms are gated at 900ms for heal/regen and 1000ms for speed, each requiring the effect to be inactive and (for heal) health below twice the HEALTH setting (default 6). The window click is the differentiator: the swap emits C0E traffic on the player container, optionally with the inventory screen open (GuiInventory is explicitly allowed), which the hotbar-only throwers avoid.

Spoof-slot routing and swap

getBestSpoofSlot returns the first hotbar slot whose container slot 36-44 is empty, or the first slot already holding a potion - the throw target that minimises visible disruption. getBestPot scans container slots 9-44 for a splash potion of the wanted effect, ranks candidates with isBestPot (rejecting any potion of the same effect with a higher amplifier, or an equal amplifier with a longer duration), and if the winner is not already in the spoof slot performs swap(i, hotbarSlot): windowClick(windowId, i, hotbarSlot, 2) - mode 2 SWAP, which exchanges the inventory slot with the named hotbar slot and emits a C0E. The scan permits mc.currentScreen == null or a GuiInventory, so the swap can legitimately occur while the player is looking at the inventory screen, and the windowId comes from inventoryContainer, keeping the click on the player window. After the swap the module sends the throw burst and resets the timer; the 200ms timer clears the public potting flag so a sprint or scaffold module can resume quickly.

Throw burst and rotation modes

The burst is queued in one pre-update tick: C09(hotbarSlot), C05PacketPlayerLook(rotations[0], rotations[1], onGround), C08(inventory.getCurrentItem()), C09(oldSlot). The C05 is what distinguishes Sigma from the others - the throw pitch is claimed on the wire before the use, so the server throws the splash at the claimed rotation. getRotations returns either {currentYaw, 90} or, with PREDICT on, the yaw to a point at posX + motionX * 26, boundingBox.minY - 3.6, posZ + motionZ * 26 - a lead-aim 26 ticks ahead and 3.6 blocks below the feet, so the potion lands under the predicted position. The C08 is the face-255 use form carrying the potion stack from the current slot, which the C09 just switched to. The three settings (SPEED, REGEN, HEALTH) build a pots[] priority list [heal, regen, speed]; heal and regen share the 900ms gate and the health check (health < HEALTH * 2), speed uses the 1000ms gate and no health requirement, and both require the effect to be inactive.

Effect ranking and gate cadence

isBestPot normalizes the comparison surface: it rejects potions with null or multi-effect lists, then walks the entire container comparing every splash of the same effect ID by amplifier first and duration second - a genuine best-of-inventory selection, unlike the Memeware/Nekoware ranker bug in the sibling analyses. The gates are timer-based: heal/regen re-arm at 900ms, speed at 1000ms, each only when the effect is not active, so buff refresh is demand-driven rather than periodic. The effect list is fixed by the settings - heal (ID 6) is always armed, regen (10) and speed (1) are toggles - and the module never drinks, only throws splash. The combination of a wire-claimed rotation and a window-click swap makes Sigma's AutoPot the most packet-visible of the three autopot modules: C0E, C09, C05 and C08 per cycle.

How it counteracts this module

NCP's FastConsume times the gap between starting and finishing a consumable. The interaction side is fed by InventoryListener.onPlayerInteract (consumables stamp fastConsumeInteract and fastConsumeFood) and the completion side by PlayerItemConsumeEvent; the check compares the elapsed time against fastConsumeDuration with lag division and a VL that decays by 0.6 on clean completions. The C09 half is where the ledger does engage: InventoryListener.onItemHeldChange (MONITOR priority) resets fastConsumeInteract to now and clears fastConsumeFood on every slot change, and the module's C09-to-pot and C09-back sandwich the throw, so each ceremony re-stamps the interaction baseline twice. The result is that NCP's consume machinery churns on every throw without ever flagging - the honest reading is that this check is structured for drinking/eating clients and the module's splash-only design steps around its only timing hook.
