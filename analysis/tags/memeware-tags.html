Analysis

Overview

A custom-nametag renderer: it cancels the vanilla nameplate render event and, each render frame, draws its own TTF tag above every non-invisible player at the interpolated position. The positions come entirely from the entity stream the server already broadcast — S0CPacketSpawnPlayer (S0C) and S0FPacketSpawnMob (S0F) plus the entity-move packets — so the module emits no serverbound traffic.

Architecture

Two lwjeb consumers. The RenderPlayerNameEvent consumer cancels the vanilla label so only the custom tag draws; the Render3DEvent consumer walks mc.theWorld.playerEntities, skips invisible players, and for each survivor computes the interpolated position (lastTickPos blended toward posX/posY/posZ by the render tick factor, minus the render manager's offsets) and hands it to TagUtils.renderNametag. The module overrides onEnable/onDisable as no-ops, so all behavior is the two consumers.

What the tag draws

TagUtils.renderNametag builds a nameplate from the player's formatted display name with [F]/[C] badges for flying and creative players, a color-coded health percentage (green >75%, yellow >50%, orange >25%, red below), a distance-scaled background rectangle that stays a constant 8+ pixels even at range, and the player's equipped item plus armor icons. Sneaking shifts the label, and the whole thing is billboarded to the camera. It is a pure render-path replacement: every input is data the vanilla client already holds.

Detection surface

The nametag consumes spawn packets (S0C for players, S0F for mobs) and the entity-move stream that everyone receives. Nothing the module does changes what the server sees, so no anticheat check can fire on the rendering itself. The checks that matter are the ones policing the same entity-state stream server-side: entity replication ledgers (Grim), spawn/bookkeeping utilities (NCP), and interaction ray validation (Hawk) — which together mean knowing where players are (what Tags draws) confers no combat advantage the server will accept.

What this file does

The renderer behind the module. renderNametag guards against the local player and dead entities, decorates the display name ([F] flight, [C] creative, plain at 64+ blocks), appends the health percentage with its color, then sets up a billboarded GL matrix (camera rotation from RenderManager, distance-scaled font size via the /5.0f clamp), draws a translucent background rectangle, renders the name string, and finally draws the equipped item plus the four armor slots as icons in a row. It reads only the player's entity state and the render manager's camera — no world queries, no packets — which is why the whole feature is confined to the client's render thread.

How it counteracts this module

Grim's server-side tracker for every entity packet: it consumes spawn, teleport, relative-move, rotation, metadata, effect, and equipment packets and maintains a PacketEntity model (positions, poses, attributes) that the reach and hitbox checks query when validating interactions. The spawn packets that seed a player's entity entry server-side are the same S0C/S0F packets whose data Tags reads client-side to draw its labels. Honest note: Tags is a pure consumer of that replicated state — it never sends anything, so its drawing cannot diverge from Grim's model. The check is the closest real handler of the exact packet stream the module reads, and it demonstrates why entity ESP is harmless to Grim: the AC knows precisely where every entity is, from the same broadcast.

How it counteracts this module

NCP's movement utilities own the server-side bookkeeping of spawn and respawn: world-spawn locations are exempted from certain position validations, and join/respawn positions feed the setback anchor logic that MovingListener consults to reset tracking after a spawn teleport. Honest note: this is the server-side counterpart of the spawn events that seed the client's entity list — the same event stream (S0C spawn, S08 teleport) whose results Tags interpolates into nametag positions. The connection is infrastructural: NCP canonicalizes where players are when they spawn so all downstream checks share one truth, while the module merely draws from the client's copy of that truth.

How it counteracts this module

Hawk's interaction check replays the player's look ray against the victim entity's bounding box whenever the player attacks or interacts, with ping-based lag compensation and a configurable ping limit, and flags interactions whose direction does not intersect the victim ('failed entity interact direction'). This is the direct answer to the combat use-case of entity ESP: knowing where players are — which is precisely what Tags renders — does not help land hits, because the server validates that the client's actual look ray geometrically hit the entity's box at the lag-compensated position. Honest note: the module is still invisible to the check (it sends no interaction packets), but the check is the real enforcement that makes the module's information useless for combat.
