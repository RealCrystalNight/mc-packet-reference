Overview

Memeware's InvMove keeps the movement keys live while a GUI screen is open. On every UpdateEvent, and only when the current screen is not GuiChat, the module writes the raw keyboard state straight into the pressed flags of the forward, right, left, back and jump keybindings. MovementInputFromOptions reads those flags, so the player entity keeps producing forward, strafe and jump input while an inventory or other container screen has focus, and the C03 position stream keeps advancing under an open window.

Input-path bypass

The module never touches packet code. It writes KeyBinding.pressed from Keyboard.isKeyDown(keyCode) for the five movement bindings, bypassing the GUI input path entirely. The GuiChat exclusion means typing in chat does not walk the player, and the handler runs on the pre update event, so the re-asserted flags are in place before MovementInputFromOptions.updatePlayerMoveState() reads them the same tick. The player controller then behaves as if no screen were open.

Wire fingerprint

EntityPlayerSP.func_175161_p fires the pre UpdateEvent and sends one C03 variant per tick based on position and look deltas. With the module, position deltas stay nonzero while the inventory is open, so the server receives position-changing C06 packets (and the sprint-state C0B changes that accompany them) for a player whose server-side container is still open. Vanilla clients freeze in place under a screen, which is exactly the gap the module exploits and the fingerprint the inventory-move checks key on.

Server-side view

The server tracks the open window from the player's window interactions, so a position change with a live container is a contradiction it can validate. CheaterDeleter flags position-changing moves while a screen handler is open, Photon flags any movement past the breaking-time leniency and any jump, Negativity scores distance and sprint and sneak deltas from Bukkit events, and Hawk flags rotation, sprint or sneak while an inventory is open. All four are C03-corpus checks.

What this file does

The module is self-contained: one handler consumer, one GuiChat guard, and a loop over the five movement keybindings. For each binding it assigns keyBinding.pressed = Keyboard.isKeyDown(keyBinding.getKeyCode()), which is exactly the state the vanilla input classes read (MovementInputFromOptions calls getIsKeyPressed()). Because the write happens on the pre update event, the forced state survives until the next event, and because the raw keyboard poll bypasses the screen, no GUI focus check can clear it.

The jump binding is included, so the module also permits jumping while an inventory is open, which Photon's inventory-move check treats as a separate and heavier violation. The GuiChat guard is the only behavioral carve-out, and it exists so chat text entry does not drive the player.

How it counteracts this module

CheaterDeleter's check runs on every serverbound move through PlayerMovementListener.onMovement and keys on the exact module signature: packet.isChangePosition() while player.getCurrentScreenHandler() != null (lines 41-48). After a 500ms grace from the moment the screen opened (lines 58-59), invalidateMove flags when a horizontal delta grows while the server-side velocity on that axis is zero (lines 62-77), i.e. an accelerating walk with no applied velocity, which is precisely what forced keybind input produces. The flag is MINOR severity with a 100ms cooldown, and the data resets on window close and on damage (onPlayerDamage extends the grace by 1000ms, lines 99-104).

The module's sustained WASD movement past the grace period drives deltas that grow against zero server velocity, so the check flags on steady use. The bypass surface is real: movement that rides server-applied velocity (knockback, a moving platform) or movement confined to the first 500ms after opening does not trip it, and the check skips players near non-solid collision and in spectator. A careful module user who drifts instead of accelerates can stay under the delta-growth heuristic.
