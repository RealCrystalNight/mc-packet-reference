Analysis

Overview

A see-through-walls renderer: every render frame it draws translucent boxes over chests, ender chests, dispensers, and droppers (walking the client's loadedTileEntityList) plus breakable cake blocks found by a 5-block-radius block scan. All positions come from world data the server already sent via chunk packets such as S21PacketChunkData; the module only changes what is drawn, so it emits no packets and cannot be detected by packet analysis.

Architecture

One Render3DEvent consumer drives everything. Five boolean options (Chests, Ender Chests, Dispensers, Droppers, Breakable Cakes) gate the draws. The cake scan is a triple loop over a 5-block cube around the player's integer position that compares getBlockState(blockPos).getBlock() against Blocks.cake and boxes each hit; the tile-entity pass iterates mc.theWorld.loadedTileEntityList with an instanceof dispatch (TileEntityChest, TileEntityDropper, TileEntityDispenser, TileEntityEnderChest) and skips whichever type its toggle disables, drawing every remaining entity with RenderUtils.drawEsp. The boxes are the same semi-transparent black (Color(0,0,0,21)) in both paths.

Data source and detection surface

The chests, dispensers, and droppers are tile entities: their block positions are delivered to every client inside chunk data (S21PacketChunkData tile-entity section) and held in the client's loadedTileEntityList from the moment the chunk arrives. The cake scan reads the same chunk block array. So the module reveals nothing the client was not already told — the server broadcast these positions to everyone; the cheat is only that the ESP makes them visible through walls. A server cannot observe the drawing, so the only real countermeasures in the corpus are the X-ray family, which target the mining behavior that seeing-through-walls enables rather than the rendering itself.

What this file does

The constructor registers five toggles. eventConsumer0 first runs the optional cake scan — a 10x10x10 cube centered on the player, which means roughly 1000 getBlockState lookups per frame, each hitting the client's chunk block-array cache; then the tile-entity loop, which is the cheap path since loadedTileEntityList is already populated by chunk loading. Both render paths funnel into RenderUtils (box for the scanned blocks, drawEsp for the tile entities) with the same translucent black fill. No packet is read or written beyond what the render thread already consumes.
