Overview

Nekoware v1 private's Commands module is a byte-identical fork of the Memeware 7.3 command system: the same LWJEB consumer on the outgoing packet bus cancels every C01PacketChatMessage that starts with the '.' prefix and dispatches the stripped command word to the same eleven-branch switch table. The only differences are branding - clientName is 'Nekoware' instead of 'Memeware', editionName is 'Dev', and the module manager reference is Nekoware.INSTANCE - plus the ChatUtil tag text. The interception model is identical: client commands never reach the server, .say re-emits its payload as a C01 prefixed with U+F705, and the clip commands move the player through the vanilla teleport path.

Fork lineage

The two files are the same source tree: same package layout under me/nekoWare versus me/memewaredevs, same me.hippo.api.lwjeb event @Handler decorator, same Module.Category.MISC constructor call, and a switch table that is character-for-character the Memeware implementation including its quirks. The dead 'say' gate, the ineffective args[2] null guard on .bind, the String.replace-based command stripping, and the static clientName/editionName branding strings all carry over unchanged. Only the manager lookup (Nekoware.INSTANCE.getModuleManager) and the default branding values differ, which makes this a private rebrand of the same chat-command infrastructure rather than an independent implementation.

Dispatch and residue

Dispatch semantics are identical to the parent client: .bind writes LWJGL key binds into modules, .t/.toggle call Module.toggle(), .vclip uses setPositionAndUpdate for an immediate position packet while .hclip uses setPosition and lets the next movement tick pick up the offset, .name copies the player name to the clipboard, and .say joins its arguments and calls sendChatMessage with U+F705 prepended so the re-emitted C01 escapes the dot-prefix filter. The server-visible residue is the same three channels: the private-use-character chat output of .say, the teleport movement of the clip commands, and the user's normal chat, which passes through the interceptor untouched.

What this file does

The module is the eventConsumer0 field: a @Handler Consumer<PacketOutEvent> that filters C01PacketChatMessage, cancels dot-prefixed messages before the wire, and switches on the stripped first token. All eleven branches mutate local state only - module key binds, toggles, the clipboard, the static branding strings, and the instance prefix. The .say branch re-emits its payload through sendChatMessage with U+F705 prepended, which is why the second message is not re-cancelled: it no longer starts with '.'. The 'say' boolean is never assigned so the interception always runs, and the .bind branch's args[2] null check cannot work because split never yields null elements - a short invocation throws AIOOBE after cancellation, failing client-side without affecting the wire. Feedback for every branch goes through ChatUtil.printChat.

How it counteracts this module

NCP's Commands check exists precisely because command streams are a spam vector: ChatListener.onPlayerCommandPreprocess feeds every PlayerCommandPreprocessEvent into it, with the source comment 'We listen to PlayerCommandPreprocess events because commands can be used for spamming too.' Each command adds weight 1.0 to data.commandsWeights (an ActionFrequency, line 66) and to a short-term tick counter that resets when server lag exceeds a factor of 1.3 (lines 67-88); the violation is max(windowScore - cc.commandsLevel, shortTermWeight - cc.commandsShortTermLevel) (line 91), escalating to a captcha or cc.commandsActions (lines 96-104).

The check cannot see this module's own commands, and that is the honest core of the countering story: the fork cancels dot-prefixed chat client-side, so PlayerCommandPreprocessEvent never fires for .bind, .t or .prefix. What the check does bound is the command traffic the fork lets through unchanged - any normal '/' command the same user issues is scored exactly as if the module did not exist, including burst patterns from the same session. For a private client whose selling point is an invisible command language, the residue it does produce is the only thing any server-side check can ever measure.

How it counteracts this module

Text scores every chat message the server receives, which for this fork means every message that survives the dot-prefix filter. The score combines per-word notLetter ratios squared (lines 209-231), uppercase ratio beyond one third (line 150), letter-count and partition ratios for longer messages (lines 157-169), and an 8-second repeat-similarity comparison against the player's own last message via StringUtil.isSimilar(..., 0.8f) (lines 174-179). Two ActionFrequency accumulators - chatFrequency and chatShortTermFrequency - fold the per-message score into windowed totals compared against textFreqNormLevel and textFreqShortTermLevel (lines 257-265), with flat penalties for chatting within 8 seconds of joining and after 8 seconds of not moving (lines 194-202). A violation arms the captcha or executes actions (lines 267-294).

The .say output is the fork's most identifiable residue: a message beginning with U+F705, a private-use code point no legitimate client emits, scores notLetter on its first word, and a repeated .say produces byte-identical text that the repeat-similarity path compares at 0.8 similarity. The user's ordinary chat in between is scored at whatever rate they actually type, so the check does not distinguish the client from a fast human - it only measures what arrives.
