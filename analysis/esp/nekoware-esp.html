Analysis

Overview

Player ESP is a wire-silent render overlay: on every Render3DEvent it walks mc.theWorld.loadedEntityList and draws a fixed translucent black box around every EntityPlayer except the local player. The entities it draws are fed by the server spawn stream (S0C for players, S0F for mobs, both filtered to EntityPlayer), and the drawing itself is pure client-side GL11 work, so the module has no packet fingerprint and no server-side detection surface.

Render pass

The module is a single Consumer<Render3DEvent> field carrying the @Handler marker that the client's PubSub bus subscribes at toggle time. The consumer loops mc.theWorld.loadedEntityList, skips the local player and any entity that is not an EntityPlayer, and calls RenderUtils.drawEsp(o, new Color(0, 0, 0, 21).getRGB()) for the rest. drawEsp renders a 1x2x1 axis-aligned box from (posX - 0.5, posY, posZ - 0.5) to (posX + 0.5, posY + 2.0, posZ + 0.5) using the color's alpha, so the box is a barely visible 8 percent opacity black outline at fixed size, with no color, health, distance or invisibility settings.

Data source

loadedEntityList is populated entirely from the receive path: S0C spawns players into the client world, S0F spawns mobs, and the destroy, teleport and velocity packets move and remove them. The EntityPlayer filter means only S0C-fed players ever render; S0F mob spawns are skipped by the instanceof check even though they populate the same list. The module reads entity positions each frame, so the boxes track interpolation and render through walls; nothing is sent back.

Wire presence

Rendering is client-local state. The module neither sends nor cancels any packet, and it does not mutate the entity list, so the server-side entity ledger is identical to a vanilla client's. There is no packet whose content could betray the overlay. The countering entries below are therefore honest boundaries: the checks that handle the S0C and S0F spawn stream in each anticheat, none of which can observe a render-side read of the same data.

How it counteracts this module

Grim mirrors every spawn into a server-side entity ledger: the S0C and S0F handlers build PacketEntity objects with tracked positions and hitboxes that feed reach, phase and prediction checks, and a spawn also clears the player's accepted-spawn-teleport flag. This is the closest thing to a spawn consumer in the corpus, and it is a one-way mirror: the ESP reads the same spawn data locally for rendering, while the replication ledger records only server-originated state. Nothing the module does alters an entity's tracked position or existence, so the ledger sees a vanilla stream. The entry is the honest statement that entity-replication machinery cannot observe a render-only read.
