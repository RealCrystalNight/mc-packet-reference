Sigma 4.11 AntiVelocity — Full Source Analysis

Sigma 4.11's AntiVelocity is a three-mode anti-knockback module selected by the MODE Options setting (Basic, AACPush, AACFlag) and driven from EventPacket plus EventUpdate. Basic is a packet modifier: it scales the S12 vector in place by the HORIZONTAL and VERTICAL percentage settings (default 0/0) using integer fixed-point arithmetic, cancels the packet outright when both percentages are zero, and additionally cancels S27 explosion knockback while in basic mode. AACPush is a motion rewriter: it lets the S12 through untouched, stores the vector, and for the next 10 ticks while hurtResistantTime is positive rewrites the horizontal motion every tick with MoveUtils.strafe at a decaying boost (0.05 down to 0), hard-cuts to a 0.2 strafe when speed exceeds 0.35, and damps motion when no keys are held. AACFlag is a teleport exploit: it cancels the S12 and pushes a C04PacketPlayerPosition with Double.NaN as Y (onGround true) straight into the send queue, exploiting vanilla's illegal-position check (which bounds only x and z) and the fact that NaN comparisons are always false, so the server resets the player with an S08 teleport to its pre-knockback position; the module absorbs the S08 by preserving the player's yaw and pitch while hurtResistantTime is positive. The module never touches outgoing C03 packets (an early return skips them), only intercepts the self-entity S12, and disables itself implicitly while the Fly module is in BowFly mode. onEnable resets the AACPush tick counter.

Overview

Basic is a packet modifier: it scales the S12 vector in place by the HORIZONTAL and VERTICAL percentage settings (default 0/0) using integer fixed-point arithmetic, cancels the packet outright when both percentages are zero, and additionally cancels S27 explosion knockback while in basic mode. The module never touches outgoing C03 packets (an early return skips them), only intercepts the self-entity S12, and disables itself implicitly while the Fly module is in BowFly mode. onEnable resets the AACPush tick counter.

Architecture

onEvent branches on event type. EventPacket handling starts with an early return for outgoing C03 packets, so the module never interferes with the player's own movement stream - the AACFlag C04 is injected through addToSendQueue directly and is covered by that same return. The S12 branch verifies the entity id against the player and skips interception while Fly is enabled in BowFly mode, then dispatches on the mode string. An S08PacketPlayerPosLook branch preserves yaw and pitch on the teleport when AACFlag is active and the player is in hurt time. EventUpdate runs the AACPush countdown and motion rewriting while hurtResistantTime is positive.

State is minimal: the count tick counter (reset in onEnable), the stored xmot/zmot from the last S12, and the mode string. The S27 explosion branch is mode-gated to basic (case-insensitive), so explosion knockback is only cancelled in that mode.

Basic: scale or cancel

Basic reads the VERTICAL and HORIZONTAL settings and rewrites the S12 with setMotX(horizontal * x / 100), setMotY(vertical * y / 100), setMotZ(horizontal * z / 100) - integer arithmetic on the fixed-point components, so the vector is reduced by the configured percentages. When both percentages are zero the packet is cancelled instead of scaled, which is the full anti-knockback case. The S27 branch cancels explosion knockback outright whenever basic is selected, so a Basic user takes neither entity knockback nor explosion knockback.

The same event handler runs for every mode; the mode string is read once per event and also written into the module suffix via setSuffix.

AACPush and AACFlag: motion rewrite and NaN teleport

AACPush is the only mode that does not cancel the S12: the vector is stored (xmot/zmot as x/1000, z/1000, used only for the speed magnitude check) and the vanilla knockback applies. Then, for up to 10 ticks while hurtResistantTime is positive, EventUpdate computes boost = 0.05 - count/200 and calls MoveUtils.strafe(boost), which rewrites motionX/motionZ from the facing yaw based on the held keys. If the resulting horizontal speed exceeds 0.35 the module zeroes motion and strafes at 0.2, and if no movement keys are held it multiplies motion by (0.8 - boost). The result is a controlled push-out trajectory rather than the vanilla knockback decay.

AACFlag instead cancels the S12 and injects C04PacketPlayerPosition(player posX, Double.NaN, player posZ, onGround true) through addToSendQueue. Vanilla's processPlayer bounds the illegal-position check to x and z at 3.0E7 and every NaN comparison is false, so the NaN Y is neither kicked nor flagged; the corrupted server-side position makes the server teleport the player back with S08 to its pre-knockback coordinates, which cancels the knockback on the server's own initiative. The module's S08 branch preserves yaw and pitch so the reset does not disorient the user. It only fires when the S12 has a horizontal component (x != 0 && z != 0).

What this file does

The module is one file. The EventPacket branch contains the outgoing-C03 early return, the S08 yaw/pitch preservation for AACFlag, the entity-id and Fly/BowFly gates, and the mode dispatch: Basic scales or cancels the S12 via setMotX/Y/Z and cancels S27; AACPush stores the vector and arms the countdown; AACFlag cancels the S12 and injects the NaN-Y C04 through addToSendQueue. Notable details: the S27 cancel is gated on the mode string matching 'basic', the outgoing-C03 early return guarantees the injected C04 is never re-intercepted, and onEnable resets the count so the AACPush burst restarts cleanly on each toggle.

What this file does

MoveUtils.strafe(double speed) is the only external helper the AACPush mode reads. It resolves the pressed movement keys (forward/back/left/right, including diagonals) against the player's current rotationYaw and rewrites motionX and motionZ as sin/cos projections at the given speed, so the AACPush burst moves the player along their facing rather than along the knockback vector. The same class also carries defaultSpeed() and setMotion() used by Sigma's movement modules, but only strafe matters to AntiVelocity.

This is the piece that turns AACPush from 'let the knockback through' into 'replace the knockback trajectory': every hurt tick the module overwrites the horizontal motion the vanilla client derived from the S12 with a fixed-magnitude facing-relative burst, which is what the countering checks below measure as a missing or altered required vector.

How it counteracts this module

Grim's KnockbackHandler is a PacketSendListener on ENTITY_VELOCITY that wraps the packet in a transaction sandwich: sendTransaction() before the velocity and a second transaction through tasksAfterSend after it. The vector is recorded into firstBreadMap keyed by the first transaction id, and tickKnockback promotes it into lastKnockbackKnownTaken once the client echoes a larger transaction id - proof the packet reached the client. From that moment the vector is required movement: the prediction engine must see it in the player's motion. onPredictionComplete compares the prediction offset against offsetToFlag (config Knockback.threshold, default 0.001), accumulates it into a threshold with decay 0.999 up to maxAdvantage 1, and set-backs at offset >= 0.1 (immediate-setback-threshold). A knockback that arrives while Grim itself is sending a setback is recorded with isSetback and treated leniently, because the position reset would mask it anyway.

All three Sigma modes fail the requirement. Basic at 0/0 cancels the S12, but the server already sent it and the sandwich confirmed delivery, so the required vector simply never appears in the predicted motion and the offset is the full knockback. Basic at partial percentages scales the packet client-side, which cannot change the server-side record Grim read, so any nonzero reduction produces an offset above the 0.001 floor. AACPush lets the S12 through but then rewrites motionX/Z with strafe every hurt tick and hard-cuts at 0.35, so the predicted trajectory diverges from the required vector even though the packet was received. AACFlag's cancelled S12 plus NaN-Y C04 leaves the required vector un-taken; the resulting server teleport is a teleport, not knockback consumption (and it is not a Grim setback, so the isSetback leniency does not apply). The only honest bypass surface is transaction eating - suppressing the client's transaction echo so the vector is never promoted out of the uncertain firstBreadMap bucket - which Sigma's modes do not attempt.

How it counteracts this module

Hawk's MoveEvent keeps a pending knockback list per player and matches every move's velocity against it. handlePendingVelocities computes the move delta (to - from), and for each pending kb entry checks the Y component within 0.01 (unless the player collides with a block, jumps, swims or steps), then X and Z inside maxDiscrepancy = weirdConstant * baseMultiplier * sprintMultiplier + 0.003 epsilon, where weirdConstant is 0.098 on ground (0.2518462 while jump-sprinting, 0.0196 swimming), baseMultiplier is 5 * walkSpeed * speed-pot multiplier (or 10 * flySpeed when flying) and sprintMultiplier 1.3 (2 flying). A kb entry older than ping + 200ms with no matching move sets failedKnockback (outside vehicles), and AntiVelocityBasic.check punishes that at VL 5 with 'may be using anti-velocity (basic)'. The class comment says it is tested to detect down to a 10% difference.

Basic at 0/0 cancels the S12, so no move ever matches the pending entry and it expires into a flag. Basic at partial percentages keeps the move inside maxDiscrepancy only while the reduction leaves the scaled remainder inside the window - for the default 10% detection claim, reductions beyond roughly 10% of the vector fall outside and flag. AACFlag produces the same expiry: the NaN C04 and the follow-up S08 teleport are teleport events, not knockback matches, so the entry ages out. AACPush is the subtle case: the S12 is received and the vanilla vertical motion does follow the kb, but every hurt tick strafe() overwrites motionX/motionZ with a facing-relative boost, so the X/Z match test fails and the entry expires - the vertical component alone cannot satisfy the check.

How it counteracts this module

Spartan's VelocityListener is a MONITOR-priority ProtocolLib adapter on ENTITY_VELOCITY. For the self entity it reads the fixed-point x, y, z through BackPlib.getSafeInt divided by 8000.0, builds a CPlayerVelocityEvent carrying the claimed vector, forwards the packet's cancellation state, and dispatches it on the CheckThread to VelocityEvent.event, which stores it as protocol.claimedVelocity, pushes it onto the claimedVeloGravity and claimedVeloSpeed queues (each capped at two entries) and runs Spartan's checks with executeRunners. The flagging lives in the movement checks that consume claimedVelocity - the file is the feed, not the verdict - but the feed is what matters here: it records the vector the server itself sent.

Because the claimed vector is read server-side from the wire, Sigma's client-side manipulation cannot change it. Basic at 0/0 and AACFlag cancel the S12, so the player's movement shows a total deficit against the claimed vector. Basic at partial percentages still shows a proportional deficit, since the queue compares the reported movement against the full server vector. AACPush overshoots in a different way: the module adds horizontal boost on top of the received knockback, so the movement exceeds the claimed horizontal profile while the vertical decay is normal. The two-entry queue cap is the tolerance surface - only the last two claims are compared, so a module that alternates clean movement between hits can stay under the checks' tolerances, but Sigma's per-hit rewriting leaves no clean window.

How it counteracts this module

NCP's movement model queues the vertical velocity the server applied and later consumes it to explain the player's actual movement. checkUnusedVelocity reads the pos and neg UnusedTracker instances of the SimpleAxisVelocity vertical tracker; UnusedTracker.addValue records a violation amount only when the direction has been blocked since the entry was added, i.e. the server pushed velocity in a direction the player never moved, and quickCheckDirection reports the violation count, accumulated amount and update count before resetting the results.

In this build the check is a debug ledger: quickCheckDirection logs through DebugUtil and returns false with a TODO for a real frequency or amount check, so the player cannot fail it yet - the honest framing is that NCP's velocity queue model is what would expose the module once the check is enabled. Basic at 0/0 and AACFlag leave the vertical push un-consumed (the cancelled S12 means the client never moves along it, and the NaN move is not a consumption), so the tracker accumulates; AACPush consumes the vertical component normally but the extra horizontal strafe is outside what the vertical tracker models. As shipped, an AntiVelocity user faces NCP's SurvivalFly envelope, not this check.
