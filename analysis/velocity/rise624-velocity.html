Analysis

Overview

Rise 6.2.4's Velocity is a mode selector: the module class only declares a ModeValue with twenty Mode instances and an onSwing BooleanValue, and every mode is a separate class in the combat.velocity package. Standard scales or cancels S12 and S27 with horizontal and vertical percentages plus an explosion-ignore flag; Grim waits for an S19 hurt status before cancelling the following S12 and sending a C07 digging action; Vulcan cancels the knockback and replaces the transaction stream with forged C0F confirmations while hurtTime is 10; Intave and AAC damp the motion directly without touching packets; and the Legit modes (Legit/Jump Reset and Polar) force a jump on the knockback tick at a configurable chance. The mode set maps to named anticheats (Grim, Vulcan, Intave, AAC, Matrix, Karhu, MMC, UniversoCraft, Redesky, Watchdog) plus generic behaviours (Buffer Abuse, Delay, Ground, Tick, Bounce, Grim Reduce, Watchdog Prediction), with Standard as the default.

Architecture

The parent module is a thin composition root. mode is a ModeValue whose add calls instantiate each mode class with its display name and the parent, and setDefault selects Standard. The onSwing value is read by every mode through getParent().onSwing.getValue() and, when true, gates the packet handler on mc.thePlayer.isSwingInProgress, so the module only acts when the client is actually swinging. Each mode is an EventLink-wired class: the event bus scans declared Listener fields annotated with @EventLink and invokes them at the declared priority, and Standard and Grim register at Priorities.VERY_LOW so other modules see the packet first.

The modes share the client's component system: BadPacketsComponent for stream sanity, TargetComponent for nearby-entity checks, PacketUtil for sending and MoveUtil for motion helpers. The mode classes hold their own values (NumberValue percentages, BooleanValue toggles) so the GUI presents each mode's settings inside the parent module's screen. Enabling a mode registers its listeners; switching modes swaps the whole listener set.

Key techniques

StandardVelocity is the baseline. With horizontal zero it applies the packet's vertical motion to the player and cancels the packet; with nonzero percentages it scales motionX and motionZ by horizontal over 100, motionY by vertical over 100, and replaces the packet; the Explosion Ignore flag cancels S27 outright, otherwise the explosion offsets are scaled the same way. GrimVelocity keys on S19PacketEntityStatus: only an opcode-2 hurt status for the self entity arms realVelocity, and only the next S12 for the self entity is cancelled, after which a C07 digging packet is sent from the player's position on the next PreUpdate, using START_DESTROY_BLOCK while looking at a block and swinging and STOP_DESTROY_BLOCK otherwise.

VulcanVelocity cancels S12 at zero/zero unless the Vulcan Speed mode is active and moving, in which case it amplifies the vector by 1.9 instead; it also intercepts S32 confirmations while hurtTime is 10, cancels them and emits a forged C0F with alternating window ids (1 and -1) and uids (-1 and 1) and a toggled accepted flag, keeping the server's transaction ledger busy with garbage confirmations around the hit. IntaveVelocity and AACVelocity never touch the packet stream: they multiply the live motion by 0.6 on a hit and, for Intave, cancel sprint, reproducing the vanilla hit-slowdown the server expects without any packet at all.

No-packet and jump-reset modes

IntaveVelocity runs on PreUpdate: if an attack landed, no hit-slowdown was applied and the player is sprinting, it multiplies motionX and motionZ by 0.6 and calls setSprinting(false). The HitSlowDownEvent listener sets slowDown so the damping is skipped when the client's own hit-slowdown already ran, and the attack flag is cleared every tick. AACVelocity applies the same 0.6 damping on PreMotion when onGround and hurtTime are both positive and BadPacketsComponent reports a clean stream; its jump field is never set, so the MoveInputEvent listener that consumes it is dead code in this build.

LegitVelocity (aliased Legit/Jump Reset and Polar) arms a jump flag on the S12 when the player is on the ground and the vertical component is positive, with the Legit Timing gate restricting it to the knockback window (ticksSinceVelocity at most 14 or onGroundTicks at most 1 when enabled), then forces the jump in MoveInputEvent with the Chance setting as the probability. This converts the knockback into a jump arc, which prediction-based velocity checks read as taken. The onSwing gate applies to every mode, so all of them can be restricted to swing-active moments.

The module is annotated with aliases and description translation keys (module.combat.velocity.name and module.combat.velocity.description) and category Category.COMBAT, with the developer comments apologizing to Tecnio and Hazsi left in the source. The onSwing value is the module's single shared control: every mode reads it through getParent().onSwing.getValue() to gate its own handler.

What this file does

StandardVelocity is the default and the only mode that scales S27 as well as S12. The receive listener runs at Priorities.VERY_LOW and first checks the onSwing gate and the event's cancelled state. For S12 with the entity id matching the player, a zero horizontal slider applies the packet's vertical motion to the player (motionY equals the fixed-point Y divided by 8000.0) and then cancels the packet, which preserves the vertical launch while removing the horizontal push; nonzero percentages scale motionX and motionZ by horizontal over 100, motionY by vertical over 100, and replace the packet with the scaled copy. The Explosion Ignore toggle cancels S27 outright; without it the explosion offsets are scaled with the same percentages.

The file also carries a PreMotion listener whose body is entirely commented out (a Watchdog-speed interaction with a 0.3 strafe and random-jitter damping), and a Teleport listener with a vacuous if statement comparing the teleport Y against the player position. Those are dead code in this build; the live behavior is the receive listener alone. The horizontal and vertical NumberValues default to 0, which is the full-cancel configuration users start from.

What this file does

GrimVelocity is built around the hurt-status packet rather than the velocity packet itself. The receive listener only arms realVelocity when S19PacketEntityStatus arrives with an entity resolving to the player and opcode 2, the hurt animation; it then cancels the next S12 for the self entity, clears the flag and sets velocity, so only knockback that follows an actual hurt status is removed. On the next PreUpdate the mode sends a C07PacketPlayerDigging from the player's own position, choosing START_DESTROY_BLOCK when the mouse is over a block and the player is swinging, and STOP_DESTROY_BLOCK otherwise, with EnumFacing.UP.

The digging action is the mode's cover traffic: it replaces the cancelled knockback with a block-interaction packet timed to the hurt, so the server sees activity around the hit even though the velocity never arrived. The S19 gate is what makes the mode selective, it only cancels knockback that follows a genuine hurt status, so non-hurt velocity (explosion knockback, for example) passes through untouched. The listener runs at Priorities.VERY_LOW so other modules can observe the S19 and S12 first.

What this file does

VulcanVelocity combines S12 handling with transaction forgery. With both sliders at zero it cancels the S12 unless the Vulcan Speed mode is active and the player is moving, in which case it amplifies the vector instead (motionX and motionZ by 1.9, motionY unchanged); nonzero percentages pass the packet through with a 1.0 multiplier. S27 explosion knockback is cancelled at zero/zero and scaled with the percentages otherwise.

The distinctive part is the S32 branch: while hurtTime is exactly 10, every incoming S32PacketConfirmTransaction is cancelled and a forged C0FPacketConfirmTransaction is sent with alternating window ids (1 then -1) and uids (-1 then 1) and a toggled accepted flag. The server receives confirmations that never match its own transaction records, which desyncs the transaction ledger around the hit and masks the missing knockback confirmation. The transaction flag alternates every call, so the forged stream never repeats an identical pair.

The mode also depends on the Vulcan Speed mode's configuration at runtime: the amplification path reads getModule(Speed.class).mode.getValue().getName() and compares it to the string 'Vulcan', an object-identity comparison against a string literal that never matches, so the amplification branch is effectively unreachable and the S12 is always cancelled at zero/zero in practice.

How it counteracts this module

Grim's KnockbackHandler sandwiches the ENTITY_VELOCITY packet between two server transactions and treats the echo of the second as proof the knockback arrived. tickKnockback promotes the velocity from firstBreadMap into lastKnockbackKnownTaken on that transaction, and from then on the prediction engine requires the vector in the player's motion. onPredictionComplete flags when the prediction offset exceeds offsetToFlag (default 0.001) and sets the player back once the offset reaches 0.1 or the accumulated threshold (decay 0.999, ceiling 4) hits maxAdvantage 1.

Rise 6.2.4's Standard mode at zero/zero is a direct hit: the vector is required and absent, so the offset is the full knockback. GrimVelocity's S19 gate and C07 digging do not help, because Grim's requirement is driven by its own transaction sandwich, not by the client's hurt status or digging actions; the cancelled S12 still leaves the required vector missing. The amplification branch in VulcanVelocity (1.9 multiplier) would make the offset worse, not better, and the forged C0F stream does not satisfy Grim's sandwich, which validates its own negative transaction ids.

The bypass surface is the same as for every Grim-facing velocity module: eat the second transaction receipt and its echo so the velocity never leaves the uncertain firstBreadMap bucket and is never required. The forged confirmations VulcanVelocity emits actually work against this, because Grim tracks its own ids and a confirmation that matches nothing is a stream anomaly. On the server side Grim also applies a client-version precision conversion to the vector before it is required, which absorbs small fixed-point rounding but not a cancelled or scaled knockback.

How it counteracts this module

Hawk's AntiVelocityJump targets the sprint-jump-on-knockback exploit: taking knockback while doing a sprint jump in the same tick, which resets the knockback's vertical component to a jump arc. The check samples the moves that follow accepted knockback: when the player is on the ground, sprinting, has been grounded for more than one tick, is not colliding with a block above, and the move is a jump, the jump count increments; every accepted-knockback move increments the total. Once the sample reaches the samples setting (default 10), a jump ratio above ratioThreshold (default 0.85) triggers the 'may be using anti-velocity (jump)' violation at 1 VL, and both counters reset.

Rise 6.2.4's Legit modes are the direct target: LegitVelocity (Legit/Jump Reset and Polar) arms a jump on the S12 and forces it through MoveInputEvent with the Chance setting as the probability. With Chance at 100 the player jumps on essentially every knockback, so the ratio of jump moves to accepted-knockback moves approaches 1.0, well above 0.85, and the check flags after ten samples. Lower Chance values dilute the ratio; at 50 the ratio sits around 0.5 and passes, which is the honest bypass: keep the jump probability below the threshold and the check rewards.

The check only samples while the player is on the ground, sprinting and not colliding above, so jumps taken from air or without sprint never enter the sample, and landingTickMap resets the ground timer whenever the player leaves the ground. Among the other modes, IntaveVelocity's sprint cancellation actually helps here, because the check requires sprinting to sample at all, so a player whose sprint was cancelled is never measured. The 0.85 threshold with 10 samples means occasional legit sprint-jumps pass; only the sustained pattern flags.

In this build the check is a debug ledger that logs through DebugUtil and returns false with a TODO for a real frequency or amount check, so it cannot flag yet. The mechanism it would enforce is the queue model: getOrUseVerticalVelocity consumes queued velocity to explain a vertical move, and a cancelled knockback leaves the velocity unused, which is exactly the violation the tracker accumulates. The honest status is that NCP's velocity enforcement is unfinished here: the tracker is real and fed on every move, but the verdict path is a TODO, so today the effective NCP counter is the SurvivalFly envelope, not this check.

How it counteracts this module

Spartan's VelocityListener claims every ENTITY_VELOCITY for the self entity: it reads the three fixed-point components divided by 8000.0 through BackPlib.getSafeInt, builds a CPlayerVelocityEvent, forwards the packet's cancellation state, and dispatches it on the CheckThread through VelocityEvent.event. VelocityEvent stores the claim in claimedVelocity, pushes it onto the claimedVeloGravity and claimedVeloSpeed queues (each capped at two entries) and calls executeRunners, which feeds Spartan's movement checks.

The movement checks compare the reported movement against the claimed vector, with gravity applied on the gravity queue, so a client that cancels the S12 receive-side is still measured against the vector the server sent. The listener records the original packet contents, so client-side scaling (Standard percentages) does not change what Spartan expects; a 50% vertical reduction shows up as a movement deficit against the full claim. GrimVelocity's S12 cancel and VulcanVelocity's cancel produce the same deficit.

The bypass surface is the queue shape and the ground profile: the last two claims only, and no-packet modes that preserve the vertical movement (IntaveVelocity and AACVelocity damping only the horizontal plane) present movement close to the claimed gravity profile, which keeps them under the checks' tolerances. The bukkit-side twin of this listener, VelocityEvent, claims PlayerVelocityEvent the same way, so the two feeds are kept consistent through the packetsEnabled flag in PlayerProtocol.
