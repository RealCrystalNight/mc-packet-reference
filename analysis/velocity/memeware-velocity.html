Overview

Memeware 7.3's Velocity is a bare receive-side cancel module with no settings, no modes and no scaling. A single @Handler Consumer<PacketInEvent> field subscribes to the client's LWJEB event bus; on the incoming path the patched NetworkManager.channelRead0 fires PacketInEvent before processPacket and drops the packet if any handler cancelled the event. The handler cancels S27PacketExplosion unconditionally - before any entity check, so every explosion knockback is eaten - and cancels S12PacketEntityVelocity only when the entity id matches the player, which is a full cancel: the vanilla handler never sees the knockback vector. onEnable and onDisable are empty.

Because there is no configuration, the module's behavior is constant: a user who enables it takes zero knockback from hits and explosions until they toggle it off.

Architecture

The module is a single event subscription. The update field is declared as Consumer<PacketInEvent> with the @Handler marker from me.hippo.api.lwjeb, which registers it on the event bus when the module is enabled. The interception point is the client's patched NetworkManager: channelRead0 constructs a PacketInEvent wrapping the incoming packet, fires it on the bus, and returns without calling processPacket when the event's cancelled flag is set. The Event base class (me.memewaredevs.client.event.Event) carries that flag with cancel()/isCancelled() - the handler's e.cancel() is what the network layer honors.

State is nonexistent: no counters, no stored vectors, no mode string. The only logic is the packet-type checks and the entity-id comparison (func_149412_c() against mc.thePlayer.getEntityId()).

Cancellation surface

The S27 branch runs first and cancels every explosion packet with no entity check - explosions have no entity id, so the module eats all explosion knockback. The S12 branch then cancels only self-entity velocity. Both are full cancels: the packet is dropped before the vanilla handler, so the client never applies any part of the vector, and there is no percentage path to reduce rather than remove.

This differs from the other two velocity modules in the same lineage: Sigma's AntiVelocity only cancels S27 in Basic mode and can scale the S12, and Nekoware's copy gates the entire handler behind a mode selection. Memeware's version has neither gate - enabling the module is the whole configuration.

What this file does

The client patches the vanilla receive path to host the event bus. channelRead0 constructs a PacketInEvent from the incoming packet, fires it through EventAPI.fire, and when the event's cancelled flag is set, returns before processPacket is ever called - so a cancelled S12 or S27 never reaches NetHandlerPlayClient and the vanilla velocity application never runs. The same hook also fires PostPacketInEvent after processing for post-handlers.

This file is what makes the module's cancel effective: without the patch, e.cancel() would only set a flag nobody reads. It is also the reason the module is invisible to the server in one sense (the server already sent the packet and records the knockback server-side) and fully visible to prediction-based checks (the client's motion simply never contains the vector the server sent).

How it counteracts this module

Grim's KnockbackHandler sandwiches every ENTITY_VELOCITY between two server transactions: sendTransaction() before the velocity and a second transaction via tasksAfterSend after it. The vector is recorded into firstBreadMap keyed by the first transaction id and promoted into lastKnockbackKnownTaken when a larger transaction echo proves the client received it - from then on the vector is required movement. onPredictionComplete measures the prediction offset against offsetToFlag (default 0.001), accumulates it with decay 0.999 into a threshold capped at maxAdvantage 1, and set-backs the player when the offset reaches 0.1 (immediate-setback-threshold).

Memeware's full cancel is the plainest possible failure: the server sent the S12, the sandwich confirmed delivery, and the client's predicted motion never contains the vector, so the offset accrues from the first missed move and the player is set back. There is no partial-reduction gray zone because the module has no scaling path. The check's own leniency - a knockback recorded while Grim is sending its own setback (isSetback) is not required - does not help here, because the packet was sent by the server in normal play, not during a Grim setback. The known bypass is transaction eating (suppressing the transaction echo so the vector never leaves firstBreadMap), which this module does not implement.

How it counteracts this module

Spartan's VelocityListener is a MONITOR-priority ProtocolLib adapter on ENTITY_VELOCITY that records, for the self entity, the server-sent vector (fixed-point ints divided by 8000.0) into a CPlayerVelocityEvent. VelocityEvent.event stores it as protocol.claimedVelocity, pushes it onto the claimedVeloGravity and claimedVeloSpeed queues (capped at two entries) and feeds Spartan's checks through executeRunners. The checks that consume the queues compare the player's reported movement against the claimed vector, with gravity applied to the gravity queue; the listener itself is the feed, not the verdict.

Cancelling the S12 receive-side - the only thing Memeware can do - does not cancel the server's record, so the claimed vector is always present and the movement is always measured against it. A full cancel produces a total deficit: the queues expect the knockback trajectory and the player reports none. The tolerance surface is the two-entry queue cap: only the last two claims are compared, so a user who toggles the module off between hits can present clean windows, but a continuously enabled Memeware Velocity never does.
