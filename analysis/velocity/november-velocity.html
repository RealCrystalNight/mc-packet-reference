Analysis

Overview

November Recode 2.0's Velocity module is a single class with eight modes. REDUCE and REVERSE scale the S12 vector in place with separate horizontal and vertical percentages; CANCEL drops the packet entirely; GRIM cancels the S12 and then eats the S32 confirmations and their C0F echoes so the transaction clock never confirms the knockback arrived; VULCAN cancels the S12 and the one C0F that follows; WATCHDOG_SAFE cancels the S12 but re-applies the vertical component to the player's motion while on the ground; and INTAVE and WATCHDOG are stubs that do nothing in this build. The GRIM mode is the most elaborate: it keeps a queue of cancelled transaction action numbers and matches outgoing C0F uids against it, cancelling the echoes of exactly the transactions it swallowed.

Architecture

The module registers three listeners. EventUpdate runs every tick and clears the funny flag once the transaction queue drains; EventPacket.In handles S12 and S32; EventPacket.Out handles C0F. The settings are a Mode enum plus Horizontal and Vertical floats (0.01 to 200.0, default 50.0) whose visibility lambda only shows them in REDUCE and REVERSE. State is the ConcurrentLinkedQueue of Short action numbers and the funny boolean; disable() clears both, and the null checks at the top of the receive listener reset the state whenever the world or player changes.

The enum drives the dispatch with switch expressions over the packet branches. The module is registered with the name Velocity, the description 'Reduces or cancels out taken velocity', and category Category.COMBAT through the @Register declaration. The transaction queue is a ConcurrentLinkedQueue because the receive listener and the send listener can run on different threads.

Key techniques

REDUCE and REVERSE scale in place: each motion component is multiplied by the percentage over 100.0, truncated back to int, and written with setMotionX/Y/Z, and REVERSE then negates all three. Because the packet fields are ints on the 8000 fixed-point scale, the cast truncates the fractional part of each scaled value. CANCEL, GRIM and VULCAN call setCanceled(true) on the receive event so the vanilla handler never applies the vector. WATCHDOG_SAFE cancels the S12 but, when the player is on the ground, adds motionY over 8000.0 to the player's live motionY, keeping the vertical launch while discarding the horizontal push.

GRIM sets funny on the cancelled S12; every S32 that arrives while funny is cancelled and its action number queued, and every outgoing C0F whose uid matches a queued number is cancelled, so the server's transaction accounting for that window is silently dropped. VULCAN is the simpler variant: one cancelled S12 arms funny and the very next C0F is cancelled. INTAVE and WATCHDOG carry TODO comments and no code, and the horizontal and vertical settings do not affect CANCEL, GRIM, VULCAN or WATCHDOG_SAFE.

Transaction-level bypass

The GRIM mode is aimed at anticheats that bracket velocity with transactions, notably Grim's KnockbackHandler, which sandwiches the S12 between two server transactions and treats the echo of the second as proof the knockback arrived. By cancelling the S32 receipts and the matching C0F echoes, the module prevents that promotion: the velocity stays in the uncertain, not-yet-arrived bucket and is never required by the prediction engine, so the missing knockback never produces an offset. The funny flag is cleared only when the queue drains, so the eating continues until every swallowed transaction has been accounted for.

The cost is a desynced transaction stream: every cancelled receipt and echo moves the client's transaction ledger away from the server's, which transaction-order checks and inventory and UI confirmations notice over time. The queue is deliberately cleared on disable and on world null so the desync cannot persist across sessions, and the update listener clears funny once the queue is empty. VULCAN leaves the transaction stream mostly intact, which is why it is labeled as working on older Vulcan versions only.

What this file does

The whole module is this one file. The receive listener branches on the packet type: S12 carries the mode dispatch (REDUCE and REVERSE scale the vector, CANCEL and GRIM and VULCAN cancel it, WATCHDOG_SAFE applies the vertical component on the ground), and S32 carries the GRIM transaction eating, which cancels the receipt and queues the action number when funny is set. The send listener matches outgoing C0F uids against the queue and cancels the echoes, and the update listener clears funny when the queue drains.

The REDUCE and REVERSE scaling is worth noting for its precision: the packet fields are ints on the 8000 fixed-point scale, so multiplying by a percentage and casting back to int truncates the fractional part of every component, which means the scaled vector can differ from the exact percentage by up to one fixed-point unit per axis. REVERSE negates all three axes after the percentage scaling, producing a full redirection of the knockback.

The mode enum, the settings, the queue and the funny flag are the entire state surface. The visibility lambda on the horizontal and vertical settings hides them in every mode except REDUCE and REVERSE, so the GUI only exposes the sliders where they matter. The INTAVE and WATCHDOG modes are honest stubs with TODO comments ('i have no clue' and 'frappy or plus add this i dont have alts'), and the module's disable() hook clears the queue and flag so the transaction eating cannot leak into the next session.

How it counteracts this module

Grim's KnockbackHandler is the exact mechanism November's GRIM mode was written against. The check sandwiches every ENTITY_VELOCITY between two server transactions: sendTransaction() before the packet and a second transaction queued through tasksAfterSend. The velocity is recorded in firstBreadMap keyed by the first transaction id, and tickKnockback promotes it into lastKnockbackKnownTaken only when a transaction with a larger id arrives, which is how Grim proves the packet reached the client. From that promotion onward the vector is required movement, and onPredictionComplete flags when the prediction offset exceeds offsetToFlag (default 0.001), with a setback once the offset reaches 0.1 or the accumulated threshold (decay 0.999, ceiling 4) hits maxAdvantage 1.

November's GRIM mode attacks the promotion itself. It cancels the S32 receipts while funny and queues their action numbers, then cancels the matching C0F echoes on the send side, so the second transaction of the sandwich never confirms and the velocity stays in the uncertain firstBreadMap bucket, never required and never flagged. The same pattern applies to the first bread: calculateFirstBreadKnockback only returns a velocity whose transaction has been confirmed, and an eaten echo leaves it unknown. This is the check's genuine blind spot, and the mode's entire design exists to exploit it.

The cost is the transaction ledger. Every cancelled receipt and echo moves the client's accounting away from the server's, and Grim's transaction tracking validates its own negative ids, so a confirmation that matches nothing or a missing echo is a stream anomaly that other checks notice. The queue is cleared on disable and on world null, which bounds the desync to the active session, and the update listener clears funny once the queue drains. A player who eats transactions forever will eventually trip the transaction-order surface even if the velocity offset never accrues.
