Overview

Spicy's FastPlace is a two-line timer kill. Its entire logic runs in the EventUpdate pre phase of every tick: it writes 0 into mc.rightClickDelayTimer, the field that Minecraft's right-click handler re-arms to 4 after every processed right click and that the main loop decrements once per tick. Vanilla uses the timer to enforce a minimum four-tick gap between right-click actions, so blocks place at most once every five ticks; with the timer pinned at 0, every click is processed immediately and the placement rate rises to the click-processing ceiling of one C08PacketPlayerBlockPlacement per tick, roughly 20 per second against vanilla's 4 per second. The module touches nothing else: no rotation rewrite, no packet injection, no reach change. Every placement it produces is an ordinary C08, which is what makes the module's only observable the rate of its own C08 stream.

The timer kill

Three sites in Minecraft.java give the timer its lifecycle. The main loop decrements rightClickDelayTimer once per tick while it is above zero (line 1743). The use-item handler is only entered while the timer reads exactly 0 (line 2166: keyBindUseItem down, rightClickDelayTimer == 0, not already using an item), and rightClickMouse() ends by resetting the timer to 4 (line 1577). The module's pre-tick write of 0 therefore collapses the cooldown to zero for every tick the mouse button is held, and because the click handler runs at most once per game tick, the module's ceiling is one placement per tick — 20 per second — against vanilla's one per five ticks.

Wire effect and limits

Each placement is a stock C08PacketPlayerBlockPlacement carrying the vanilla payload: the targeted position, face, held item and the four float offsets. Nothing about the packet's geometry changes, so geometry-based checks see nothing. The gain is purely rate: a sustained 20/s C08 stream instead of 4/s. The same delay gate also throttles right-click item use, so the timer kill accelerates item interactions as well, but the module's purpose and its name are block placement. The C08 rate is the entire detectable surface.

The timer is born and consumed in three spots. Line 292 declares the public int rightClickDelayTimer. Zeroing the field from an event hook defeats the gate without touching the rest of the click path, so every subsequent right click in the same tick passes. Because the click handler itself runs once per tick, the module cannot exceed one C08 per tick no matter how fast the mouse is clicked — the 20/s ceiling is structural, not configurable.

How it counteracts this module

NCP's FastPlace check scores every processed block placement into data.fastPlaceBuckets, an ActionFrequency with 2 buckets of 1000ms each (BlockPlaceData line 53), giving a two-second window. check() computes a full-window score against cc.fastPlaceLimit and, in parallel, a short-term counter (fastPlaceShortTermCount within cc.fastPlaceShortTermTicks) against cc.fastPlaceShortTermLimit; the violation is the larger of the two, lag-adjusted through TickTask, and executeActions decides cancellation. A vanilla click-spammer reaches about 8 places per two-second window (4/s); the module's zeroed timer sustains 20/s, roughly five times that rate, so the full-window score crosses the default limit and the short-term counter trips within the first second of sustained placing.

The check is content-blind — it reads no geometry, no rotation, no item — which is exactly right for this module: the timer kill leaves every other C08 field vanilla, so the rate ledger is the only check in the blockplace battery that actually fires on it.
