Spicy AutoClicker — Full Source Analysis

Spicy's AutoClicker is a hold-to-click module driven from one EventUpdate handler and a single NumberSetting: APS (0-20, default 10). A free-running millisecond Timer gates the swing/attack cycle at a fixed 1000/APS period - the module has no randomization knob at all - and the whole cycle only fires while the left mouse button is held (keyBindAttack.pressed). Every cycle starts with swingItem(), which emits the C0A arm swing; when the crosshair is over an entity the module sends a C02 ATTACK, and when the use-item key is held with a sword it wraps the attack in an unblock/re-block pair: a C07 RELEASE_USE_ITEM at BlockPos.ORIGIN to unwind the previous block, then blockHypixel, which re-raises the sword through sendPacketNoEvent with a C02 INTERACT carrying a rotation-derived aim vector, a second C02 INTERACT and a C08 block placement at BlockPos(-1, -1, -1) with facing 255 - the classic Hypixel sword-block spoof. Off-entity cycles fall back to blockHypixel or a vanilla sendUseItem, so holding left click against a wall keeps the block raised. Analysis

Overview

Spicy's AutoClicker is a hold-to-click module driven from one EventUpdate handler and a single NumberSetting: APS (0-20, default 10). A free-running millisecond Timer gates the swing/attack cycle at a fixed 1000/APS period - the module has no randomization knob at all - and the whole cycle only fires while the left mouse button is held (keyBindAttack.pressed). Every cycle starts with swingItem(), which emits the C0A arm swing; when the crosshair is over an entity the module sends a C02 ATTACK, and when the use-item key is held with a sword it wraps the attack in an unblock/re-block pair: a C07 RELEASE_USE_ITEM at BlockPos.ORIGIN to unwind the previous block, then blockHypixel, which re-raises the sword through sendPacketNoEvent with a C02 INTERACT carrying a rotation-derived aim vector, a second C02 INTERACT and a C08 block placement at BlockPos(-1, -1, -1) with facing 255 - the classic Hypixel sword-block spoof. Off-entity cycles fall back to blockHypixel or a vanilla sendUseItem, so holding left click against a wall keeps the block raised. The static blocking flag and the commented-out 'Swing + Autoblock' ModeSetting are the only remnants of a richer design.

Architecture

The module is a single EventUpdate branch with no event-type filtering beyond that. The gate is timer.hasTimeElapsed((long)(1000 / aps.getValue()), true): Timer.hasTimeElapsed returns true once now - lastMS exceeds the deadline and then resets lastMS to the current System.currentTimeMillis(), so the period is measured from the previous fire rather than from a scheduled slot and no phase error accumulates. Because the gate is only evaluated on each EventUpdate tick, the real-time deadline is quantized to the next 50ms tick boundary, so the packet spacing is the nominal period plus up to one tick of latency. At the default 10 APS the cycle lands every ~100ms; at 20 APS every ~50ms. The APS 0 edge case is worth noting: 1000 / 0.0 is +Infinity, the cast to long saturates to Long.MAX_VALUE, and hasTimeElapsed(Long.MAX_VALUE) can never be true, so the module is inert at 0. The hold gate is re-checked on every tick, so releasing the mouse stops the cycle on the next update with no release shaping - no trailing clicks, no anti-shortpress behavior.

Attack path and Hypixel autoblock

When objectMouseOver.typeOfHit is ENTITY, the module first unwinds a previous block: if the use-item key is held and the equipped item is an ItemSword, it sends C07PacketPlayerDigging RELEASE_USE_ITEM at BlockPos.ORIGIN and clears the blocking flag, then sends the C02PacketUseEntity ATTACK through the normal send queue. Immediately after, if the use-item key is still held with a sword, blockHypixel re-raises the block: it computes the target rotations with RotationUtils.getRotations, calls the module's private sendUseItem (a verbatim copy of the vanilla use-item path - syncCurrentPlayItem, then itemStackIn.useItemRightClick), and fires three packets through sendPacketNoEvent: a C02 INTERACT whose Vec3 is RotationUtils.getVectorForRotation(rotations[0], rotations[1]) (the aim vector itself used as the interact point), a plain C02 INTERACT, and a C08PacketPlayerBlockPlacement at BlockPos(-1, -1, -1) with facing 255 and the held item. sendPacketNoEvent bypasses the event bus, so these packets are invisible to module-level interception. Off-entity the same blockHypixel runs if the use-item key is held with a sword; otherwise, if not already blocking, the module calls mc.playerController.sendUseItem (the real vanilla player controller path) and sets blocking = true - so clicking at a wall keeps the sword raised instead of swinging at air. onEnable and onDisable only snapshot mc.thePlayer.isBlocking() into the static blocking field, which is why the flag survives across the toggle.

Timing fingerprint

The click train is a fixed-period timer with no randomness: inter-click deltas are 1000/APS plus tick-quantization noise only, so at any stable APS the interval is either constant or alternating between two tick multiples (15 APS, for instance, oscillates between 1- and 2-tick spacings as the 66.7ms deadline lands). The swing always precedes the attack by construction - swingItem() runs before the C02 in the same tick - giving a strict 1:1 swing-to-attack ratio with no swung-but-not-attacked and no attacked-without-swing packets. Against hold-gated assumptions the module behaves like a human holding the button, but the cadence itself is machine-regular, and the two Hawk checks in the countering section exist precisely to measure that regularity.

What this file does

The Timer is a free-running wall-clock deadline, not a scheduler. lastMS is initialized to System.currentTimeMillis() at construction; hasTimeElapsed(time, reset=true) (lines 11-25) returns true when now - lastMS exceeds time and, because reset is passed true, immediately sets lastMS back to now. The period is therefore measured from the previous fire time: the next deadline is always 'one period after the last actual fire', so a delayed evaluation (a tick that ran late) does not cause a burst of catch-up clicks - there is no fixed schedule to catch up to. This is also why the AutoClicker's spacing carries tick quantization: the gate is only polled on EventUpdate, so a deadline that falls mid-tick only fires on the next tick, adding up to 50ms of latency to that interval. reset() is never called elsewhere by the module, so the only resets are the self-resets inside the gate. The same Timer class is used by Spicy's Killaura with a random float added to the period; the AutoClicker passes a plain 1000/APS, which is the entire difference between the two modules' timing fingerprints.

How it counteracts this module

Hawk's FightSpeed caps sustained click speed server-side. Every non-INTERACT InteractEntityEvent is timestamped with the HawkPlayer's current tick; the delta since the last attack is recorded only when it is at most RECORD_SENSITIVITY (4) ticks and appended to a per-player delta list. Once the list holds SAMPLES (default 10) deltas, the sum is converted to CPS as 1 / (sum / samples / 20), i.e. 20 divided by the average tick spacing, and an average above MAX_CPS (default 16) punishes with 'failed attack speed. Spicy's module feeds this check directly: at 20 APS the fixed 50ms period averages exactly 1 tick per click, so the reported CPS is 20 and every 10-click window trips the cap; at 15 APS the 1/2-tick alternation averages 1.33 ticks, reporting ~15 CPS, just under the line. The module's fixed period is the worst case for this check - a human's 15-20 CPS bursts would show far higher average tick spacings because real clicking does not sustain a 50ms period. The counter surface only opens at APS values whose tick-quantized average spacing stays under 1.25 ticks (roughly 12-16 APS sustained), and even there the fixed period is what the consistency check below exploits.

How it counteracts this module

FightSpeedConsistency targets machine-regular cadence rather than raw speed. It records the same tick deltas (RECORD_THRESHOLD = 20 * (1 / MIN_CPS) + 1), averages them over SAMPLE_SIZE (default 20) clicks into one CPS value, collects 5 such window averages, and computes their standard deviation: a stdev below STDEV_THRESHOLD (default 0.05) punishes with 'failed click consistency. Autoclicker?', but only when the window average exceeds MIN_CPS (default 10). This is the exact check Spicy's fixed 1000/APS period cannot pass: every 20-click window at any stable APS averages to the same value, the stdev of the 5 samples is effectively zero, and the only requirement is that the module click above 10 CPS on average - which means any APS setting above 10 is an immediate flag, and even 10 APS sits on the boundary. The tick-quantization jitter (at 15 APS, windows mixing different 1/2-tick counts) is far too small to move the stdev above 0.05. There is no randomization setting in the module to raise it, which is the entire point of the comparison with Sigma's AutoClicker in the sibling analysis.

Spartan's protocol layer samples the C0A stream itself. Spicy's module produces the worst-case signal for any rate/regularity analysis on this feed: at a stable APS the delay between consecutive C0As is constant (plus tick quantization), a distribution a human never produces, and every swing carries its own C02, so the swing and attack rates are identical and both maximal. The check implementation class itself is not present in this source snapshot - only the sampling listener and the check registration - so the exact FastClicks thresholds cannot be quoted, but the listener is the layer that turns the module's fixed-period C0A train into the delay samples the detector judges.
