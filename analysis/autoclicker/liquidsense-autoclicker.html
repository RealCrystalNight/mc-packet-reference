Analysis

Overview

AutoClicker fakes mouse clicks through KeyBinding.onTick while a mouse button is held, one independent latch per button, driven from Render3DEvent and paced by TimeUtils.randomClickDelay. Each fire recomputes a fresh uniform delay over the [1000/maxCPS, 1000/minCPS] span, so the cadence is wall-clock randomized rather than fixed-period. An optional Jitter mode perturbs yaw and pitch by up to one degree in UpdateEvent to break rotation heuristics. Because the module never touches packet classes, the click output is whatever the vanilla click pipeline emits: a swing (C0A) and, on a ray-traced hit, the C02 attack.

Click latches

onRender fires at render rate, not tick rate. The left branch requires keyBindAttack.isKeyDown and leftValue, the right branch requires keyBindUseItem.isKeyDown, rightValue and a player who is not using an item; each branch then calls KeyBinding.onTick on the vanilla key binding, which sets its pressed flag for the game loop's next tick. The vanilla run-tick click handling consumes that flag: clickMouse() swings the arm and attacks the targeted entity, rightClickMouse() uses the held item, so the module needs no packet code of its own. leftLastSwing and rightLastSwing are wall-clock stamps updated per fire and the next delay is resampled immediately, so the inter-click gaps are independent uniform draws.

Delay model

TimeUtils.randomClickDelay(minCPS, maxCPS) computes (long) ((Math.random() * (1000 / minCPS - 1000 / maxCPS + 1)) + 1000 / maxCPS) with integer division. With the stock defaults 5-8 CPS that is a uniform draw over [125, 200] milliseconds, mean near 162ms, about 6.2 clicks per second rather than the nominal 6.5 midpoint, and the value change handlers clamp the bounds so minCPS can never exceed maxCPS. The span covers the whole band uniformly: every interval is as likely as any other, which is the signature consistency statistics key on.

Jitter and delivery

Jitter mode runs from UpdateEvent while a button is held and rolls Random.nextBoolean for each axis: yaw and pitch move by up to plus or minus one degree per tick, with pitch clamped to the [-90, 90] range so the random walk cannot escape the legal vertical envelope. The rotation edits land in the player's view and therefore in the next C03 look values, but clicks are unaffected. Delivery of the click itself is tick-quantized even though the latch is millisecond-precise: a delay that expires mid-tick waits for the next run-tick, so the effective inter-C0A gap is the drawn delay rounded up to the tick boundary.

How it counteracts this module

FightSpeed records non-INTERACT InteractEntityEvent deltas within a 4-tick sensitivity window, keeps a 10-sample buffer and reports CPS as 20 divided by the average tick spacing, flagging above MAX_CPS 16. At stock 5-8 CPS settings the module lands near 6.2 clicks per second, far under 16, so the check only engages when the user pushes minCPS toward the 20 cap; at a fixed 20 APS the 1-tick spacing reads exactly 20 and trips every sample.
