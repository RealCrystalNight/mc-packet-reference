Analysis

Overview

Memeware 7.3's Spammer is a one-second chat broadcaster: a single LWJEB handler on UpdateEvent checks a wall-clock Timer, and whenever 1000ms have elapsed it sends exactly one chat message through ChatUtil.sendChat - a direct C01PacketChatMessage enqueue. The text comes from two modes registered via addModes. 'Aids' walks 121 lines of Jake Paul's 'It's everyday bro' lyrics from a Java properties ResourceBundle (jakepaul.properties), sending one line per second in order and wrapping at line 121; 'Memeware' cycles 10 advertisement lines from fart.properties ('Memeware by Dort#0001 aka professional bhopper', 'Memeware > ALL', 'DORT > ALL'). The module has no timing jitter, no cooldown beyond the fixed second, and no awareness of server chat rules - it emits a constant one-packet-per-second stream of template text for as long as it is enabled.

Architecture

The module is one @Handler Consumer<UpdateEvent> plus a util Timer (a millisecond stopwatch over System.nanoTime) and an int message index. onEnable resets the index to 0. Each tick the handler asks timer.delay(1000L) - elapsed wall-clock milliseconds since the last reset - and when the answer is true it picks the mode branch, builds one message, sends it, and calls timer.reset(). Because the gate is wall-clock and the handler runs once per tick, the actual cadence is one message per elapsed second, slightly stretched by tick granularity. The index handling differs per mode: 'Aids' increments before sending, so it emits Jake.1 through Jake.121 then wraps to 0; 'Memeware' checks the wrap condition (index > 9 resets to 0) before sending, so it emits memeware.0 through memeware.9 on a 10-message cycle.

Template sources

SpamUtil loads two ResourceBundles by fully qualified name from the spammer/ package: jakepaul.properties for Aids and fart.properties for Memeware. getAids and getMemeware wrap ResourceBundle.getString in a try/catch that returns '!' + key + '!' on MissingResourceException, which is the module's only failure mode - in practice every key the index walks exists. The Aids pool is the notable one: 121 lines that are mostly the 'It's everyday bro' song, and the pool itself contains consecutive duplicate lines (Jake.38/39/40, Jake.77/78/79, Jake.94/95/96, Jake.120 are all 'It's everyday bro'), so the rotation emits byte-identical messages back to back. The Memeware pool is ten ad lines referencing the client and its staff, several sharing the words 'Memeware' and 'DORT'. ChatUtil.sendChat wraps each line in a C01PacketChatMessage and pushes it through sendQueue.addToSendQueue, the same path vanilla chat uses - no length check, no event-bus detour, and because the lines never start with '.', the Commands module's interceptor leaves them alone.

Wire behavior

The server sees a fixed-rate chat stream: one C01 per second, sustained for as long as the module stays enabled, with content drawn from two tiny closed pools. There is no randomization of order, no jitter in the interval, and no pause when chat is muted or when a server-side rule would object - the Timer just keeps firing. The stream is also content-blind to the client's own Commands module: sendChat goes straight to the send queue, and since none of the template lines carry the dot prefix, the two modules coexist without interfering. The practical consequence is that the module's traffic is the most regular, most repetitive chat a server can measure - a textbook rate signature - while the individual messages remain ordinary-looking C01 packets.

How it counteracts this module

NCP's Text check is built for exactly this traffic shape. Every message scores content (uppercase ratio beyond a third, letter-count and partition ratios, squared per-word notLetter scores - lines 150-231) and then feeds two ActionFrequency accumulators, chatFrequency and chatShortTermFrequency, each with a minimum score floor and windowed totals compared against cc.textFreqNormLevel and cc.textFreqShortTermLevel (lines 257-265). A sustained one-message-per-second stream keeps both accumulators at their floors permanently, and since the module sends continuously, the windowed scores stay above the violation levels until the module is disabled; each violation adds to textVL and triggers the captcha or configured actions (lines 267-294).

The content path has an even more direct hit. The Aids pool contains consecutive duplicate lines - Jake.38/39/40, Jake.77/78/79, Jake.94/95/96 are all 'It's everyday bro' - so the rotation itself emits byte-identical messages back to back, and isSimilar(lcMessage, chatLastMessage, 0.8f) within the 8000ms window (lines 174-179) fires on those transitions; at one message per second the window comfortably spans the duplicates. The stand-still penalty (textMsgNoMoving, lines 200-202) also applies: a player camping a spot while spamming accrues flat extra weight after 8 seconds without movement. The only part of the module that dodges the repeat path is the rotation itself - most pool lines differ from their neighbors - but the frequency accumulators do not care about content, and the Memeware-mode pool repeats shared words ('Memeware', 'DORT', 'ALL') across its ten lines, which feeds the per-word paths instead.

How it counteracts this module

Captcha is the escalation every Text violation reaches: when shouldStartCaptcha returns true (CHAT_CAPTCHA active and no captcha started yet, lines 105-108), Text calls sendNewCaptcha on the first violation (Text line 278), which generates a random string of cc.captchaLength characters and sends it to the player (lines 65-70). From then on checkCaptcha requires message.equals(data.captchaGenerated) - an exact match (line 41). Every other message increments captchTries and captchaVL, re-displays the question, and once captchTries exceeds cc.captchaTries executes cc.captchaActions (lines 47-61).

The Spammer cannot answer by construction: its timer fires every second regardless of what the server asked, and the message it sends is the next template line, never the generated captcha string. So once the frequency accumulators arm the captcha, the module converts itself into a guaranteed-wrong-answer machine - one failed attempt per second - and walks straight into the kick/ban ladder. The only ways out are manual: the user must disable the module and type the captcha by hand. The module has no detection of the captcha question, no pause path, and no way to feed the answer back, which turns NCP's weakest defense into a decisive one against this particular client behavior.

How it counteracts this module

LetterEngine is the optional content-analysis layer Text invokes at line 242 (engine.process(letterCounts, player.getName(), cc, data)); its returned weights are summed or maxed into the message score per cc.textEngineMaximum (Text lines 245-251). It runs config-gated global processors - FlatWords, WordPrefixes and SimilarWordsBKL (BK-Levenshtein tree with range 2, 30-second expiry, 1000-entry cap) - plus per-player processors whose data expires after 10 minutes (600000ms, line 81), each weighted by cc.textGlobalWeight / cc.textPlayerWeight.

For the Spammer, the per-player profile is the relevant mechanism: the engine learns the distribution of words a player actually uses, and the module's closed template pools are the opposite of that distribution. The Aids mode replays the same 121 lyric lines forever, and the Memeware mode reuses 'Memeware', 'DORT' and 'ALL' across ten of its lines, so repeated words and word-prefixes from the learned set accumulate processor weight on every cycle; SimilarWordsBKL additionally scores near-duplicate words within edit range. Because the spammer emits one message per second, the engine gets constant reinforcement instead of the sparse, varied input a human produces. The honest caveat is configuration: the processors only run when the corresponding CHAT_TEXT_GL_*_CHECK / textPlayerCheck flags are enabled, so this layer is an amplifier for the frequency check rather than a standalone detector.
