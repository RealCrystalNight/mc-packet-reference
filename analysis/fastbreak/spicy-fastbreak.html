Overview

Spicy's FastBreak accelerates block breaking by writing a fixed amount into the client-side damage accumulator every update tick: curBlockDamageMP gains speed/100 (speed 1-20, default 20), so at the default the accumulator climbs 0.2 per tick on top of vanilla's hardness-based contribution and any block crosses the 1.0 break threshold in about five ticks of holding, regardless of how hard it is. The handler clamps the accumulator at 1.0 and returns once the break threshold is reached. Unlike other clients it never touches blockHitDelay, so the 5-tick post-break pause stays vanilla and chained breaks keep their normal gap. An older EventAddBlockDamage approach that set the damage directly sits in the source commented out.

Fixed-rate damage accumulation

PlayerControllerMP.onPlayerDamageBlock adds the block's relative hardness to curBlockDamageMP on each damage tick and sends C07 STOP_DIGGING when the accumulator reaches 1.0 (Spicy PlayerControllerMP lines 289-330). The module runs on every EventUpdate: while the accumulator is below 1.0 it adds speed/100 (0.01 to 0.2), and once at or above 1.0 it pins the accumulator to exactly 1.0 and returns, letting the vanilla break path fire on the current damage tick. Because the added term dominates the hardness term for hard blocks, the effective break time converges to about five ticks at default speed for any block that would otherwise take longer; soft blocks that vanilla breaks in one or two ticks are barely affected, since their own hardness term already crosses the threshold.

Wire fingerprint

The module sends no packets of its own; it changes the controller state that drives vanilla C07 emission. The per-block window shrinks from the hardness-based duration (stone by hand is about 45 ticks) to roughly five ticks at default speed, so the server sees START_DIGGING followed by STOP_DIGGING after a fraction of the expected time. blockHitDelay is untouched, so the 250ms inter-block pause remains, which distinguishes this implementation from the zero-delay variants and means the chained-break signature is weaker than in clients that also zero the delay.

Detection surface

The counters split across the two effects. NCP blockbreak FastBreak and Hawk BlockBreakSpeedSurvival compare the measured break time against an expected time derived from the block's hardness and the player's tool, which is the direct counter to the collapsed window; NCP blockbreak Frequency caps breaks per time frame and bites in creative-mode chains. The Arc lineage offers nothing here: Vrekt-Arc's block-break check is creative-gated, and Vrekt-Arc v2 dropped the block package entirely, its PacketListener subscribing only to FLYING, POSITION, USE_ENTITY, ARM_ANIMATION, HELD_ITEM_SLOT and BLOCK_PLACE.

What this file does

The module is a single EventUpdate handler with one NumberSetting. The speed setting spans 1-20 with a 20 default, and each pre-update either adds speed/100 to mc.playerController.curBlockDamageMP or, once the accumulator has reached 1.0, pins it there and returns. The pin matters: without it the accumulator could ride above 1.0 while the vanilla break path waits for its own damage tick, and with it the break fires on the first damage tick after the threshold.

The commented-out EventAddBlockDamage block shows the previous design, which set the damage directly from the speed value inside the block-damage event; the shipped build moved the mutation to the update tick instead, which spreads the acceleration over the damage controller's own cadence. The class carries no other logic: no blockHitDelay manipulation, no packet interception, no onEnable/onDisable behavior.

The relevant state is curBlockDamageMP (line 47) and blockHitDelay (line 57). onPlayerDamageBlock decrements blockHitDelay and returns without damaging while it is positive, sets blockHitDelay to 5 when a new block is first targeted (line 234), resets the accumulator on a block change, adds getPlayerRelativeBlockHardness to curBlockDamageMP each damage tick (line 319), and when the accumulator reaches 1.0 sends the break and resets both fields (lines 289-330).
