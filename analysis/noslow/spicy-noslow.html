Overview

Spicy's NoSlow works on two layers. Client-side, the fork's EntityPlayerSP has been modified so the item-use movement damping — the moveForward/moveStrafe *= 0.2 applied while using an item — is gated on the NoSlow module being disabled, so turning the module on removes the local slowdown without touching the item-use state. Server-side, the module runs a release-spam cycle: on every pre-tick while the player is blocking, moving and grounded, with no killaura target, it sends a C07PacketPlayerDigging(RELEASE_USE_ITEM) whose BlockPos coordinates are drawn randomly from the full double range, with EnumFacing.DOWN. Each release clears the server's item-use state, so the server never observes a blocking player. The C08 re-place branch in the same handler is unreachable dead code: the outer guard already requires the pre phase, so the else that would re-arm the use-item placement is never taken.

The client-side half

EntityPlayerSP.onLivingUpdate (line 832) is a modified copy of vanilla's damping: if (isUsingItem() && !isRiding() && !SpicyClient.config.noSlow.isEnabled()) { moveStrafe *= 0.2F; moveForward *= 0.2F; sprintToggleTimer = 0; }. The 0.2 damping is preserved verbatim but conditioned on the module's toggle, so with NoSlow on the client keeps full input speed while still holding the sword up. This half is client-internal: the server only sees its consequence in the C03 stream, which shows full-speed movement while the player appears to block.

The wire cycle

While isBlocking(), isMoving() and isOnGround(0.42) hold, with the killaura target null, every EventUpdate pre sends C07PacketPlayerDigging(RELEASE_USE_ITEM). The position is junk on purpose: each coordinate is RandomUtils.nextDouble(Double.MIN_VALUE, Double.MAX_VALUE), flooring to enormous integers far outside the world — RELEASE_USE_ITEM processing ignores the position anyway, so the payload is harmless noise. The server clears the player's item-use on each release, so its blocking state flaps to false every tick. The else branch that would send C08PacketPlayerBlockPlacement with BlockPos(-1, -1, -1) and face 255 (the vanilla use-item re-arm) is unreachable because the outer condition already requires e.isPre(), making the module release-only as shipped.

The module is one pre-update handler gated on isBlocking, isMoving, the 0.42 ground probe and an empty killaura target. The active statement sends the C07 release with the randomly generated BlockPos and EnumFacing.DOWN; the inner else that would send the C08 re-arm is dead code because the outer condition already tests e.isPre(). The Killaura import shows the intended combat integration: NoSlow holds its releases while the aura has no target.

How it counteracts this module

A discrepancy over 0.1 at a position update triggers the rubberband, and at VL above RELEASE_ITEM_OVER_VL (default 4) the check force-releases the item via pp.releaseItem().

For this module the branch only bites in the window where the server still believes the player is blocking: the release spam clears the server-side item-use on the first packet, so after one tick Hawk treats the player as a normal non-blocking mover and the full-speed C03s pass. The check is the counter to the C08-re-arming NoSlow variants that keep the server-side blocking state alive — the behavior this module's dead re-arm deliberately avoids.
