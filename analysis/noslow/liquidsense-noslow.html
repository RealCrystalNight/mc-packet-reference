Overview

NoSlowDown attacks the item-use slowdown on two layers. Client-side, the fork's MixinEntityPlayerSP fires a SlowDownEvent carrying the vanilla 0.2F/0.2F multipliers whenever the player uses an item or sword-blocks, and the module's onSlowDown handler replaces those values with per-item multipliers (default 1.0, full speed). Server-side, the Packet family of modes keeps the item-use state re-armed: a C07 RELEASE_USE_ITEM in the motion PRE phase and a C08 use-item placement in POST, per tick or on a half-rate cadence depending on the mode, with a Hypixel variant that re-arms at a constant fake block coordinate.

Client-side slowdown removal

The fork hook lives in MixinEntityPlayerSP.onLivingUpdate: when a held item is present and the player is using it or sword-blocking through the Aura blocking status, and not riding, it constructs SlowDownEvent(0.2F, 0.2F), multiplies movementInput.moveStrafe and moveForward by the event's values, and resets sprintToggleTimer to 0. The module's onSlowDown handler rewrites those values through getMultiplier: ItemFood, ItemPotion and ItemBucketMilk pick the consume multipliers, ItemSword the block multipliers, ItemBow the bow multipliers, and any other item falls back to the vanilla 0.2F. All six multipliers default to 1.0, so a stock install completely cancels the input slowdown with no packet cost at all.

Packet re-arm loop

Packet mode runs from MotionEvent and needs a sword in hand, movement (unless AAC4 mode is on, which drops the movement gate) and a blocking state from either the player or the Aura blockingStatus. The PRE phase queues C07PacketPlayerDigging(RELEASE_USE_ITEM, BlockPos(-.8,-.8,-.8), DOWN) and POST queues C08PacketPlayerBlockPlacement with the same fake block position, face 255 and the held stack: the release ends the server-side use, the re-arm restores it, so the server never sees the sustained item-use that would re-apply slowdown. AAC4 mode halves the rate by gating on ticksExisted and 1 (odd ticks only) plus an aura-target or blocking requirement, using BlockPos(-1,-1,-1) for the release. Hyt32 fires whenever the Aura has no target, releasing at BlockPos.ORIGIN and re-arming at getHypixelBlockpos, which despite the Random calls always evaluates to the constant BlockPos(2820, 0, 2820).

SlowDownEvent as the mechanism

The event itself is defined in Events.kt with mutable strafe and forward floats, and the mixin reads the mutated values back through getStrafe and getForward before applying them. Because the module writes 1.0F defaults, the multiplication becomes identity and the sprintToggleTimer reset in the mixin stays vanilla. The packet ceremony therefore manages server-side item state only; the movement gain is purely the fork hook, which is why the module has no effect when the mixin is not active, and why the onSlowDown handler alone would be a no-op without the mixin firing the event.

How it counteracts this module

UseItemAdapter timestamps every C07 RELEASE_USE_ITEM and sets CombinedData.isHackingRI when a release arrives within timeBetweenRL (default 70ms) of the previous one; SurvivalFly then tags the move noslowpacket and runs Improbable on the horizontal distance. Packet mode's per-tick release and re-arm land about 50ms apart, well inside the window, so the release stream trips the flag; AAC4's odd-tick cadence spaces releases at roughly 100ms, just past the 70ms ledger, which is the honest evasion surface.

How it counteracts this module

Hawk's Speed check tracks players who are pulling a bow, consuming or blocking, and once releaseItemOverVl (default 4) is exceeded it forces releaseItem() on the player, tearing down the re-arm loop server-side so the next C08 use-item cannot re-enter the blocking state. The forced release resets the item-use the module is trying to preserve, so sustained noslow packet streams accumulate the VL that triggers it.
