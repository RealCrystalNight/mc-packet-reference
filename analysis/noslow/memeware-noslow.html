Two independent mechanisms share the module name. The packet re-arm cycle

In the NCP mode, while mc.thePlayer.isBlocking() is true the pre phase queues C07PacketPlayerDigging(RELEASE_USE_ITEM, BlockPos.ORIGIN, EnumFacing.UP), and the post phase calls setItemInUse(getCurrentEquippedItem(), 71999999) followed by mc.playerController.sendUseItem. This fork's sendUseItem (PlayerControllerMP line 457) syncs the held slot, addToSendQueue's a C08PacketPlayerBlockPlacement carrying only the item stack (line 463), then runs useItemRightClick locally. The 71999999 duration is effectively infinite, so the client believes the block is still held for the whole fight while the server saw a release. Per blocking tick the server therefore receives RELEASE_USE_ITEM followed by a use-item C08: the release clears the server's item-in-use state (which is what allows sprint and full-speed movement to be consistent), and the C08 re-arms the use for combat purposes.

Mode and timing profile

The packet pair fires every tick while blocking, so the C07 release cadence is 20/s, 50ms between releases; vanilla sends a single RELEASE_USE_ITEM when the use key is released, so the per-tick release stream is the module's packet fingerprint. The dead registrations matter for behavior: addModes registers 'AAC', 'NCP' and 'Velt' (line 18), but the handler tests only isMode('NCP') (line 23), so switching to 'AAC' or 'Velt' leaves the packet layer inert while the client-side EntityPlayerSP hook (which does not consult the mode string) keeps removing the slowdown. A user in those modes gets the speed gain with no packet re-arm, which produces the one-fingerprint state: full-speed blocking movement with no releases at all.

How it counteracts this module

NCP's UseItemAdapter intercepts C07 and timestamps every RELEASE_USE_ITEM (lines 412-425): when a new release arrives less than timeBetweenRL (default 70ms, line 128) after the previous one, it sets CombinedData.isHackingRI. The NCP mode's releases land 50ms apart, so every release after the first marks the player; SurvivalFly consumes the flag (line 877) by tagging the move 'noslowpacket' and running Improbable.check on the horizontal distance (line 880), so the full-speed sprint the re-arm cycle enables is scored against NCP's statistical speed model instead of the vanilla slowdown. This is the direct counter to the packet layer: the module removes the slowdown, and the release-gap detector fingerprints exactly that removal.

How it counteracts this module

Hawk's Speed check predicts the horizontal position from the previous move and compares it against the actual update; on a discrepancy beyond its threshold it punishes and rubber-bands, and its releaseItemOverVl setting (default 4, line 80) then forces the item to release (lines 213-214) when the flagged player is pulling a bow, consuming or blocking. The module's whole effect is sprint-speed movement while blocking, so a blocked sprint that accumulates speed VL triggers the forced release, which tears the re-arm loop down: the client is made to emit a genuine RELEASE_USE_ITEM that the module did not schedule, and the server-side use state desyncs.
