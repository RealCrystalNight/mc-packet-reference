Overview

Sigma's AutoTool switches to the fastest digging tool while the attack key is held. The EventTick handler returns immediately unless keyBindAttack is pressed and the mouse-over carries a block position, then delegates to BlockUtils.updateTool, which scans the nine hotbar slots for the item with the greatest getStrVsBlock against the targeted block and writes inventory.currentItem directly. The module never constructs packets: the C09 held-slot change is emitted by the fork's PlayerControllerMP.syncCurrentPlayItem whenever the tracked slot diverges at the next interaction, and the C07 dig pairs are the vanilla clickBlock stream.

Tool selection

updateTool iterates the hotbar with a strength accumulator that starts at 1.0F and a strictly greater-than comparison, so a bare hand (1.0 strength) never wins and the first slot that beats the current best is kept; ties favor the lowest index. The selection is purely getStrVsBlock against the targeted block state: there is no durability weighting, no enchantment-aware ranking and no silk-touch or fortune logic, so the module picks the raw fastest dig and will happily choose a nearly broken tool over a fresh one.

Wire shape

The write goes through the public currentItem field, and the C09 comes from PlayerControllerMP.syncCurrentPlayItem, which is called at the top of the interaction entry points (clickBlock, onPlayerDamageBlock, onPlayerRightClick and the rest) and emits C09PacketHeldItemChange only when the tracked slot diverges from the field. Because the switch happens while the attack key is held, the C09 lands immediately before the vanilla C07 START and STOP dig pair of the next break, producing the C09(tool), C07 pair, C09(restore) fingerprint around each dig when the player switches back.

Scope and gating

The module is inert while the attack key is released, and it bails when objectMouseOver is null or carries no block position, so it only fires at an actually targeted block. It never touches the inventory window, never ranks armor or offhand state, and has no settings at all: the constructor is empty, which makes the module a pure convenience layer over the vanilla dig path.

How it counteracts this module

UseItemAdapter's onChangeSlot handles PlayerItemHeldEvent: on a real slot change it calls requestItemUseResync, which forcibly releases an item in use so a held-slot switch cannot mask an ongoing eat or block. For AutoTool the handler is inert: the switches happen between digs, outside any item use, so there is no in-use state to release, and the resync path never fires.

The entry is the documented gap of the family: no NCP check scores the C09-to-C07 pairing that is AutoTool's actual fingerprint. The slot change is only observable at the protocol level (the C09 before the dig), and NCP's only held-slot hook is the item-use resync, which by design ignores switches that occur while nothing is in use. Servers that want the pairing need a protocol-level switch-and-dig check, which this tree does not ship.
