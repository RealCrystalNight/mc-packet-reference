Overview

AntiBlind is a one-line visual cleaner: on every UpdateEvent it checks isPotionActive(Potion.blindness) and, when the flag is set, removes the effect from the local active potion map with removePotionEffect. The strip is purely client-side; the server keeps the blindness effect and its expiry timer, so no packet leaves the client and the module is invisible to traffic analysis. The only wire interaction is receive-side: S1C metadata carries the entity's potion-effect bitmask, and S1D re-applications are stripped again on the next update tick.

Registration and per-tick strip

The module is the Memeware event pattern at its smallest: a single public Consumer<UpdateEvent> field named eventConsumer0. Module.toggle() calls EventAPI.put(this) on enable, which subscribes the instance to the client's PubSub bus, and the bus invokes every Consumer field whose generic type matches the fired event. The consumer tests mc.thePlayer.isPotionActive(Potion.blindness) and calls mc.thePlayer.removePotionEffect(Potion.blindness.id) (id 15) when true. In the fork's EntityLivingBase, removePotionEffect pulls the PotionEffect out of activePotionsMap and calls onFinishedPotionEffect, which sets potionsNeedUpdate and, because worldObj.isRemote is true on the client, skips the attribute-modifier half entirely; the local DataWatcher potion bitmask is recomputed on the next onUpdate. The blindness overlay in EntityRenderer is driven by isPotionActive, so the black screen and fog vanish the same tick.

Wire presence is zero

Nothing is sent. The server-side player still has the effect: health packets, S1D apply, S1E expire and the S1C metadata bitmask all continue as vanilla. Because the removal only edits the client's activePotionsMap, the divergence is confined to the local render state. If the server re-applies blindness (a new S1D or a refresh), the next UpdateEvent strips it again within a tick, so the effect can never render. A server cannot learn that the effect was removed: no client packet reports potion state, and the S1C stream is server-originated.

Failure modes

The strip is keyed on the local map, so it depends on the effect having been applied client-side first: an S1D that arrives while the module is disabled leaves the overlay until re-enable. removePotionEffect returns the removed effect and the null branch is silent, which is harmless here. Because the consumer runs on UpdateEvent only, the module never touches other players, only the local camera state. There are no settings, no modes and no config surface; the module is unconditional behavior for the render category.

How it counteracts this module

The only Grim consumer of self-targeted S1C metadata. It unwraps WrapperPlayServerEntityMetadata for the player's own entity id, strips the pose entry on 1.14+ clients and reads the watcher-0 flags byte to track sprinting, gliding and swimming for prediction. It never reads the potion-effect bitmask and it reacts only to server-originated packets, so the module's local removePotionEffect produces no observable input: the S1C stream Grim sees is identical to a vanilla client's. This entry is the honest boundary for the whole module family: the strip is a render-state edit that no metadata consumer can observe.
