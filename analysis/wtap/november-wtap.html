Overview

November Recode 2.0's WTap re-asserts the sprint flag around each melee attack so the server treats the attacker as freshly sprinting when it applies the vanilla sprint-knockback multiplier. An EventPacket.Out listener watches every C02 attack against an EntityLivingBase and, while the local player is sprinting and the Delay timer has elapsed, either queues a C0B STOP_SPRINTING then START_SPRINTING pair in SILENT mode or drops the local sprint flag for the Hold Delay window in LEGIT mode. Both modes produce the STOP then START sequence that resets the server-side sprint state; the difference is delivery: SILENT pushes both C0Bs straight into the send queue in one tick, while LEGIT flips keyBindSprint.pressed and setSprinting through the vanilla flag path so the pair is emitted by the normal C0B mirror and split across ticks.

Mode split and state

The module keeps two timers and one boolean: timer gates how often a wtap can fire, holdTimer measures how long LEGIT mode keeps sprint dropped, and canWTap tracks whether the flag is currently down. disable() restores sprint through legitSprint(true) whenever the module is turned off mid-hold, so a disabled module never leaves the player de-sprinted. The Mode setting defaults to LEGIT; the Delay setting (default 250ms, scale 0.5, range 0-5000ms) is the cooldown between wtaps and the Hold Delay setting (same defaults, visible only while Mode is LEGIT) is how long the sprint stays dropped before the update listener calls legitSprint(true) again.

SILENT delivery

When Mode is SILENT, the C02 listener builds a C0BPacketEntityAction STOP_SPRINTING and immediately queues a START_SPRINTING behind it through mc.thePlayer.sendQueue.addToSendQueue, both in the same tick, and sets canWTap true so the hold path never engages. The pair ends with the sprint flag true, which is what the server needs to see for the next attack to count as sprinting, and because both packets are queued back to back they arrive in one server tick. The client-side sprint flag is never touched, so sprint movement continues at full speed through the whole exchange.

LEGIT delivery

LEGIT mode calls legitSprint(false), which sets keyBindSprint.pressed false and thePlayer.setSprinting(false). The setSprinting call mirrors into a C0B STOP through the vanilla EntityPlayerSP path, and the hold timer starts; when holdTimer passes the Hold Delay the update listener flips canWTap back and calls legitSprint(true), whose setSprinting(true) emits a C0B START roughly five ticks later at the default 250ms hold. The pair is therefore event-visible and tick-split, which is the quieter fingerprint, at the cost of a brief local speed loss while the flag is down.

How it counteracts this module

Grim's BadPacketsF tracks the server-side sprint state and flags a START while the tracked state is already true, or a STOP while it is already false, with a one-packet exemption for the first unknown state. The November pair is a strict STOP from a true state followed by a START from a false state, so a clean alternating burst passes the check by construction. The failure mode is overlap: if a second wtap fires while the previous pair's state has not settled, or the player's own sprint toggle interleaves with the module's pair, the stream stops alternating and a duplicate START or STOP arrives, which flags and cancels the packet.

The SILENT mode's unconditional pair is also exposed when the player is not actually sprinting, because the C02 listener requires isSprinting and so never fires in that state; the exposure is instead latency jitter collapsing two pairs into one tick, which turns a valid alternation into a duplicate. This is the honest both-sides statement: the clean case passes, the jitter case flags.

How it counteracts this module

SprintA runs after prediction and flags whenever the server-side sprint flag is true while the player's food level is at or below 6.0. November's module has no food gate: the C02 listener only checks isSprinting, so it keeps re-asserting START through long engagements while sprinting itself drains hunger, and a sustained fight naturally crosses the line. A vanilla player would have been forced out of sprint by the hunger system well before that point, so the module's persistence is what the check catches.

The honest boundary is that the module cannot avoid this by configuration: dropping the flag below the hunger threshold would also disable the knockback trick, because the whole point is to keep the server-side sprint state true at attack time. Grim's threshold and the module's requirement are the same rule seen from opposite sides.
