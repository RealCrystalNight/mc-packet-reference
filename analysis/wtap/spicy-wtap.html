Spicy Wtap — Full Source Analysis

Spicy's Wtap attaches the sprint reset directly to the attack packet. A single EventSendPacket handler watches the outgoing stream, and when it sees a C02PacketUseEntity with the ATTACK action while the food level is above 6, it captures the current sprint state, pushes a C0BPacketEntityAction STOP_SPRINTING followed by START_SPRINTING onto the send queue, and restores the local sprint flag. The pair trails the C02 and re-arms the server-side sprint state for the following hit, which is what keeps the vanilla sprint knockback multiplier applied to consecutive attacks. Unlike Rise's tick-driven burst, Spicy emits exactly one pair per attack, gated by the same food rule vanilla applies to sprinting, and the handler never fires on anything but C02 ATTACK packets, so the enqueued pair cannot re-enter the handler.

Analysis

Overview

Spicy's Wtap attaches the sprint reset directly to the attack packet. A single EventSendPacket handler watches the outgoing stream, and when it sees a C02PacketUseEntity with the ATTACK action while the food level is above 6, it captures the current sprint state, pushes a C0BPacketEntityAction STOP_SPRINTING followed by START_SPRINTING onto the send queue, and restores the local sprint flag. The pair trails the C02 and re-arms the server-side sprint state for the following hit, which is what keeps the vanilla sprint knockback multiplier applied to consecutive attacks. Unlike Rise's tick-driven burst, Spicy emits exactly one pair per attack, gated by the same food rule vanilla applies to sprinting, and the handler never fires on anything but C02 ATTACK packets, so the enqueued pair cannot re-enter the handler.

Architecture

The module registers one handler on the EventSendPacket bus with a pre-phase check. onEvent casts the packet, tests instanceof C02PacketUseEntity, reads getAction() and requires it to equal Action.ATTACK, then requires mc.thePlayer.getFoodStats().getFoodLevel() > 6. The handler body captures continueSprint from isSprinting(), enqueues the STOP then START pair through mc.thePlayer.sendQueue.addToSendQueue, and calls setSprinting(continueSprint) to restore the client-side flag. The food gate mirrors the vanilla hunger rule that sprinting requires more than 6 hunger, so the module never contradicts the client's own sprint eligibility.

Ordering and send path

The handler runs while the C02 is already being processed, and the pair is appended to the outgoing queue, so the server sees the STOP and START after the attack that triggered them. That ordering is the point of the technique: the reset applies to the next hit in the chain, and because the client flag is restored to continueSprint, the player keeps sprinting visually and mechanically. addToSendQueue bypasses the event bus, so the pair is not re-broadcast to other modules, and even if it were, the handler only reacts to C02 ATTACK packets, so there is no loop. The module is inert when the player is not sprinting only in the sense that the pair still goes out; the local flag restore then just re-asserts the non-sprint state.

Behavioral footprint

Each melee hit emits exactly two C0B packets, one STOP and one START, with no tick timer and no burst window, which distinguishes it from Rise's nine-pair burst. The footprint is therefore a two-packet toggle pair per C02 attack, always in the same order and always from a true sprint state when the player is sprinting, or from a false state when the player is not, because the pair is sent unconditionally past the food gate. That unconditional send is the module's tell: a STOP while the server already believes the player is not sprinting is a duplicate status packet, which server-side checks read as a protocol violation.
