Overview

Sigma 4.11's Killaura is a full combat automation module driven entirely from the pre phase of EventUpdate, with EventRender3D reserved for ESP and EventStep for critical timing. One onEvent method branches on event type: the pre update picks a target (or a whole list in Multi mode), writes the aim into the outgoing movement packet via em.setYaw/setPitch, gates attacks on a per-tick timer (cps is re-rolled between the MIN/MAX APS settings every tick), and then either fires hitEntity or fakes a miss with a bare swing. Rotation is pluggable across Basic (instant snap), Smooth (yaw/1.7 easing), Legit (a nonlinear easing with a carried momentum term aacB) and Predict (one-tick velocity extrapolation), and the aura itself has Switch/Single/Multi/Multi2 target cycling, a Pre/Post attack-timing split, a hit-chance gate that also hard-misses when the needed yaw change exceeds an interval that shrinks with distance, and four autoblock flavors (NCP, Hypixel, Basic1, Basic2) that park the sword via a client-side itemInUseCount = 999 flag while the real block state is driven by C02 INTERACT + C08 placement packets. It also folds in a miniCrit integration that rewrites the movement packet's Y and onGround to manufacture fall-criticals whenever the Criticals module runs in Minis or HMinis mode.

Architecture

All logic lives in one @RegisterEvent handler listening for EventUpdate, EventRender3D and EventStep. The pre update first runs the death and respawn guards (toggle off when GuiGameOver shows or ticksExisted <= 1), then a conflict check that bails whenever BedFucker or CakeEater is mid block-break or Scaffold owns the look (Legit/Cubecraft/Custom with ROT), because those modules would fight Killaura for the rotation. Targeting is a two-pass sweep over mc.theWorld.loadedEntityList: getOptimalTarget(range) for the primary and blockTarget = getOptimalTarget(blockRange) for autoblock, each filtered by validEntity (distance, WALLS-gated visibility, AntiBot exclusion, friends, teams, invisibles, players-only) and ranked by sortList under the Angle/Range/FOV/Armor priority. In Single/Switch/Multi2 the chosen target is stored and the hit pipeline runs once per tick when timer >= 20/cps; Multi instead builds the full loaded list, aims at the first entry and sends one attack to every entry in the same tick. The post phase (TYPE=Post) runs the identical interval/hitchance gate on the post update, and blockTarget handling arms or parks the shield around it.

Rotation and miss gating

The rotation modes differ in how much of the required yaw is written per tick. Basic writes the exact rotation via em.setYaw/em.setPitch, so the movement packet that tick carries the full snap. Smooth steps yaw by targetYaw / 1.7 per tick. Legit uses customRots, a piecewise easing: yawFactor = targetYaw^2 / (4.7 * targetYaw) normally (targetYaw / 3.7 when the delta is under 5 degrees), and whenever the raw factor exceeds 7 it stores aacB = yawFactor * 7 and switches to targetYaw / 3.7, so the next tick adds the remembered momentum (yawFactor = targetYaw^2 / (6.7 * targetYaw) + aacB) -- an explicit attempt to break per-tick yaw-rate limits by splitting one large rotation across two packets. Predict aims at posX + (posX - lastTickPosX), one tick of extrapolation. getCustomRotsChange randomizes the aim point by +-0.3 blocks on x/z and -(0.4 + mult * randoms[1]) on y whenever the target is not inside the player's own bounding box, and bakes a -2.5 degree pitch bias into the returned delta. Independently of the rotation mode, shouldMiss is forced true when a random draw exceeds the HITCHANCE percent, when a new target was picked within the last 70ms (newTarget.delay(70)), while AutoPot is potting, or when the yaw still needed at attack time exceeds interval = 60 - distance * 10 (50 - distance * 10 in Legit), which collapses to near zero at max range; a miss still swings (swingItem) so the client-side animation and the server-side C0A both fire without an attack.

Attack cadence and autoblock packet flow

The attack gate is a tick counter, not a timer: timer increments every pre update and an attack fires when timer >= 20/cps, with cps re-rolled as randomNumber(min, max) between the MIN and MAX APS settings (both default 5, range 1-20), so at 20 APS one C02 ATTACK lands per tick and in Multi mode one per target per tick. hitEntity unblocks first if needed, fires the EventAttack hook around swingItem + playerController.attackEntity (the vanilla local attack so knockback and item damage simulate), then re-blocks in Basic1 mode. Autoblock is a three-packet sequence: with the INTERACT setting on, block() sends a C02 carrying a random Vec3 (x/z in +-0.5, y in 0-2.0) and a second C02 with Action.INTERACT, then a C08PacketPlayerBlockPlacement with the held item; blockHypixel() swaps the C08 position for PlayerUtil.getHypixelBlockpos(username) with facing 255. The shield is represented client-side by forcing mc.thePlayer.itemInUseCount = 999, and unBlock() reverses it with syncCurrentPlayItem plus a C07PacketPlayerDigging RELEASE_USE_ITEM at BlockPos.ORIGIN. The miniCrit hook rewrites the movement packet instead: in HMinis it cycles em.setY(posY + 0.0625 / 0.0626 / 0 / 0) with lastReportedPosY = 0 and setOnGround(false), and in Minis it staggers a 0.0628 offset off lastStep timing (the C04 it builds is commented out, so only the Y rewrite ships) -- the server sees the player fall ~0.06 blocks between hits and awards the fall-critical damage bonus.

How it counteracts this module

In this Spartan snapshot (the ai.idealistic line, CheckEnums wiring the KILL_AURA and HIT_REACH hacks to their check classes), CombatListener is the USE_ENTITY pipeline: onPacketReceiving resolves the target entity id against online players, fires a PlayerUseEvent into the combat checks for every ATTACK action, and records the attack in a pendingAttacks map (an OverflowMap capped at 1024 entries). The map is drained onPacketSending when the server's damage event for that entity arrives, and a pending attack that outlives the matching transaction is flagged through isSDesync() with the message 'attack faster than the transaction response' -- Spartan's rate check is keyed to the transaction echo, not to a fixed APS ceiling.

That transaction anchor is the relevant counter for Sigma's burst shapes. Multi mode emits N C02 attacks in a single tick, and at 20 APS the module sustains 20 attacks per second, while the transaction stream is one server response per tick: bursts of simultaneous C02s cannot each have a distinct transaction predecessor, so the pendingAttacks map accumulates entries that never drain in order, and the desync path reports attacks arriving faster than the transaction responses. The combat event that CombatListener fans out also feeds the hitbox validation (RayUtils.inHitbox ray tests) that the HIT_REACH hack is wired to in CheckEnums, which is where the module's 4.5-8 block default range is caught by the server-side hitbox intersection instead of the client's own claim.
