Analysis

Overview

Memeware 7.3's Kill Aura is a blockhit-styled melee aura built around a release-attack-reblock cycle. The Aura module registers a single 'Kill Aura' toggle with Single/Multi/Hypixel modes, and SingleAura.doUpdate drives the Single mode from every UpdateEvent (pre and post phases): while a target is in range it snaps both yaw and pitch to the target on every tick, releases the held item with a C07 dig packet, swings and sends the C02PacketUseEntity ATTACK, then re-blocks with a C08 use-item placement on the following tick. Attack cadence comes from one shared Timer at 1000 / Click Speed milliseconds (12-20 CPS default 12), and targeting is the first EntityLivingBase in the loaded entity list within range (default 6, up to 8) with no line-of-sight test, so hits land through walls and the Players/Monsters/Animals toggles are never actually read by the Single path.

Architecture

The Aura module (module/combat/Aura.java) registers 'Kill Aura' with the settings Click Speed (12, 1-20), Block Chance (60), Range (6, 1-8), Auto Block (on), Keep Sprint, Players/Animals/Monsters/Invisibles/Teams, and dispatches its onUpdate handler to SingleAura, MultiAura or HypixelAura by mode. SingleAura is a static helper: doUpdate is called once per UpdateEvent and branches on e.isPre() and e.isPost() to order the blockhit state machine. Module state is entirely static - a shared Timer, the booleans block/unblock/unblocked, and Aura.isBlocking / Aura.currentEntity - so mode switches share one clock and one flag set. Several registered settings are never read on the Single path: Block Chance, Keep Sprint and Teams are ignored, and CombatUtil.getTarget does not consult the Players/Monsters/Animals flags at all, so Single mode attacks any living entity. onDisable resets the statics and, when SingleAura.unblock is set, sends a C07 RELEASE_USE_ITEM at a nearby air position so the player is not left visually blocking.

Blockhit state machine

The cycle is driven by two flags. block starts true; on a post-phase update, if Aura.isBlocking (sword in hand, Auto Block on, and CombatUtil.canBlock finds a target within range + 4) and block is set, the module sends C08PacketPlayerBlockPlacement with the fixed BlockPos(-0.2223, -0.132, -0.312), facing 255, the held item and a 0.0F hit vector - the classic 'use item on air' right-click - and sets the public unblock flag that the module's onDisable consumes. block is unconditionally reset to true at the top of the next update, so the C08 re-fires on every post phase while a target exists, keeping the sword raised. The attack is gated by unblocked: when timer.delay(1000L / clickSpeed) fires on a pre-phase update the module sends C07PacketPlayerDigging RELEASE_USE_ITEM at a.offsetDown() (the same fixed position with Y minus one), sets unblocked = true, block = false, and resets the timer; on the following update, swingItem() plus a C02PacketUseEntity ATTACK are sent and unblocked clears. Each cycle is therefore C07 release, C0A swing + C02 attack, C08 re-block, repeated at Click Speed cycles per second, and because the C02 only fires on the update after a release, the module never attacks from the blocking state. AutoPotion.isPotting() short-circuits the whole pass so potting and attacking never interleave.

Aim and targeting

Target selection is CombatUtil.getTarget, which iterates mc.theWorld.loadedEntityList and returns the first EntityLivingBase within range that is alive, not the player, not in the static bot list, and not invisible (unless Invisibles is on). There is no canEntityBeSeen call and no sorting, so the chosen target is whichever living entity the entity list happens to expose first - not necessarily the nearest - and walls never block a hit. Aim is RotationUtils.getRotations, which targets ent.posY + ent.getEyeHeight() / 2.0F from a fixed eye height of the player's posY + 1.2 and returns both yaw and pitch; doUpdate writes both into the UpdateEvent via setYaw/setPitch, so the client's next movement packet carries a fully snapped look on every tick a target is held. Because the C02 ATTACK is sent on the same tick the look was overwritten, the server-side hit-scan direction and the attack are tick-aligned - exactly the signature that rotation-pattern checks look for.

How it counteracts this module

Hawk re-derives hit validity on the server instead of trusting the client. FightHitbox defers each InteractEntityEvent until the next MoveEvent so the ray uses the yaw/pitch the client actually attacked with (for 1.8 clients the stored yaw is used because the cursor is a tick behind), then casts from the attacker's eye location (position + 1.62, minus 0.08 when sneaking) along that direction against the victim's hitbox, rewound through hawk's lag compensator by the attacker's ping and expanded by a 0.005 epsilon. maxReach defaults to 3.1 (5.0 in creative). An intersection farther than maxReach punishes with 'Reach: Xm'; no intersection at all punishes 'Did not hit hitbox.' when checkBoxIntersection is on (default); and with checkOccluding enabled, a block hit before the victim punishes 'Interacted through <block>'.\n\nAgainst Memeware this fires on every hit: the Range setting defaults to 6 and goes to 8, so the 3.1 cap is exceeded by several blocks and each attack reports its measured reach. The module also never calls canEntityBeSeen, so with checkOccluding on, the C02 through a wall is exposed as a block intersection that arrives before the victim. What the check cannot see is a legitimate sub-3.1 attack: the 0.005 epsilon and lag-compensated victim position absorb the small interpolation error, but a 6-block hit is nowhere near that tolerance, so lowering Range to 3 or below is the only way past it.

A cancelless hint check that analyzes the mouse-move samples around each interaction. How it counteracts this module

NCP counts only real attacks: the ProtocolLib UseEntityAdapter interprets every USE_ENTITY packet, resolves the action (legacy reflection or ProtocolLib enum wrappers), and feeds only ATTACK actions into data.attackFrequencySeconds, an ActionFrequency with 16 buckets of 500ms covering 8 seconds. Each check call compares five running sums against the config limits - the newest 500ms bucket against 8, the 1s sum against 15, the 2s sum against 30, the 4s sum against 60 and the 8s sum against 95 - and triggers a violation the moment any sum exceeds its limit, feeding TickTask's Improbable system with weight 3.0 and applying the default actions (cancel vl>10, kick at vl>200).\n\nMemeware sends exactly one C02 per blockhit cycle at Click Speed (12-20 CPS), so the module's upper range is what this check counters: a sustained 16 CPS trips the 1s cap (16 vs 15) and the 2s cap (32 vs 30), and 17+ CPS trips the 500ms cap (8-9 vs 8). The default 12 CPS sits comfortably under all five caps, and the 8s window means short bursts average out, so a user who keeps Click Speed at or below 15 sees no violations - the module's max of 20 is the exposure.

How it counteracts this module

Arc v2's composite killaura check runs from FightListener.onFight on the EntityDamageByEntityEvent at HIGHEST priority and scores five sub-conditions with defaults from config.yml: max-direction-angle 1.2 radians, max-swing-time 80ms, max-reach 4.2 blocks, max-attacks 16 per second and max-attack-packets 20 per second. The Multi branch compares the angle between two consecutively attacked entities (angleDifference > 1.2 while both are within reach), Direction measures the angle from the player's look vector to the entity, NoSwing fires when more than 80ms pass without an arm swing, Reach measures the distance to the entity's location minus its current velocity (knockback exclusion), and Speed counts attacks and attack packets per second, resetting each second.\n\nAgainst Memeware the reach sub-check is the hard counter: the module's 6-8 block Range dwarfs the 4.2 cap and the distance is measured to the entity position minus velocity, so knockback does not mask it. The Speed sub-check catches the top of the CPS range (20 CPS exceeds both 16 attacks/s and 20 packets/s), while the default 12 CPS passes. Direction passes because the module snaps both yaw and pitch onto the target, and NoSwing passes because swingItem() precedes every C02 - so on a default-config server only the reach component fires, and it fires on every hit.
