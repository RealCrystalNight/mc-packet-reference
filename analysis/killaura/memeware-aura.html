Overview

Architecture

Aura.java registers 'Kill Aura' with a ModeSetting holding Single, Multi and Hypixel plus Click Speed (12, 1-20), Block Chance (60, 1-100), Range (6, 1-8), Auto Block, Keep Sprint and the Players/Animals/Monsters/Invisibles/Teams toggles. Its @Handler onUpdate is one lambda that branches on isMode and calls SingleAura.doUpdate, MultiAura.doUpdate or HypixelAura.doUpdate with the module, the event and the Minecraft instance. Module state lives in two public statics on Aura itself - isBlocking and currentEntity - while each helper keeps its own private statics: SingleAura owns a Timer and the block/unblock/unblocked flags, MultiAura owns a Timer, the target list, a rotating targetIndex and a Random for the block-chance roll, and HypixelAura owns a Timer plus block and stopServerBlocking. Because the helpers are stateless classes, switching modes mid-fight hands the next event to a fresh set of flags but keeps the shared isBlocking/currentEntity that render code and onDisable read. onDisable clears both statics and, when SingleAura.unblock is set, sends a C07 RELEASE_USE_ITEM at BlockPos(0.221, 0.221, 0.213) facing UP so a disable between a release and a re-block does not leave the player stuck blocking server-side. Notably the Teams setting is read nowhere: all three modes hardcode teams = false, and the target scans ignore the Players/Monsters/Animals flags, so the module attacks any qualifying living entity regardless of the UI toggles.

Mode dispatch and Hypixel specifics

The three modes differ in cadence and in how aggressively they hide the block state. Single mode targets one entity (first match in the loaded entity list, no sorting and no visibility test) and cycles C08 re-block on post updates, C07 release plus C02 attack on timer-fired pre updates. Multi mode rotates its aim through the target list one index per cycle while attacking every entry in the list on each timer fire, so its look direction (targets.get(targetIndex)) is usually not the entity it is actually hitting (Aura.currentEntity is set to targets.get(0)). Hypixel mode is the per-server special: it computes the effective click speed as MathUtils.getRandom(cps - 2, cps) when the setting is above 2, so at the default 12 the inter-attack interval is randomized between 50ms and 60ms, breaking the fixed period that consistency checks look for; below 3 the setting is used verbatim. It also writes rotations into three places at once - the UpdateEvent yaw/pitch for the movement packet plus rotationYawHead, rotationPitchHead and renderYawOffset - so the server sees the snap in the look packet while the render and head-tracking fields agree. Blocking state is tracked with the local stopServerBlocking flag: it arms when a target appears, and when the target list empties with autoBlock on, the mode sends a C07 RELEASE_USE_ITEM at BlockPos.ORIGIN facing DOWN so the server-side block is dropped on target loss, mirroring what Single mode's onDisable does on module disable.

Attack and autoblock packets

Single mode: on a post-phase update, if Aura.isBlocking (sword in hand, Auto Block on, CombatUtil.canBlock within range + 4) and the block flag is set, it sends C08PacketPlayerBlockPlacement with the fixed BlockPos(-0.2223, -0.132, -0.312), facing 255, the held item and a zero hit vector - the classic use-item-on-air right-click - and raises the unblock flag; when the timer fires on a pre update it sends C07 RELEASE_USE_ITEM at the same position offset down one block, swings (C0A), clears block, and the C02 ATTACK lands on the following update. Multi mode gates blocking on chance(Block Chance): on pre it queues C07 RELEASE_USE_ITEM at BlockPos.ORIGIN facing UP, on post it calls setItemInUse plus playerController.sendUseItem (which emits its own C08), and on each timer fire it loops the whole target list sending, per target, a silent C18PacketSpectate(CubeUtil.CUBECRAFT_UUID) followed by swingItem and a C02 ATTACK - so the sweep rate is targets-per-cycle times cycles-per-second. Hypixel mode condenses the cycle into one tick: on pre, when the randomized timer fires, it releases with C07 at BlockPos.ORIGIN facing DOWN, swings and attacks; on the same tick's post phase it re-blocks with C08 at a BlockPos built from RandomUtils.nextDouble(Double.MIN_VALUE, Double.MAX_VALUE) on every axis, coordinates no real block can occupy, toggling Aura.isBlocking back on.

How it counteracts this module

Hawk's FightSpeed measures the gap between consecutive C02 ATTACK interactions in client ticks. It only logs a click when the gap is at most RECORD_SENSITIVITY (4) ticks, accumulates 10 samples, and computes the average CPS as 1 / ((sum / 10) / 20); an average above MAX_CPS (16 by default) punishes and rewards otherwise. Against Multi mode this is a guaranteed flag: the mode sends one C02 per target in the same tick, so consecutive deltas are 0, the sum is 0, and the CPS computation divides by zero and produces Infinity, which the check punishes outright. Single and Hypixel modes hit the same wall at the top of the range: a sustained 18-20 CPS trips the 16 CPS cap after 10 samples, and Hypixel's randomized window (cps - 2 to cps) does not help because the average still lands at the setting. The default 12 CPS with a roughly 50ms per-tick jitter sits under the cap, which is the config the module ships with.

How it counteracts this module

NCP's Angle builds an AttackLocation per damage event with the player's position, yaw, the victim id and the deltas to the previous entry, keeps a 1000ms window, and scores four signals: average movement below 0.2 blocks, average time between attacks below 150ms, average yaw change above 50 degrees, and switch speed counted whenever the victim id changes with a yaw jump over 30 degrees. Each signal that exceeds its configured threshold feeds data.angleVL, which decays by 0.98 on clean checks and executes actions past its violation level. Multi mode scores maximum on every signal: the whole sweep happens in one tick (time near 0), the player does not move between victims (movement near 0), and consecutive victims are different entities in different directions (id changes with large yaw jumps), so with detection-tuned thresholds the accumulated VL crosses the cancel line within a handful of cycles. The stock thresholds in this tree (move 100, time 150, yaw 60, switch 50) sit above the 20-30 maximum per-call scores, so the check only acts when an admin lowers them, which standard NCP detection configs do.
