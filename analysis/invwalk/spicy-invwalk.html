Analysis

Overview

Spicy's InvWalk lets the player move while any GUI screen is open. On every pre EventUpdate, when mc.currentScreen is non-null and not a chat screen, the module re-asserts the forward, back, left, right and jump keybinds from the raw keyboard state, which vanilla would otherwise ignore while a screen is up. The resulting movement is ordinary C03 traffic produced by the normal movement handler; onDisable clears all six binds including sprint to avoid stuck keys. The module's value is the inventory-walk gameplay itself, and its detection surface is the window-state checks that expect no movement while a container is open.

Architecture

The module body is a single pre EventUpdate branch guarded by mc.currentScreen. When a screen is open and it is not a GuiChat, the five movement binds, forward, back, left, right and jump, are re-asserted from the raw keyboard state via KeyBinding.setKeyBindState(bind.getKeyCode(), Keyboard.isKeyDown(bind.getKeyCode())). The chat exclusion keeps typing in chat from moving the character. onDisable is the cleanup half: for each of the six binds including sprint it clears pressed, but only when the raw key is no longer down or a screen is still open, so a key genuinely held after the module turns off is not stuck.

Key techniques

Vanilla clears the movement input while any GUI is up, so without the module no C03 movement would be produced; with it, held keys keep driving the player through the normal movement handler. The re-assertion runs every tick, so key state changes are picked up within one tick and the player can start and stop moving while the inventory is open. The six-key list on disable is broader than the five-key loop on update, which is why sprint is restored on shutdown but never re-asserted during play: the module cannot sprint-burst from a chest, only walk and jump.

Detection surface

The module constructs nothing itself, but the re-asserted binds make the vanilla movement handler emit the same position-rotation packets it would emit with no screen open, and that is precisely the traffic window-state anticheats check for. The relevant server-side enforcement is window-open movement checking and the toggle and speed bounds on whatever else the player runs at the same time.

How it counteracts this module

Arc-v2's Speed check measures the reported horizontal delta against a world-derived envelope, with ice, ice-block, block-move and step modifiers and configurable maxima, punishing distances the player's movement mode and potion effects cannot justify. It is the generic horizontal-speed bound for the anticheat.

Inventory walking produces ordinary-speed movement: InvWalk re-asserts the same key states the player would use with no screen open, and the client's motion physics are unchanged, so the reported deltas stay inside the running-speed envelope and the check passes. It appears in this entry list because inventory-walk is frequently combined with speed enhancement, and the moment a speed module runs while the inventory is open, the C03 stream carries deltas past the envelope and Speed flags the session.

The boundary: by itself the module never violates a horizontal-speed check, and no speed check can distinguish an inventory-open move from a normal move by content, because the packets are identical. Detection of inventory walking relies on window-state checks such as Hawk's InventoryMove; Speed only contributes when the player is cheating horizontally on top of it.
