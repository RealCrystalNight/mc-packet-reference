Analysis

Overview

Tenacity's Sprint is a one-line key-forcer: every pre-motion tick it sets the vanilla sprint key binding's pressed state to true — except while the Scaffold module is enabled — which walks the client's own sprint state machine into sprinting whenever its gates pass (forward input at 0.8 or above, food above 6, not blinded, not using an item), and the vanilla transition code emits the C0B START_SPRINTING entity action on the state change. onDisable releases the key and clears the sprinting state directly. The module builds no packets and changes no server-side state by itself; its entire wire footprint is the C0B stream the vanilla client produces for a permanently held sprint key.

Architecture

The module registers one IEventListener on MotionEvent with no settings. The handler's only guard is a module-repository lookup: if ScaffoldModule is enabled, the listener returns, so the key is never forced while scaffolding. onDisable releases the key binding and calls setSprinting(false) on the player, undoing both the binding state and the entity flag so the sprint state cannot linger after a manual toggle-off.

Key-forcing mechanics

keyBindSprint.pressed = true every tick feeds the vanilla sprint logic in EntityPlayerSP.onLivingUpdate: sprint starts when forward input is at 0.8 or above, food is above 6 (or the player may fly), the player is not blinded and not using an item (Tenacity's NoSlow module can override the item gate), and sprint stops when forward input drops below 0.8, the player collides horizontally, or food drops to 6 or below. The C0B entity action fires only on state transitions — the client compares isSprinting() against serverSprintState and sends START or STOP on change — so the module's permanent key press yields one START per transition, never a packet flood.

Wire footprint and limits

Functionally the module is indistinguishable from a player physically holding the sprint key: same state machine, same gates, same single C0B per transition. Its abuse surface is therefore not a packet anomaly but the sprint-state contract itself — sprinting kept alive through the strafes, item uses (with NoSlow) and boundary conditions that vanilla's forward gate alone cannot police once the state is on. Detection targets that contract: direction-vs-state consistency, redundant status packets, and the hunger window.

How it counteracts this module

Hawk's SprintDirection polices the contract between sprint state and movement direction. It records the last tick the player was not sprinting and only evaluates once sprint has been active for at least two ticks, then reconstructs the expected move from the tracked velocity (adjusting for soul sand, webs, hit slowdown, friction and the 0.2 forward component of a jump) and compares the actual horizontal move against the yaw vector: an angle beyond pi/4 + 0.3 radians (~62 degrees) punishes with a rubber-band. The 2-tick grace and the exemptions are the check's honest tolerance; within them, vanilla-compliant sprinting passes.
