Packets This Module Uses

C0APacketAnimation

Analysis

Overview

A two-mode cosmetic held-item animation switcher: on every UpdateEvent it writes a static int — 1 for the '1.7' mode, 6 for the 'Sigma' mode — that the client's render path reads to change the swing/held-item pose. It sends no packets; the vanilla C0APacketAnimation swing stream continues unchanged, so swing-packet anticheats observe an identical stream.

Architecture

The module's entire state is a public static int anim. The single UpdateEvent consumer sets it to 1 or 6 depending on which of the two modes (1.7, Sigma) is selected; any render or animation code elsewhere in the client reads Animations.anim to choose its pose. There is no per-tick work beyond the assignment, no onEnable/onDisable logic, and no packet interaction.

The swing packet is untouched

C0APacketAnimation is emitted by the vanilla swing path (attacks, block interactions, right-clicks) through EntityPlayer.swingItem, independently of how the held item is rendered. Because the module only changes the client-side pose, the C0A stream the server receives is byte-identical to vanilla. The real anticheat surface for animation cheats is therefore not this module but the adjacent class that does alter the swing stream — killaura that attacks without swinging (caught by NoSwing checks) and autoclickers that flood swings (caught by swing-frequency checks).

A static int plus one consumer. The UpdateEvent handler compares the active mode by name and writes the matching animation id into the shared static, which is the entire public contract of the module — other Nekoware render code switches its pose off Animations.anim, so toggling the module changes the visual without any per-frame cost or any packet.
