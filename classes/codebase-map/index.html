Codebase Map

Complete reference of the deobfuscated 1.8.9 net/minecraft source: world model, protocol, client runtime, utilities — every signature copied verbatim.

This document is a complete reference of the deobfuscated Minecraft 1.8.9 source under the net/minecraft/ package. It is meant to be given to an AI as context before any task that touches this codebase, so the model does not waste tokens grepping for symbols, does not invent helper methods that already exist, and does not reinvent geometry, packet, or inventory primitives that are already provided.

The document is organized so you can read it top-to-bottom and understand how the game fits together, or jump to any section and find the actual field names and method signatures available. Every signature in this file is copied verbatim from the source — if a name appears here, it exists in the codebase exactly as shown.

How to read this map

The codebase has 1,612 Java files spread across 23 top-level packages. The architecture follows a clear separation: the net.minecraft root holds shared types used on both client and server; net.minecraft.client holds everything that only runs on the player's machine (rendering, GUI, the local player); and net.minecraft.server holds the integrated server used in singleplayer (in multiplayer this code does not run on the player's side — the dedicated server is a separate jar that uses the shared types). The net.minecraft.network package is shared because both ends speak the same protocol.

A useful mental model: imagine the program as four concentric layers. At the center is the **world model** — blocks, entities, items, NBT. One layer out is the **network protocol** that serializes that model. One more layer out is the **client runtime** — Minecraft class, the render pipeline, the GUI system, the local player. The outermost layer is the **integrated server**, which only matters in singleplayer.

When you build something that interacts with the game, you almost always work in the third layer (client runtime) and use the inner two layers as primitives. Knowing which class lives in which layer tells you what is and isn't safe to mutate from where.

The inner layer: the world model

Block (`net.minecraft.block.Block`, 148 methods)

A Block instance describes a *kind* of block — not a specific position. There is exactly one Block instance for stone, one for dirt, one for every block type. Each one is a singleton stored in the static registry Block.blockRegistry. To get from a position to the block at that position, you go through World.getBlockState(BlockPos).getBlock() — the state tells you what variant (e.g. wool color, log axis) sits there, and getBlock() recovers the singleton.

Block carries protected fields for its bounding box (minX, minY, minZ, maxX, maxY, maxZ), blockHardness, blockResistance, lightOpacity, lightValue, stepSound, blockParticleGravity, blockMaterial, and slipperiness (used for ice physics — anything that overrides this affects entity friction on top of it).

IBlockState is the immutable view of a block-at-a-position. Its interface is tiny:

java
public interface IBlockState {
    Collection<IProperty> getPropertyNames();
    <T extends Comparable<T>> T getValue(IProperty<T> property);
    <T extends Comparable<T>, V extends T> IBlockState withProperty(IProperty<T> property, V value);

Notice withProperty returns a *new* IBlockState — these are flyweights, so don't try to mutate them in place.

Entity hierarchy

The entity class chain is Entity → EntityLivingBase → EntityPlayer → AbstractClientPlayer → EntityPlayerSP for the local player, and Entity → EntityLivingBase → EntityPlayer → AbstractClientPlayer → EntityOtherPlayerMP for any other player visible in the world. Mobs split off after EntityLivingBase into EntityCreature, EntityMob, EntityAnimal, etc.

Every entity carries position, motion, and rotation as **public mutable fields**, not getters. This is a deliberate choice in vanilla; you write entity.posX = newX rather than calling a setter. Knowing the exact field names is therefore essential.

The protocol layer

Now we move outward to the network layer. The Minecraft protocol is stateful — at any moment the connection is in one of four states defined by EnumConnectionState: HANDSHAKING, STATUS, LOGIN, or PLAY. The state determines which packet IDs are valid in each direction.

For a normal multiplayer session the lifecycle is:

1. Client opens TCP to the server, connection state is HANDSHAKING.
2. Client sends C00Handshake(version, host, port, nextState). nextState is 1 for server list ping or 2 for login.
3. State transitions to STATUS or LOGIN.
4. Through LOGIN, encryption (S01PacketEncryptionRequest / C01PacketEncryptionResponse) and compression (S03PacketEnableCompression) negotiate, then S02PacketLoginSuccess arrives.
5. State transitions to PLAY. The server sends S01PacketJoinGame with your entity ID, gamemode, dimension, difficulty.
6. From here on you exchange play-state packets every tick (20 ticks per second).

EntityPlayerSP.onUpdateWalkingPlayer — the tick that builds C03

For a complete understanding, here is the *literal* logic of how the local player's position is sent to the server every tick. This method is called from EntityPlayerSP.onUpdate() when not riding (riding sends C0CPacketInput plus a C05PacketPlayerLook instead):

java
public void onUpdateWalkingPlayer() {
    // 1. Sync sprint state if it changed since last tick
    boolean flag = this.isSprinting();
    if (flag != this.serverSprintState) {
        this.sendQueue.addToSendQueue(new C0BPacketEntityAction(this,
            flag ? START_SPRINTING : STOP_SPRINTING));
        this.serverSprintState = flag;
    }

    // 2. Sync sneak state if it changed
    boolean flag1 = this.isSneaking();
    if (flag1 != this.serverSneakState) {
        this.sendQueue.addToSendQueue(new C0BPacketEntityAction(this,
            flag1 ? START_SNEAKING : STOP_SNEAKING));
        this.serverSneakState = flag1;
    }

    // 3. If this player is the camera (i.e. not spectating someone else)
    if (this.isCurrentViewEntity()) {
        double dx = this.posX - this.lastReportedPosX;
        double dy = this.getEntityBoundingBox().minY - this.lastReportedPosY;
        double dz = this.posZ - this.lastReportedPosZ;
        double dyaw = this.rotationYaw - this.lastReportedYaw;
        double dpitch = this.rotationPitch - this.lastReportedPitch;
        boolean moved   = (dx*dx + dy*dy + dz*dz > 9.0E-4) || this.positionUpdateTicks >= 20;
        boolean rotated = (dyaw != 0) || (dpitch != 0);

        if (this.ridingEntity == null) {
            // Pick the smallest packet that conveys the change
            if (moved && rotated) {
                send new C06PacketPlayerPosLook(posX, bb.minY, posZ, yaw, pitch, onGround);
            } else if (moved) {
                send new C04PacketPlayerPosition(posX, bb.minY, posZ, onGround);
            } else if (rotated) {
                send new C05PacketPlayerLook(yaw, pitch, onGround);
            } else {
                send new C03PacketPlayer(onGround);          // The "still here" ground-only ping
            }
        } else {
            // Riding case: tell the server motionX/motionZ but use -999 as the Y sentinel
            send new C06PacketPlayerPosLook(motionX, -999.0, motionZ, yaw, pitch, onGround);
            moved = false;
        }

        this.positionUpdateTicks++;
        if (moved)   { lastReportedPosX/Y/Z = current; positionUpdateTicks = 0; }
        if (rotated) { lastReportedYaw/Pitch = current; }
    }
}

Two non-obvious facts: the Y coordinate sent is boundingBox.minY (your feet), not posY (your hip), and even when idle a C03PacketPlayer(onGround) goes out every 20 ticks because positionUpdateTicks forces a full re-send. This is why the connection feels "alive" even when you stand still.

EntityLivingBase.jump and moveEntityWithHeading — the physics

When you press space and you're on the ground, EntityLivingBase.jump() runs:

java
protected void jump() {
    this.motionY = (double)this.getJumpUpwardsMotion();      // 0.42
    if (this.isPotionActive(Potion.jump)) {
        this.motionY += (amplifier + 1) * 0.1F;              // jump-boost
    }
    if (this.isSprinting()) {
        float f = this.rotationYaw * 0.017453292F;           // degrees → radians
        this.motionX -= MathHelper.sin(f) * 0.2F;
        this.motionZ += MathHelper.cos(f) * 0.2F;            // sprint jump impulse
    }
    this.isAirBorne = true;
}

Every tick, EntityLivingBase.moveEntityWithHeading(strafe, forward) runs the rest of the physics. The friction coefficient 0.91F is applied to motion each tick on land; on the ground it gets multiplied by the block's slipperiness (default 0.6, ice 0.98). In water and lava the same skeleton runs with different constants. moveFlying(strafe, forward, friction) is the inner step that transforms input strafe/forward into actual motionX/motionZ deltas after applying the friction.

Worth knowing: the rendering call sites

Rendering for the world happens inside EntityRenderer.renderWorldPass(int pass, float partialTicks, long finishTimeNano), which calls RenderGlobal.renderEntities and RenderGlobal.renderBlockLayer for each block layer (SOLID, CUTOUT_MIPPED, CUTOUT, TRANSLUCENT). The HUD is rendered separately in GuiIngame.renderGameOverlay(float partialTicks) which is called once per frame from EntityRenderer.updateCameraAndRender.

The order each frame is roughly: runTick (game logic, may run more than once if behind on ticks) → updateCameraAndRender(partialTicks) → renderWorld → renderWorldPass for each stereoscopic pass → GuiIngame.renderGameOverlay → currentScreen.drawScreen (if any GUI is open).

Coordinate, threading, and timing conventions

It is worth burning into memory a few things that are easy to get wrong if you don't know them.

The Y axis is vertical, X is east-positive, Z is south-positive. Yaw 0 means facing south (+Z); yaw 90 means west (-X); yaw -90 means east (+X); yaw 180 or -180 means north (-Z). Pitch -90 is straight up, +90 is straight down, 0 is horizon. Yaw increases clockwise when looking down at the player.

When sending position packets, vanilla sends boundingBox.minY (the feet Y) and not posY (which is the same value, equivalent to feet, for most entities — but never assume; always use getEntityBoundingBox().minY to be safe and consistent with vanilla's packet builder).

A tick is 50 milliseconds — 20 ticks per second. Timer.renderPartialTicks is the 0.0–1.0 fraction of the next tick already elapsed when a frame is being rendered; you use it to interpolate prevPosX + (posX - prevPosX) * partialTicks so things move smoothly between ticks.

The main client thread is the only thread safe for touching mc.theWorld, mc.thePlayer, GUI state, or the renderer. The Netty I/O thread arrives in NetworkManager.channelRead0 and packet processPacket methods, but NetHandlerPlayClient.handleXxx immediately re-schedules onto the main thread via PacketThreadUtil.checkThreadAndEnqueue. If you ever need to schedule work onto the main thread from another thread, mc.addScheduledTask(Runnable) is the supported entry.

The S12 velocity packet encodes blocks/tick as int = blocksPerTick * 8000, clamped to ±3.9 before scaling. So a horizontal knockback of 0.4 blocks/tick goes over the wire as 3200.

Block-state IDs are packed as (blockId << 4) | meta in the legacy serialization path; modern code uses Block.BLOCK_STATE_IDS to map IBlockState ↔ int without that constraint.

The 0.91 friction constant in EntityLivingBase.moveEntityWithHeading is multiplied by the ground block's slipperiness when the entity is on the ground. Default slipperiness is 0.6F; ice is 0.98F; slime is also higher. Multiply 0.91 by the appropriate value to see the per-tick decay.

Reach distance is 4.5 survival when calculated from eyes (getBlockReachDistance() returns 5.0 for blocks, 3.0 for entity interact in survival; creative is 5.0 everywhere except entity which is 6.0).
