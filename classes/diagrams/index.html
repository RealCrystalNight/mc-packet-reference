Diagrams

Visual companion: architecture layers, packet lifecycle, threading, collision, raytrace and movement constants in plain ASCII.

This file is the visual companion to MCP_1_8_9_CODEBASE_MAP.md. The map describes *what* exists in the codebase; these diagrams describe *how* the parts connect and *how data flows* between them. Read the map first to learn the names; read this file to learn the shapes.

Every diagram below is plain ASCII so it survives copy-paste into any context window. They are organized roughly from outermost (how the whole game is laid out) inward to specific subsystems (collision, raytracing, friction). Each diagram is followed by a short explanation of what it teaches.

---

1. The four architectural layers

The codebase has a clear concentric structure. At the center is the world model — what blocks, entities, and items are. One ring out is the network protocol — how that model is serialized. One ring further is the client runtime — the game loop, renderer, GUI, local player. The outermost ring is the integrated server, which only exists in singleplayer.

The teaching point: outer layers depend on inner layers, but never the reverse. Block doesn't know about packets; Packet doesn't know about Minecraft.theWorld. When you write new code, find the innermost layer where it belongs and put it there — code in the wrong layer creates circular dependencies or accidentally depends on Minecraft.getMinecraft() from a place that should be reusable on the server side too.

In multiplayer, Layer 4 doesn't run on your machine — it runs on the dedicated server, which is a separate jar that uses Layers 1 and 2 but has its own implementation of Layer 3-equivalent code (MinecraftServer, NetHandlerPlayServer, EntityPlayerMP, WorldServer). The client side never touches WorldServer or EntityPlayerMP even in singleplayer except through carefully threaded boundaries.

2. Entity class hierarchy

The entity tree is deep but well-organized. Most of the methods you'll call on the local player are defined two or three levels up the chain, which is why knowing the hierarchy matters: if a method isn't on EntityPlayerSP, it's almost certainly inherited from EntityLivingBase or Entity.

                              Entity
                                │
       ┌────────────────┬───────┴────────┬──────────────────┐
       │                │                │                  │
EntityLivingBase   EntityItem    EntityXPOrb         EntityArrow
       │           (dropped       (xp drops)         (+ siblings EntityFireball,
       │            items)                           EntitySnowball, EntityFishHook
       │           (each directly                     in .projectile; EntityEnderPearl
       │            extends Entity)                   in .item)
       │
   ┌───┴────────────────┬─────────────┬──────────────────────┐
   │                    │             │                      │
EntityPlayer    EntityLiving (children: EntityCreature [most
   │           mobs], EntityFlying [Ghast], EntityAmbientCreature
   │           [Bat]; Creature extends Living extends LivingBase)
   │                │
   │       ┌────────┴────────┐
   │       │                 │
   │   EntityMob       EntityAgeable
   │   (hostile,       (Villager extends this;
   │    extends         EntityAnimal extends this:
   │    Creature)       passive Cow, Sheep, Pig,
   │       │           Chicken, Horse, Rabbit, ...;
   │   Zombie, Skeleton, Wolf extends EntityTameable
   │   Creeper, Spider,  (Tameable extends Animal))
   │   Witch, Enderman, ...
   │
AbstractClientPlayer
   │
   ├──→ EntityPlayerSP      (the local "you")
   │       fields: sendQueue, movementInput, sprintingTicksLeft
   │       method: onUpdateWalkingPlayer() — builds C03/C04/C05/C06
   │
   └──→ EntityOtherPlayerMP (any other player visible)
           method: setPositionAndRotation2() — called by NetHandlerPlayClient.handleEntityMovement (S14) / handleEntityTeleport (S18) for interpolation

The teaching point: EntityPlayerSP is the only one of the two AbstractClientPlayer subclasses that *sends* packets. EntityOtherPlayerMP only *receives* updates from the server about other players and interpolates them smoothly. So sendQueue only exists on EntityPlayerSP — don't go looking for it on a generic player reference.

Also: the abstract EntityLivingBase.getHeldItem() is overridden by EntityPlayer to read from inventory.getCurrentItem(), and by EntityLiving.getHeldItem() (returning equipment[0], inherited by all mobs). So calling getHeldItem() on a generic EntityLivingBase does the right thing regardless of whether you have a player or a mob.

3. The packet protocol lifecycle

A connection goes through four states. Each state has its own packet ID space, so packet ID 0x01 in LOGIN is a completely different packet from 0x01 in PLAY. The state transitions are deterministic.

        ┌─────────────────────┐
        │     HANDSHAKING     │   Initial state on TCP connect
        │   (state ID = -1)   │
        └──────────┬──────────┘
                   │
                   │ Client sends:
                   │   C00Handshake(protocolVersion, host, port, nextState)
                   │     nextState = 1 → STATUS
                   │     nextState = 2 → LOGIN
                   ▼
        ┌─────────────────────┐
        │   STATUS or LOGIN   │
        │   (state ID = 1/2)  │
        └──────────┬──────────┘
                   │
                   │ STATUS path (server-list ping):
                   │   C →  C00PacketServerQuery
                   │   S →  S00PacketServerInfo
                   │   C →  C01PacketPing
                   │   S →  S01PacketPong
                   │   ─ connection closes ─
                   │
                   │ LOGIN path (joining a server):
                   │   C →  C00PacketLoginStart(username)
                   │   S →  S01PacketEncryptionRequest  (only if online-mode)
                   │   C →  C01PacketEncryptionResponse
                   │   S →  S03PacketEnableCompression  (sets threshold)
                   │   S →  S02PacketLoginSuccess(uuid, name)
                   ▼
        ┌─────────────────────┐
        │        PLAY         │   Now you exchange play-state packets
        │   (state ID = 0)    │   every tick, 20 times per second
        └──────────┬──────────┘
                   │
                   │ Server immediately sends:
                   │   S46PacketSetCompressionLevel   (PLAY, only when compression changes — not routine)
                   │   S01PacketJoinGame(entityId, gameMode, hardcoreMode, dimension,
                   │                     difficulty, maxPlayers,
                   │                     worldType, reducedDebugInfo)
                   │   S05PacketSpawnPosition         (world spawn)
                   │   S39PacketPlayerAbilities       (fly/invuln state)
                   │   S08PacketPlayerPosLook         (initial teleport)
                   │   S26PacketMapChunkBulk          (visible chunks)
                   │
                   │ Client replies:
                   │   C15PacketClientSettings(lang, viewDist, chatVis,
                   │                            chatColors, skinFlags)
                   │   C17PacketCustomPayload("MC|Brand", "vanilla")
                   │   (vanilla never sends C16 PERFORM_RESPAWN as a join-ready
                   │    signal; it is a post-death respawn request)
                   ▼
              ── steady state ──

The teaching point: state transitions are driven by specific packets, not by timestamps or timeouts. If you ever see a packet ID that "doesn't exist", you're probably looking at it in the wrong state's lookup table. EnumConnectionState.PLAY registry (100 PLAY-state packets: 74 CLIENTBOUND + 26 SERVERBOUND) is the lookup you want — directionMaps is private, use getPacket(direction, id) / getPacketId(direction, packet).

The teaching point: the client is mostly a thin shell that mirrors server state and predicts a little ahead. This is why a server can "rubber-band" your position with S08 and your client must teleport back — the server is the source of truth.

5. The C03PacketPlayer family — choosing which subclass to send

Every tick EntityPlayerSP.onUpdateWalkingPlayer() decides which of four position packets to send. The decision tree:

   onUpdateWalkingPlayer() — runs once per tick, ~20 Hz

         ┌──────────────────────────────────────────┐
         │  Compute delta from last reported state: │
         │                                          │
         │    dx     = posX - lastReportedPosX      │
         │    dy     = getEntityBoundingBox().minY - lastReportedPosY   │
         │    dz     = posZ - lastReportedPosZ      │
         │    dyaw   = yaw   - lastReportedYaw      │
         │    dpitch = pitch - lastReportedPitch    │
         │                                          │
         │    moved   = (dx²+dy²+dz² > 9.0E-4)      │
         │            ││ (positionUpdateTicks ≥ 20) │
         │    rotated = (dyaw ≠ 0 ││ dpitch ≠ 0)    │
         └────────────────────┬─────────────────────┘
                              │
              ┌───────────────┼───────────────┐
              │               │               │
              ▼               ▼               ▼
        moved=true       moved=true       moved=false
        rotated=true     rotated=false    rotated=true
              │               │               │
              ▼               ▼               ▼
       C06PosLook       C04Position      C05Look
       (x,y,z,yaw,      (x,y,z,         (yaw,pitch,
        pitch,onGr)      onGr)           onGr)
                              │
                              │
                              ▼
                    moved=false, rotated=false
                              │
                              ▼
                       C03Player(onGround)
                       (the "still here" ping)


   Even when idle, every 20 ticks (1 second) positionUpdateTicks
   forces moved=true so a full position is re-sent.

   When riding (ridingEntity != null), the rules change:
     - Send C06 with x=motionX, y=-999.0, z=motionZ as a sentinel
     - Always treat this as "no position update" for delta tracking

The teaching point: there is no single "send position" packet — there are four, and which one goes out depends on what changed. The shared base C03PacketPlayer declares protected x, y, z, yaw, pitch, onGround, moving, rotating but serializes only onGround; subclasses add fields. The Y coordinate sent is always getEntityBoundingBox().minY (your feet), never posY. The 9.0E-4 threshold corresponds to a 0.03-block radius — moves smaller than that are treated as "not moving" and won't trigger a C04 unless the 20-tick forcing fires.

6. Sending a packet — the call graph

This is the path a packet takes from the moment your code constructs it to the moment Netty hands the bytes to the OS socket.

   Your code calls one of:

        mc.thePlayer.sendQueue.addToSendQueue(packet)
        mc.getNetHandler().addToSendQueue(packet)
                          │
                          ▼
        ┌─────────────────────────────────┐
        │   NetHandlerPlayClient          │
        │     .addToSendQueue(Packet p)   │
        └─────────────────┬───────────────┘
                          │
                          ▼
        ┌─────────────────────────────────┐
        │   NetworkManager                │
        │     .sendPacket(Packet p)       │
        └─────────────────┬───────────────┘
                          │
              ┌───────────┴───────────┐
              │ Channel in event-     │
              │ loop thread?          │
              └───────────┬───────────┘
                          │
                ┌─────────┴─────────┐
                │                   │
              YES                  NO
                │                   │
                ▼                   ▼
     dispatchPacket(p, null)   queue into outboundPacketsQueue
                │              (pre-channel-open buffer only),
                │              schedule flushOutboundQueue()
                │              on event loop, return
                │              (open channel: writeAndFlush on event loop)
                ▼
        ┌─────────────────────────────────┐
        │   Netty pipeline:               │
        │                                 │
        │   MessageSerializer.encode() (+ MessageSerializer2 framing)   │
        │     ↓                           │
        │   ByteBuf with VarInt ID +      │
        │   p.writePacketData(buffer)     │
        │     ↓                           │
        │   NettyCompressionEncoder       │
        │   (if compression enabled)      │
        │     ↓                           │
        │   MessageSerializer2     │
        │   (prepends length VarInt)      │
        │     ↓                           │
        │   socket write                  │
        └─────────────────────────────────┘

The teaching point: sendPacket is thread-safe — you can call it from any thread. If you're not on the Netty event loop and the channel is not yet open, the manager buffers your packet in outboundPacketsQueue and schedules a flush; once open, sends use writeAndFlush on the event loop. Don't try to be clever with threading; just call addToSendQueue from wherever you are.

7. Receiving a packet — the call graph and the thread hand-off

Inbound is more interesting because it involves a thread switch. The Netty thread reads bytes; the main game thread does the work. The mechanism is PacketThreadUtil.checkThreadAndEnqueue:

   ┌───────────────────────────────────────────────────────┐
   │   Netty I/O thread                                    │
   │                                                       │
   │   Bytes arrive on socket                              │
   │              │                                        │
   │              ▼                                        │
   │   MessageDeserializer2 reads length VarInt (framing)       │
   │              │                                        │
   │              ▼                                        │
   │   NettyCompressionDecoder (if compressed)             │
   │              │                                        │
   │              ▼                                        │
   │   MessageDeserializer.decode() reads packet ID VarInt,      │
   │   looks up class in EnumConnectionState's registry,   │
   │   instantiates packet, calls readPacketData(buffer)   │
   │              │                                        │
   │              ▼                                        │
   │   NetworkManager.channelRead0(ctx, packet)            │
   │              │                                        │
   │              ▼                                        │
   │   packet.processPacket(netHandler)                    │
   │              │                                        │
   │              ▼                                        │
   │   netHandler.handleXxx(packet) called                 │
   │              │                                        │
   │              ▼                                        │
   │   First line of handleXxx is usually:                 │
   │     PacketThreadUtil.checkThreadAndEnqueue(           │
   │         this, packet, mc);                            │
   │              │                                        │
   │              ▼                                        │
   │   If we're NOT on the Minecraft thread:               │
   │     - Schedule a Runnable on mc that will             │
   │       re-call packet.processPacket(handler)           │
   │       (which dispatches to handleXxx)                 │
   │     - Throw ThreadQuickExitException                  │
   │     - Netty thread unwinds and is done                │
   │                                                       │
   └───────────────────────┬───────────────────────────────┘
                           │
                           │  Runnable enqueued on
                           │  Minecraft thread's
                           │  scheduledTasks queue
                           ▼
   ┌───────────────────────────────────────────────────────┐
   │   Minecraft main thread (Runnable from runGameLoop)   │
   │                                                       │
   │   Calls mc.scheduledTasks polling loop (in runGameLoop) │
   │              │                                        │
   │              ▼                                        │
   │   Runnable fires → packet.processPacket(handler) called AGAIN (dispatches to handleXxx)     │
   │              │                                        │
   │              ▼                                        │
   │   This time checkThreadAndEnqueue is a no-op,         │
   │   so handleXxx proceeds past it                       │
   │              │                                        │
   │              ▼                                        │
   │   handleXxx mutates mc.theWorld, mc.thePlayer,        │
   │   spawns entities, processes inventory, ...           │
   │   (safe — we're on the main thread)                   │
   └───────────────────────────────────────────────────────┘

The teaching point: every handleXxx method is *called twice* — first on the Netty thread (where it bails out immediately) and then on the main thread (where it does real work). When you read a handler's body, you can assume the world and player are safe to touch.

If you ever need to do work on the main thread from elsewhere (a custom thread, a callback, anything), use mc.addScheduledTask(Runnable). Never just touch mc.theWorld from a thread you don't control.

8. The Minecraft.runTick / render loop

The outer loop drives everything. runGameLoop runs as fast as the FPS allows. Inside it, runTick runs at 20 Hz (more if behind), and rendering runs at FPS Hz with partialTicks interpolation between the most recent two ticks.

11. The collision pipeline

When you call entity.moveEntity(dx, dy, dz), this is what happens. Understanding this is essential for anything related to movement, AABB queries, or step-up.

   Entity.moveEntity(dx, dy, dz)
            │
            ▼
   ┌────────────────────────────────────────────────────────┐
   │                                                        │
   │  1. Save the original dx, dy, dz for sneak detection   │
   │                                                        │
   │  2. Sneak-edge logic (player only, on the ground):     │
   │     Probe with getCollidingBoundingBoxes in three     │
   │     separate offset loops: (dx,-1,0), (0,-1,dz),      │
   │     (dx,-1,dz). Shrink dx, dz until you can't fall off│
   │     ┌────────────────────────────────────────────┐     │
   │     │ This is the "sneak doesn't let you fall    │     │
   │     │ off the edge" feature. It works by         │     │
   │     │ repeatedly checking whether the next       │     │
   │     │ position would have ground below it; if    │     │
   │     │ not, dx (or dz) is set to 0.               │     │
   │     └────────────────────────────────────────────┘     │
   │                                                        │
   │  3. Query collision boxes intersecting the swept AABB: │
   │     List<AxisAlignedBB> boxes =                        │
   │       world.getCollidingBoundingBoxes(                 │
   │         this, getEntityBoundingBox().addCoord(dx,dy,dz))│
   │     (field is private boundingBox, not bb)            │
   │                                                        │
   │  4. Resolve Y first (gravity & ceiling):               │
   │     for (AABB other : boxes)                           │
   │       dy = other.calculateYOffset(getEntityBoundingBox(), dy);        │
   │     setEntityBoundingBox(getEntityBoundingBox().offset(0, dy, 0));                │
   │     if (dy was reduced)                                │
   │       (we hit a floor or ceiling — onGround only if strict dy<0 later)   │
   │                                                        │
   │  5. Resolve X:                                         │
   │     for (AABB other : boxes)                           │
   │       dx = other.calculateXOffset(getEntityBoundingBox(), dx);        │
   │     setEntityBoundingBox(getEntityBoundingBox().offset(dx, 0, 0));                │
   │                                                        │
   │  6. Resolve Z:                                         │
   │     for (AABB other : boxes)                           │
   │       dz = other.calculateZOffset(getEntityBoundingBox(), dz);        │
   │     setEntityBoundingBox(getEntityBoundingBox().offset(0, 0, dz));                │
   │                                                        │
   │  7. Step-up handling (if we hit a wall horizontally    │
   │     AND there's a block ≤ stepHeight tall in the way): │
   │     Try the move again at higher Y. If it works,       │
   │     accept the higher result. Otherwise revert.        │
   │     ┌────────────────────────────────────────────┐     │
   │     │ This is why you "auto-step" up 0.5–0.6     │     │
   │     │ block stairs without jumping. stepHeight   │     │
   │     │ is 0.6 for the player, 1.0 for horses.     │     │
   │     └────────────────────────────────────────────┘     │
   │                                                        │
   │  8. Update fields:                                     │
   │     posX, posY, posZ ← bb center / minY                │
   │     isCollidedHorizontally ← (dx or dz reduced)        │
   │     isCollidedVertically ← (dy reduced)                │
   │     isCollided ← either of the above                   │
   │     onGround ← (isCollidedVertically AND original dy < 0.0D, strict <)        │
   │     fallDistance accumulates                           │
   │     doBlockCollisions() — fire onEntityCollidedWithBlock│
   └────────────────────────────────────────────────────────┘

The teaching point: collision resolution is axis-separated. Y is resolved first (so you land on a floor before checking horizontal motion), then X, then Z. Each axis uses the relevant calculateXOffset / calculateYOffset / calculateZOffset helper on AxisAlignedBB. Step-up is a fallback that retries the failed horizontal move at a higher Y.

A subtle consequence: an entity's onGround state is set *during* moveEntity, not on a separate query. So if you read entity.onGround immediately after assigning motion but before calling moveEntity, you get last tick's value.

12. The raytrace pipeline (getMouseOver / objectMouseOver)

Every tick, the crosshair re-raytraces the world to figure out what you're pointing at. This populates mc.objectMouseOver (a MovingObjectPosition) and entityRenderer.pointedEntity.

   EntityRenderer.getMouseOver(float partialTicks)
            │
            ▼
   ┌────────────────────────────────────────────────────────┐
   │                                                        │
   │  Entity viewEntity = mc.getRenderViewEntity();         │
   │  Vec3 eyes = viewEntity.getPositionEyes(partialTicks); │
   │  Vec3 look = viewEntity.getLook(partialTicks);         │
   │  double reach = playerController.getBlockReachDistance(│
   │                  ); // 4.5 surv, 5.0 creat (6.0 = extendedReach entity distance, creative)             │
   │  Vec3 endPoint = eyes.addVector(look.x*reach,          │
   │                                  look.y*reach,         │
   │                                  look.z*reach);        │
   │                                                        │
   │  // Block ray-trace (delegates to Entity.rayTrace):    │
   │  mc.objectMouseOver = entity.rayTrace(reach, partialTicks)│
   │      (which calls theWorld.rayTraceBlocks internally); │
   │                                                        │
   │  // Now look for an entity in front of that block.     │
   │  // Build an AABB containing the line eyes→endPoint    │
   │  // and query every entity intersecting it.            │
   │  AxisAlignedBB sweep = viewEntity.getEntityBoundingBox │
   │      ().addCoord(look.x*reach,                         │
   │                  look.y*reach,                         │
   │                  look.z*reach).expand(1,1,1);          │
   │                                                        │
   │  List<Entity> candidates = mc.theWorld.getEntitiesIn- │
   │      AABBexcluding(entity, sweep, predicate);          │
   │                                                        │
   │  // For each candidate, expand its bb by its           │
   │  // collisionBorderSize and call calculateIntercept    │
   │  // on the eyes→endPoint line.                         │
   │                                                        │
   │  // Pick the closest hit that's also closer than       │
   │  // the block hit (if any).                            │
   │                                                        │
   │  // If an entity was hit, replace objectMouseOver      │
   │  // with a MovingObjectPosition built from that entity │
   │  // (and set pointedEntity).                           │
   │                                                        │
   └────────────────────────────────────────────────────────┘

   After getMouseOver, mc.objectMouseOver is one of:
     - typeOfHit = MISS     → nothing in range
     - typeOfHit = BLOCK    → blockPos and sideHit are valid
     - typeOfHit = ENTITY   → entityHit is valid; hitVec is the
                              point on the entity's hitbox that
                              was hit

The teaching point: this method is the bridge between "where the camera is pointing" and "what game object is the player about to interact with". Every left-click and right-click reads objectMouseOver to decide what to do. The raytrace is cheap — it's done every tick. You can call entityRenderer.getMouseOver(1.0F) at any time to force a re-raytrace.

World.rayTraceBlocks has three overloads — the 5-arg version is what's used here. The stopOnLiquid parameter controls whether to stop on water/lava; the ignoreBlockWithoutBoundingBox flag affects how non-cube blocks (signs, torches) are handled; the returnLastUncollidableBlock flag is used to fall back to the last partially-collided block if nothing else hits.

13. Coordinate system

                    ↑ +Y (up)
                    │
                    │
                    │
                    │     ↗ -Z (north)
                    │   ↗
                    │ ↗
   -X (west) ←──────●──────→ +X (east)
                  ↙ │
                ↙   │
              ↙     │
            +Z      │
        (south)     ↓ -Y (down)
                    
   Wait — let me redraw that correctly:

                    ↑ +Y (up)
                    │
                    │   ↗ +X (east, sunrise side)
                    │ ↗
                    ●─────────→ ... (this gets messy in 2D)
                  ↙
                ↙
              +Z (south)

A cleaner coordinate reference, as text:

   Axes:
     +X = east   (toward sunrise)
     -X = west
     +Y = up
     -Y = down
     +Z = south
     -Z = north  (sunset is west, i.e. -X)

   Yaw (rotationYaw):
     0°    or  ±360°  →  facing +Z  (south)
     90°               →  facing -X  (west)
     180°  or -180°    →  facing -Z  (north)
     -90°  or 270°     →  facing +X  (east)
     Yaw INCREASES clockwise when looking down at the player.

   Pitch (rotationPitch):
     -90°  →  looking straight up
       0°  →  looking at horizon
     +90°  →  looking straight down

   The "look vector" from getLook(partialTicks) is computed as:
     pitch_rad = pitch * π / 180
     yaw_rad   = -yaw  * π / 180 - π
     x =  sin(yaw_rad) * -cos(pitch_rad)
     y =  -sin(pitch_rad)
     z =  cos(yaw_rad) * -cos(pitch_rad)

   The boundingBox is anchored differently from posX/posY/posZ:
     posX, posZ   = horizontal center of entity
     posY         = bottom of entity hitbox (== boundingBox.minY for most)
     bb.minX      = posX - width/2
     bb.maxX      = posX + width/2
     boundingBox.minY = posY                    ← what C03/C04/C06 sends
     bb.maxY      = posY + height
     bb.minZ      = posZ - width/2
     bb.maxZ      = posZ + width/2

   Eye position (used for raytracing):
     eyeX = posX
     eyeY = posY + getEyeHeight()    // 1.62 for player standing
     eyeZ = posZ

The teaching point: yaw 0 points south, not north. This trips people up constantly. Also: the wire protocol always sends getEntityBoundingBox().minY, never posY, even though for most entities they're equal — the safe habit is to use getEntityBoundingBox().minY when building position packets.

14. Friction and movement constants

   Per-tick velocity decay in EntityLivingBase.moveEntityWithHeading:

   ┌─────────────────────────────────────────────────────────────┐
   │                                                             │
   │   On land (most of the time):                               │
   │     motionX *= 0.91 * groundBlock.slipperiness              │
   │     motionZ *= 0.91 * groundBlock.slipperiness              │
   │     motionY = (motionY - 0.08) * 0.98     ← gravity         │
   │                                                             │
   │     groundBlock.slipperiness defaults:                      │
   │       most blocks ............ 0.6                          │
   │       slime block ............ 0.8                          │
   │       ice / packed ice ....... 0.98                         │
   │       blue ice (1.13+, n/a 1.8)                             │
   │                                                             │
   │     So normal ground friction is 0.91 * 0.6 = 0.546         │
   │     Ice friction is             0.91 * 0.98 = 0.8918        │
   │                                                             │
   │   In air (off ground):                                      │
   │     motionX *= 0.91                                         │
   │     motionZ *= 0.91                                         │
   │     motionY = (motionY - 0.08) * 0.98                       │
   │                                                             │
   │   In water:                                                 │
   │     motionX, Z *= f1 (0.8 base; up to 0.546 at max        │
   │                  Depth Strider: f1 += (0.546-f1)*lvl/3)  │
   │     motionY -= 0.02 (lower gravity in water)                │
   │                                                             │
   │   In lava:                                                  │
   │     motionX, Y, Z *= 0.5                                    │
   │                                                             │
   │   moveFlying(strafe, forward, friction):                    │
   │     float dist² = strafe² + forward²                        │
   │     if (dist² < 0.0001) return     // no input              │
   │     normalize, scale by friction                            │
   │     yaw_rad = rotationYaw * π/180                           │
   │     motionX += -sin(yaw_rad) * normalizedStrafe             │
   │                + cos(yaw_rad) * normalizedForward           │
   │     motionZ +=  cos(yaw_rad) * normalizedStrafe             │
   │                + sin(yaw_rad) * normalizedForward           │
   │                                                             │
   │   The friction passed to moveFlying:                        │
   │     On ground: getAIMoveSpeed() * (0.16277136 / f4³)       │
   │       (landMovementFactor); with slipperiness=0.6 this     │
   │       evaluates to about 0.1 — the magic walk speed         │
   │     In air:    0.02 (set as jumpMovementFactor)             │
   │     In water:  0.02 (×depth-strider modifier)               │
   │                                                             │
   └─────────────────────────────────────────────────────────────┘

   Vertical:
     Base jump impulse:  motionY = 0.42  (getJumpUpwardsMotion)
     Jump-boost potion:  motionY += (amplifier + 1) * 0.1
     Sprint-jump adds horizontal motion:
       motionX -= sin(yaw) * 0.2
       motionZ += cos(yaw) * 0.2
     Gravity:            motionY -= 0.08
     Air drag on Y:      motionY *= 0.98

   Terminal velocities (approx, after gravity converges):
     Free-fall:  ≈ -3.92 blocks/tick (≈ -78.4 m/s)
                 capped by S12 anyway at 3.9

The teaching point: friction is multiplicative each tick, and the value depends on what you're standing on. The 0.91 ground constant and the 0.6 default slipperiness produce the familiar ~0.546 horizontal decay per tick. Ice's 0.98 slipperiness produces the slippery feel you know from gameplay.

The container's transferStackInSlot(player, slotIndex) is the shift-click handler that knows which target range to move a stack to.

17. Mental shortcuts for navigating new code

When you encounter a name in the codebase you don't recognize, the structure usually tells you where it lives:

   Starts with C##   →  Client-to-server packet
                        net.minecraft.network.play.client.<name>

   Starts with S##   →  Server-to-client packet
                        net.minecraft.network.play.server.<name>

   Starts with Gui   →  GUI screen or HUD element
                        net.minecraft.client.gui.* (or subpackages)

   Starts with Container  →  Inventory container
                             net.minecraft.inventory.*

   Starts with Entity     →  net.minecraft.entity.* (look for the
                             matching subpackage: monster, passive,
                             item, projectile, ...)

   Starts with Block      →  net.minecraft.block.*

   Starts with Item       →  net.minecraft.item.*

   Starts with Render     →  net.minecraft.client.renderer.entity.*
                             (or the entity's own renderer file)

   Starts with Model      →  net.minecraft.client.model.*

   Starts with TileEntity →  net.minecraft.tileentity.*

   Starts with NBT        →  net.minecraft.nbt.*

   Starts with Math/Vec/  →  net.minecraft.util.*
   BlockPos/AABB/Enum
   Facing/etc.

   Ends with Packet       →  Look for the packet ID prefix (C##/S##)

   Ends with Handler      →  An INetHandler implementation
                             (NetHandlerPlayClient, NetHandlerLoginClient)

   Ends with Provider     →  IChunkProvider / ISaveFormat / similar

The teaching point: vanilla naming is consistent enough that you can usually guess a class's location from its name alone. When grepping, prefer the full class name over partial substrings — EntityPlayerSP is unique while "Player" matches hundreds of files.

Final note on usage

When pasting this into AI context along with the codebase map, the two files complement each other:

The map (MCP_1_8_9_CODEBASE_MAP.md) is the *lexicon* — it tells the AI what symbols exist and what their signatures are. Without it, the AI will invent method names that don't exist or guess wrong parameter orders.

This diagram file is the *grammar* — it tells the AI how those symbols compose. Without it, the AI knows the parts but doesn't know which orders are correct, what's allowed in which thread, or which axis is which.

Used together they let the AI write code that compiles against vanilla, threads correctly, and produces packets the server will accept. A new task description, prepended with both files, should give an AI enough context to write substantive contributions without further searching the codebase.
