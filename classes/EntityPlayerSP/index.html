Client player entity: emits C03 movement, C0A swings, C0B actions and C0C input every tick from onUpdateWalkingPlayer.

Deep Analysis

Client-side local player (extends AbstractClientPlayer). Predicts movement, health, input each tick. Tick flow: onUpdate (riding vs walk) -> onUpdateWalkingPlayer + onLivingUpdate (sprint, fly, portal). Bridges Minecraft, MovementInput and NetHandlerPlayClient sendQueue for all C packets.

Key Methods — In Depth (9)

onUpdate

Per-tick client update; delegates to walk or riding branch.

onUpdate runs every client tick for the local player and first gates on worldObj.isBlockLoaded at BlockPos(posX, 0, posZ) so no packets are sent from unloaded areas. It calls super.onUpdate first to run entity physics, collision, and position integration before any networking decision. If isRiding is true it takes the vehicle branch and does not call onUpdateWalkingPlayer at all. In the riding branch it queues a C03 C05PacketPlayerLook with current rotationYaw, rotationPitch and onGround every tick because the server drives vehicle position. It also queues a C0CPacketInput with moveStrafing, moveForward, movementInput.jump and movementInput.sneak so the server can steer the ridden horse, boat, pig or minecart. If not riding it delegates to onUpdateWalkingPlayer which owns the on-foot C03 family and C0B throttling. This split prevents double-sending position while riding and explains why ground-spoof and blink cheats hook the on-foot path. The receiver NetHandlerPlayServer validates look and input and applies them to the riding entity rather than the player.

    public void onUpdate()
    {
        if (this.worldObj.isBlockLoaded(new BlockPos(this.posX, 0.0D, this.posZ)))
        {
            super.onUpdate();

            if (this.isRiding())
            {
                this.sendQueue.addToSendQueue(new C03PacketPlayer.C05PacketPlayerLook(this.rotationYaw, this.rotationPitch, this.onGround));
                this.sendQueue.addToSendQueue(new C0CPacketInput(this.moveStrafing, this.moveForward, this.movementInput.jump, this.movementInput.sneak));
            }
            else
            {
                this.onUpdateWalkingPlayer();
            }
        }
    }

The isBlockLoaded guard stops updates when the player column is unloaded, preventing desync packets from void or unloaded chunks. super.onUpdate runs shared EntityLivingBase physics before networking so sent values reflect the new tick. The isRiding branch constructs C05PacketPlayerLook from live yaw, pitch and onGround, telling the server where the rider looks while the vehicle moves. The next line constructs C0CPacketInput from strafe, forward, jump and sneak, which is the only channel for steering ridden entities. The else calls onUpdateWalkingPlayer for the on-foot C03 and C0B logic, so suppressing either queue call creates a blink-like stall that the server later corrects.

onUpdateWalkingPlayer

Sends sprint/sneak deltas and throttled position/look updates.

onUpdateWalkingPlayer compares live isSprinting against cached serverSprintState and live isSneaking against serverSneakState, sending C0BPacketEntityAction START or STOP only on a flip to save bandwidth. It then gates all position traffic on isCurrentViewEntity so only the camera entity transmits, ignoring other render-view switches. It computes d0, d1 from posX and boundingBox.minY minus lastReported, d2 from posZ, and d3, d4 from yaw and pitch deltas. It sets flag2 when squared positional delta exceeds 9.0E-4D or positionUpdateTicks reaches 20, forcing a keep-alive at least once per second. It sets flag3 when yaw or pitch changed at all, then picks C06 pos-look when both moved, C04 position when only moved, C05 look when only rotated, else bare C03 onGround keep-alive. When ridingEntity is non-null it sends a special C06 with motionX, -999.0D Y and motionZ as a stall marker and forces flag2 false. Finally it increments positionUpdateTicks, and on flag2 or flag3 copies current pos and angles into lastReported fields and zeroes the tick counter, which is the state blink freezes.

onLivingUpdate

Handles sprint timers, fly toggle, horse jump, portal, push-out.

onLivingUpdate runs before physics each tick and first decrements sprintingTicksLeft, sprintToggleTimer and timeUntilPortal so sprint expiry, double-tap windows and portal cooldowns age correctly. It handles double-tap-W sprint by setting sprintToggleTimer to 7 on first tap and calling setSprinting true on second tap within the window, gated on food above 6, allowFlying, onGround and not using an item or blinded. It handles the sprint key, sprint cancel on slowdown or collision, and slows movementInput by 0.2 while using an item. For flight it forces isFlying true in spectator mode with a C13 send, and detects double-space via flyToggleTimer 7 to toggle capabilities.isFlying and call sendPlayerAbilities which emits C13PacketPlayerAbilities. It manages horse jump charging with horseJumpPowerCounter from -10 through 10, sending C0B RIDING_JUMP on release and computing power up to 0.8 plus curve, plus horse inventory via C0B OPEN_INVENTORY. On landing while flying in non-spectator it clears isFlying and re-sends C13, and it accumulates timeInPortal toward 1.0 for dimension travel. The server NetHandlerPlayServer re-validates abilities and jump power, so forged C13 or C0B values are the classic fly and horse-jump cheat vectors.

sendChatMessage

Forwards user chat to server.

sendChatMessage takes the raw string from the chat GUI or command line with no client-side filtering, length splitting or command parsing. It wraps the string verbatim in a new C01PacketChatMessage and adds it to sendQueue via addToSendQueue for TCP flush. It does not distinguish slash commands from public chat, leaving that decision to NetHandlerPlayServer on the receiving side. The server then routes slash-prefixed text to the command dispatcher and other text to broadcast with spam and visibility checks. Because the client sends the full string, server plugins see the exact typed content including formatting codes. Dropping or mutating this packet silences the player, while flooding it is chat spam. No other packet is emitted here, so chat has no movement or inventory side effects.

swingItem

Local arm swing plus server animation notify.

swingItem first calls super.swingItem to run the client-side arm swing timer and render animation immediately without waiting for the server. It then constructs an empty C0APacketAnimation with no entity ID or hand argument, because 1.8.9 has a single swing type inferred from the sender. It queues that packet on sendQueue so the server and then other clients via S0B animation can mirror the motion. It is called for attacks, block hits and item use visuals, decoupling visual feedback from damage outcome. The server uses the C0A arrival time as a heuristic alongside C02 attack and C07 dig packets for anti-cheat timing. Suppressing C0A while still attacking creates silent swings that look like no-animation kill-aura. The receiver NetHandlerPlayServer broadcasts the swing to trackers without changing inventory or health.

C0A
dropOneItem

Requests server item drop; no client spawn.

dropOneItem maps the boolean dropAll from the Q key handler to a C07PacketPlayerDigging Action enum, choosing DROP_ALL_ITEMS when true and DROP_ITEM for a single item. It constructs the packet with BlockPos.ORIGIN and EnumFacing.DOWN as dummy position and facing values because drops carry no block target. It queues the packet on sendQueue and returns null without spawning any EntityItem client-side, keeping inventory authoritative. The server NetHandlerPlayServer interprets the action, splits or clears the held stack, and spawns the EntityItem itself with pickup delay. Holding Ctrl-Q drives the dropAll path to empty the stack, while tapping Q drops one. Forging this C07 with modified actions is how drop-spam or inventory-desync exploits attempt to duplicate items, but the server re-validates the held stack. No S packet is produced locally here.

closeScreen

Notifies server container close.

closeScreen reads openContainer.windowId as the server-assigned container ID so the close refers to the exact chest, furnace or custom GUI. It constructs C0DPacketCloseWindow with that ID and queues it on sendQueue to tell the server the client dismissed the screen. It then calls closeScreenAndDropStack which clears the cursor ItemStack via inventory.setItemStack null, calls super.closeScreen and calls mc.displayGuiScreen null to remove the GUI. The server NetHandlerPlayServer closes its Container on C0D, cancels pending slot transactions and may drop or retain the cursor stack. Sending a wrong windowId desyncs containers and can leave ghost items until the next S2E or S30 resync. This is a pure teardown with no item movement packet, so dupes that race C0E clicks against C0D rely on server ordering here.

sendPlayerAbilities

Syncs capabilities (fly, creative) to server.

sendPlayerAbilities wraps the live this.capabilities object, including isFlying, allowFlying, isCreativeMode, flySpeed and walkSpeed, into a new C13PacketPlayerAbilities. It queues that snapshot on sendQueue with no extra validation, trusting the caller in onLivingUpdate to have flipped the flags correctly for spectator, double-space or landing. The server compares the received flags against the authoritative GameType and op state, ignoring or kicking on illegal fly enable. Because the whole capabilities struct is sent, stale walkSpeed or flySpeed values can also leak to the server if mods mutate them. respawnPlayer

Requests respawn after death screen.

respawnPlayer is bound to the death-screen respawn button and takes no position or health arguments because the server owns the spawn point. It constructs C16PacketClientStatus with EnumState.PERFORM_RESPAWN, the dedicated respawn enum distinct from OPEN_INVENTORY statistics states. It queues that packet on sendQueue so NetHandlerPlayServer can trigger ServerConfigurationManager respawn, clearing death, resetting health and food, and teleporting to spawn or bed. The client does not move itself or heal locally here, waiting for S07 respawn, S06 health and S21 chunk packets to rebuild state. Pressing the button twice queues duplicate C16s that the server idempotently ignores if already alive. Blocking this packet leaves the player on the death screen indefinitely, while forging it while alive is ignored by the server state check.
