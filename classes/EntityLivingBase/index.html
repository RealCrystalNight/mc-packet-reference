Deep Analysis

Abstract base for all living entities in 1.8.9, owning health, attributes, combat, potions and equipment state. Server-side logic broadcasts visual effects through WorldServer EntityTracker while persistent state syncs via DataWatcher slots. Client mirrors hurt, death, swing, pickup and potion color through status, animation and metadata packets.

swingItem

Start arm-swing animation and broadcast to trackers

swingItem starts a client-visible arm swing on the server and broadcasts it to all tracking clients. It first checks isSwingInProgress and swingProgressInt against half of getArmSwingAnimationEnd to avoid restarting a swing mid-stroke unless expired or invalid. On start it sets swingProgressInt to -1 and isSwingInProgress to true so updateArmSwingProgress will advance it next tick. It then guards with worldObj instanceof WorldServer to ensure this only runs on the logical server. It obtains the EntityTracker from WorldServer and calls sendToAllTrackingEntity with new S0BPacketAnimation(this, 0) where type 0 means swing arm. Receivers including the attacker itself if tracked and nearby players get S0B and play the swing animation without changing inventory or health. This keeps swings visual-only while combat damage is handled separately by attack logic. No DataWatcher change is made here because animation is transient.

    public void swingItem()
    {
        if (!this.isSwingInProgress || this.swingProgressInt >= this.getArmSwingAnimationEnd() / 2 || this.swingProgressInt < 0)
        {
            this.swingProgressInt = -1;
            this.isSwingInProgress = true;

            if (this.worldObj instanceof WorldServer)
            {
                ((WorldServer)this.worldObj).getEntityTracker().sendToAllTrackingEntity(this, new S0BPacketAnimation(this, 0));
            }
        }
    }

The guard condition prevents overlapping swings by allowing restart only when idle, past half duration, or with invalid counter. Resetting swingProgressInt to -1 and setting isSwingInProgress starts the animation timer consumed by updateArmSwingProgress. The instanceof WorldServer check confines packet sending to the logical server and avoids client double-send. sendToAllTrackingEntity forwards the new S0BPacketAnimation with entity ID and type 0 to every tracking client. Clients then render the arm swing while server logic continues independently.

onItemPickup

Broadcast pickup animation when collecting item, arrow or XP orb

onItemPickup broadcasts the pickup beam animation when a living entity collects an item, arrow, or XP orb. It first rejects dead pickup entities with isDead and rejects client worlds with worldObj.isRemote so only the server emits packets. It fetches EntityTracker from the WorldServer to find all clients tracking the picked-up entity. For EntityItem it sends S0DPacketCollectItem with args picked-up entity ID and collector entity ID so clients can fly the item to the collector. It repeats the same S0D send for EntityArrow and for EntityXPOrb using identical constructor arguments. Receivers hide or remove the ground entity and render it moving into the collector inventory or body. No inventory mutation happens here; actual stack transfer is done by caller logic before or after this visual. This separation keeps visuals in sync even if stack handling differs by subclass.

onUpdate

Per-tick equipment diff sync and arrow-count decay

onUpdate runs every tick to decay stuck arrows and sync changed equipment to tracking clients. It calls super.onUpdate first for base entity movement and then gates server-only work with !worldObj.isRemote. It reads arrow count from DataWatcher slot 9 via getArrowCountInEntity and if above zero initializes arrowHitTimer to 20 times 30 minus count. It decrements arrowHitTimer each tick and calls setArrowCountInEntity with count minus one when it expires, which updates DataWatcher slot 9 for S1C metadata sync. It then loops slots 0 to 4 comparing previousEquipment cache to getEquipmentInSlot current value with ItemStack.areItemStacksEqual. On mismatch it sends S04PacketEntityEquipment with args entity ID, slot index j, and new ItemStack so clients update rendered held item and armor. It also removes old attribute modifiers and applies new ones to attributeMap to keep damage, armor, and speed correct. It caches a copy of the new stack in previousEquipment to avoid resending every tick. Every 20 ticks it resets CombatTracker to age out old damage entries.

onDeath

Handle death drops and death animation broadcast

onDeath awards score, drops loot on the server, and broadcasts the death animation. It resolves the killer via getAttackingEntity and source.getEntity, then calls addToPlayerScore if scoreValue is non-negative. It notifies the killer with onKillEntity for achievements and AI. It sets dead to true and resets CombatTracker to close the combat log. Guarded by !worldObj.isRemote it computes looting level from the killer, checks canDropLoot and doMobLoot gamerule, then calls dropFewItems, dropEquipment, and rarely addRandomDrop. These spawn EntityItem and EntityXPOrb which have their own spawn packets. Finally it calls worldObj.setEntityState with byte 3 which WorldServer forwards as S19PacketEntityStatus op 3. Tracking clients receive S19 and play death sound, rotate the corpse, and start the death timer.

handleStatusUpdate

Client-side handler for hurt and death status bytes

handleStatusUpdate runs on the client to mirror hurt and death states received as S19PacketEntityStatus. For id 2 it sets limbSwingAmount to 1.5, copies maxHurtResistantTime into hurtResistantTime, and sets hurtTime and maxHurtTime to 10 for the red flash duration. It zeroes attackedAtYaw, plays getHurtSound with randomized pitch, and calls attackEntityFrom with generic zero damage to trigger hurt hooks without changing health. For id 3 it plays getDeathSound with randomized pitch, forces DataWatcher health to zero via setHealth, and calls onDeath with generic source to start client death animation. Both branches rely on the server having sent S19 op 2 from attackEntityFrom or op 3 from onDeath via setEntityState. Unknown IDs delegate to super.handleStatusUpdate for base entity handling like spawn particles. This keeps client visuals driven entirely by server broadcasts rather than local simulation.

addPotionEffect

Add or combine active potion effect

addPotionEffect adds or combines a potion effect and schedules a metadata sync. It first calls isPotionApplicable which rejects regeneration and poison on undead creatures but allows all else. If activePotionsMap already contains the potion ID it calls combine on the existing PotionEffect to merge duration and amplifier, then calls onChangedPotionEffect with reapply true to refresh attribute modifiers. If new it inserts the effect into activePotionsMap and calls onNewPotionEffect to apply attribute modifiers to attributeMap. Both paths set potionsNeedUpdate to true so updatePotionEffects will recompute DataWatcher slots 7 potion color and 8 ambient flag. Those DataWatcher changes are sent by EntityTracker as S1C reflect S1CPacketEntityMetadata to tracking clients. Clients then render particles, tint, and invisibility without receiving a dedicated potion packet. Duration refresh packets at 600-tick intervals also flow through this dirty path.

    public void addPotionEffect(PotionEffect potioneffectIn)
    {
        if (this.isPotionApplicable(potioneffectIn))
        {
            if (this.activePotionsMap.containsKey(Integer.valueOf(potioneffectIn.getPotionID())))
            {

            else

            }
        }

The isPotionApplicable guard filters invalid undead heals and poisons before mutation. The else branch inserts the new mapping and calls onNewPotionEffect to apply modifiers once. Both set potionsNeedUpdate so the next tick pushes DataWatcher slots 7 and 8 via S1C metadata.

removePotionEffect

Remove potion effect and refresh metadata

removePotionEffect removes a server-side potion and triggers attribute cleanup and resync. It removes the entry from activePotionsMap by integer potion ID and captures the old PotionEffect. If non-null it calls onFinishedPotionEffect which sets potionsNeedUpdate true and on the server removes attribute modifiers from attributeMap via Potion.potionTypes. The dirty flag causes updatePotionEffects to call updatePotionMetadata next tick, recomputing liquid color and ambient flag or clearing slots 7 and 8 if empty. EntityTracker then sends the changed DataWatcher entries as S1C S1CPacketEntityMetadata to all tracking clients. Receivers stop rendering that effect tint and particles and update invisibility. This differs from removePotionEffectClient which only edits the client map without attribute work. If the ID was absent no packet or modifier change occurs.

updatePotionMetadata

Recompute potion color and invisibility flags

updatePotionMetadata recomputes potion-driven DataWatcher state for S1C sync. If activePotionsMap is empty it calls resetPotionEffectMetadata which writes 0 to slot 7 color and 0 to slot 8 ambient, then calls setInvisible false to clear invisibility. If non-empty it calls PotionHelper.calcPotionLiquidColor over all active effects to blend the particle tint integer. It writes slot 8 with 1 if PotionHelper.getAreAmbient returns true else 0 to control ambient versus strong particles. It writes slot 7 with the blended color integer for client spell particles. It calls setInvisible based on isPotionActive for invisibility ID so armor and body render correctly. EntityTracker detects these DataWatcher changes and sends S1C S1CPacketEntityMetadata to tracking clients. Clients read slots 7, 8, and invisibility flag to render potion visuals.

Flag potion metadata for next tick sync

markPotionsDirty flags potion metadata for refresh on the next tick. It sets the private boolean potionsNeedUpdate to true without touching activePotionsMap or DataWatcher immediately.
