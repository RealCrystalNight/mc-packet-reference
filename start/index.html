Start Here: a guided reading path

New to the 1.8.9 Minecraft protocol? Follow this path in order: connection first, then login, then play-state movement, combat, inventory, world data, and entity tracking. Each step explains the concept in plain language and points at the packet and class pages to read next.

Step 1: 1. What the protocol is: the handshake comes first

Every connection starts with a single handshake packet before anything is encrypted or compressed. The client sends its protocol version (47 for 1.8.9), the hostname and port it connected to, and one number that picks what happens next: 1 means status (server list ping) and 2 means login (real gameplay). Nothing gameplay-related exists yet at this point, so there is no player, no world, and no per-tick logic. Read the handshake page to learn the wire layout and why cheat clients never touch it.

C00Handshake packet
Step 2: 2. Logging in: from username to play state

If the handshake requested state 2, the connection enters the login state machine. The client sends its username, the server answers with encryption and compression setup, and on success it sends a login-success packet and flips the connection into play state. This is also where version mismatches and bans produce disconnect packets. Read the login pages in order to see the full sequence before any movement or world data flows.

Step 3: 3. Server list ping: status without logging in

If the handshake requested state 1 instead, the connection never logs in. The client asks for server info, the server replies with its MOTD, player counts, and favicon, and then a ping and pong exchange measures latency. This is what the multiplayer server list uses, and it runs on a tiny separate handler with no player entity. Read these pages to understand the status handler before tackling the much bigger play state.

Step 4: 4. Movement: C03, S08, and EntityPlayerSP

Once in play state, movement dominates everything. Twenty times a second the client sends a C03-family packet with its position, rotation, and a single onGround bit, picking the small variant (position only, look only, both, or keep-alive) based on what changed. The server answers corrections with S08 teleports, which the client must confirm. The vanilla class that owns this loop is EntityPlayerSP, whose walking-player update picks the packet type each tick. Read the C03 and S08 pages together with the EntityPlayerSP analysis to see the full send-and-correct cycle.

Step 5: 5. Combat: attacking and interacting with entities

Combat in 1.8.9 is two packets: the client sends an interact or attack request naming an entity id, and the server resolves damage, knockback, and swing animation. Attack range, click timing, and rotation at click time are all server-checked, which is why aura and reach cheats center here. The swing animation packet is separate and carries no damage by itself. Read the interact page plus the animation and velocity follow-ups to see how a click becomes damage.

Step 6: 6. Inventory: clicks, slots, and windows

Inventory is a client-proposes, server-disposes system. The client sends click packets describing which slot and mouse button it used, and the server validates and echoes the result with set-slot and window-items packets. Opening a chest or crafting table starts with an open-window packet and ends with a close-window packet, each carrying the window id that ties clicks to the right container. Desyncs here cause ghost items, which is why dupe research focuses on click-versus-close ordering. Read the click page first, then the server echo pages.

Step 7: 7. World data: chunks first, block edits after

The world arrives as chunk data, not as individual blocks. After login the server streams bulk chunk packets that fill in terrain, lighting, and heightmaps for each 16x16 column, then sends small block-change packets for later edits. If you fall behind or teleport far, more chunk packets rebuild the area around you. Read the chunk-data page to learn the bulk format, then the single and multi block-change pages for edits.

Step 8: 8. Entities: spawn packets and the tracker

Other players and mobs are not sent every tick. The server spawns each entity once with a spawn packet, then streams small relative-move and teleport deltas only to clients whose tracker entry says they are in range. The EntityTrackerEntry class on the server owns that per-player visibility state and decides when to send updates or destroy packets. Read the spawn and tracker pages to understand why far-away entities simply do not exist on your client.
