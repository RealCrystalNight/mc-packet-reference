Deep Dive

Role in the protocol

C01PacketEncryptionResponse is the second LOGIN-state packet and the last plaintext packet on the connection. The client generates a random AES secret, RSA-encrypts it together with the verify token from S01PacketEncryptionRequest using the server's public key, and sends both byte arrays. The server decrypts with its private key, checks the nonce, and enables symmetric AES encryption on the channel from that point on. In 1.8.9 this is where the session service join happens: the server hashes server id, public key and secret, and calls hasJoinedServer to resolve the profile UUID.

Vanilla handling

NetHandlerLoginServer.processEncryptionResponse validates the state is KEY, decrypts the verify token with the private key, and throws IllegalStateException('Invalid nonce!') unless it matches the stored field_147330_e. It then stores the secret key, enables encryption on the NetworkManager, and spawns a 'User Authenticator' thread that computes the server-id hash and calls getMinecraftSessionService().hasJoinedServer. A null profile closes with 'Failed to verify username!'; a success moves to READY_TO_ACCEPT and sends S02PacketLoginSuccess.

Why clients touch it

Only Rise 6.1.30 and 6.2.4 BlinkComponent reference this packet, again as a buffering exemption. No module in the 8 clients cancels, mutates, or replays it. Cancelling it would kill the login outright, and there is no field worth spoofing: the nonce is server-issued and RSA-protected, so a tampered secret simply fails the nonce check or produces garbage decryption server-side. The 8 clients treat encryption as untouchable infrastructure; their disablers and ping spoofers all operate in the PLAY state where the stream is already encrypted.

Exploit surface

The genuine abuse vector lives on the other side of the exchange: a malicious server can present its own RSA key in S01PacketEncryptionRequest and the client will happily encrypt the session to it, enabling MITM for session hijacking. That is a phishing problem, not a packet-level one, and no module in the corpus touches either side. The only client-side interaction is defensive: blink must not buffer this packet, because holding it would leave the server waiting in KEY state until the login timeout.

Server-Side Handling

processEncryptionResponse: Validate.validState(KEY), decrypt verify token with the private key and compare against the stored nonce (throw on mismatch), store the AES secret, enable encryption on the channel, then authenticate asynchronously via hasJoinedServer with the server-id hash. Failures close the connection with 'Failed to verify username!'.

Protocol Analysis

LOGIN state, id 0x01. Two VarInt-length-prefixed byte arrays: the RSA-encrypted AES secret and the RSA-encrypted verify token, both PKCS1-padded by CryptManager. Must follow S01PacketEncryptionRequest; sending it without a pending KEY state throws. Immediately after this packet the entire stream switches to AES/CFB8, so every later packet is opaque on the wire.

Anti-Cheat Landscape

Not an anti-cheat surface at all: no gameplay data, no timing hooks, and the exchange is protected by the server's own nonce. Proxy setups (BungeeCord with forced hosts) use the secret to key their own encryption layer, but nothing in the 8 clients interacts with that. The practical flagging surface is zero, which is why only BlinkComponent's defensive exemption appears in the corpus.

implementation Implementation Cases

The RSA handshake closer: client sends encrypted AES secret plus verify token, server nonce-checks and enables symmetric encryption. The only corpus hit is BlinkComponent's exemption list; no module cancels or spoofs it because there is nothing to gain and everything to lose.

BlinkComponent (Rise 6.1.30, Rise 6.2.4)

Exempt C01PacketEncryptionResponse from blink buffering so the encryption exchange always completes and the connection actually becomes encrypted.

The PacketSendEvent listener's hard-coded pre-play exemption list includes C01PacketEncryptionResponse; the packet returns untouched and is never parked in the blink queue, so the login continues to the READY_TO_ACCEPT state normally.
