Deep Dive

Role in the protocol

The swing packet is the client's arm-swing notice to the server. C0APacketAnimation carries no payload: in 1.8.9 both readPacketData and writePacketData are no-ops, so the wire cost is a single packet id byte (0x0A). EntityPlayerSP.swingItem() fires it at the start of each swing cycle under the isSwingInProgress guard, and the server echoes the action to every tracked player as S0BPacketAnimation with animation id 0. Because the packet is unauthenticated action signaling, its only real content is timing: when it arrives and how often.

Vanilla handling

Server side, NetHandlerPlayServer.processAnimation calls markPlayerActive() then swingItem() on the EntityPlayerMP. The first resets the idle counter used by the player-list AFK kick logic; the second advances the entity's swing animation and broadcasts S0BPacketAnimation to all trackers. Client side, swingItem() sends the packet once per swing cycle, so one swing equals one packet in vanilla. Mining, attacking and block placement all route through the same swing; the attack itself is a separate C02PacketUseEntity.

Why clients touch it

Five distinct uses appear in the corpus. Scaffold modules send C0A after every onPlayerRightClick3d placement so the server sees a swing matching the block place (Memeware, Nekoware, Rise 5.99, Rise 6.x, Sigma, Tenacity). KillAura-family modules send it in place of swingItem() when the local animation must stay off (Spicy Killaura noSwing mode, Rise 5.99 Aura alwaysSwing). Stealer modules swing before opening chests in Nearby mode. Rise 6.x treats C0A as a swing state bit in BadPacketsComponent and sends it from velocity and flight modes to satisfy attack heuristics. Tenacity Crasher floods 2000 to 10000 C0A packets per motion tick. November Recode 2.0's Scaffold sends C0A when its swing setting is off; LiquidSense Dev's Scaffold and Tower do the same, and its MixinEntityPlayerSP rewrites swingItem to emit C0A under the NoSwing module.

Exploit surface

The packet is empty and the server broadcasts the swing to every tracker, so flooding multiplies server work per byte: Tenacity's Crasher pushes up to 10000 per tick to exhaust the server. Swing rate is also a heuristic input: anti-cheats pair C0A with C02PacketUseEntity to count real attacks, which is why velocity modes send C0A before attackEntity (GrimReduceVelocity). A spoofed swing is always safe: the packet carries no position, timestamp or sequence, so the server cannot verify it, only count it.

Server-Side Handling

processAnimation is two calls: markPlayerActive() resets the idle-tick counter that protects against AFK kicks, then swingItem() plays the arm animation and broadcasts S0BPacketAnimation to tracked players. There is no validation on the packet itself: no cooldown, no rate limit, no payload. Any count per tick is accepted and echoed.

Protocol Analysis

The class is a pure marker: readPacketData and writePacketData are no-ops, so a swing costs one VarInt id byte on the wire. The client sends it from EntityPlayerSP.swingItem() once per swing cycle, guarded by isSwingInProgress. The serverbound id 0x0A maps to the arm-swing animation id 0 in the S0BPacketAnimation broadcast. Timing is the only signal: anti-cheats derive swing rate and attack cadence from packet arrival, not from content.

Anti-Cheat Landscape

Attack anti-cheats count C0A arrivals relative to C02PacketUseEntity: swings without attacks are tolerated (mining, air swings), but bursts of swings with no C03 or C02 between them read as scaffold or autoclicker activity. Rise 6.x BadPacketsComponent explicitly tracks swing as a flag and resets it on the next C03PacketPlayer; other modules query that flag before sending spoofed actions. Flooding C0A trips server-side packet-rate limits long before any movement check.

implementation Implementation Cases

The empty swing packet. Scaffold, KillAura, Stealer and velocity modules inject C0A to keep server-side animation consistent with spoofed actions, Rise 6.x tracks it as a bad-packet state bit, and Tenacity's Crasher weaponizes its zero-payload cheapness by flooding thousands per tick.

anticheat Anti-Cheat Checks

The arm animation packet is an empty swing signal and the only per-click client input anticheats see reliably, which makes it the primitive of every autoclicker check in the corpus. Statistical checks sample the number of movement packets between swings and flag low-variance or excessive click rates (Frequency AutoClickerA, FlopAC AutoClickerA, Hydro's ArmAnimationCheck family). It is also the swing half of swing-break correlation checks (Grim NoSwingBreak) that catch nuker clients breaking blocks without swinging.

Classic low-deviation autoclicker check over the arm animation stream.

Samples the number of flying packets between WrappedPlayInArmAnimation packets, keeping a deque of 20 movement gaps. Samples are only accepted when CPS is above 6.5, fewer than 4 movements separate clicks, and the player is neither digging nor placing. When 20 samples accumulate it computes the standard deviation and outlier count; a deviation below 2 with fewer than 2 outliers fails the check.

Detects: Autoclickers with mechanical timing, where the gap between swings has near-zero variance.
