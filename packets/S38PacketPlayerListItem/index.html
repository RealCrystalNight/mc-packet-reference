Notes

Action 0 (ADD_PLAYER): UUID, name, skin properties, gamemode, ping, display name. Action 4 (REMOVE_PLAYER): just UUID. Action 2 (UPDATE_LATENCY): UUID + ping. This is how the client builds the tab list and gets player skins.

Deep Dive

Role in the protocol

The tab list state machine: one VarInt action plus a list of per-player records. ADD_PLAYER (0) ships UUID, name, the skin property map, gamemode, ping and an optional display name; UPDATE_GAME_MODE (1) and UPDATE_LATENCY (2) carry a UUID plus one field; UPDATE_DISPLAY_NAME (3) a UUID plus an optional chat component; REMOVE_PLAYER (4) a bare UUID. ServerConfigurationManager broadcasts ADD on join, REMOVE on leave, and every 600 ticks it broadcasts UPDATE_LATENCY for the whole list, which is how ping reaches the tab GUI.

Vanilla handling

handlePlayerListItem branches per action and mutates the player info map: ADD builds a NetworkPlayerInfo from the AddPlayerData, UPDATE_LATENCY overwrites the ping field, UPDATE_DISPLAY_NAME swaps the display name, REMOVE drops the entry. The ADD path doubles as the skin pipeline: the textures property is consumed by the player renderer. Server side, the packet constructors snapshot each EntityPlayerMP's profile, ping, gamemode and tab display name into records.

Why clients touch it

Four modules across three clients. Rise 5.99 Denicker intercepts ADD_PLAYER, decodes the base64 textures property from the GameProfile and compares the embedded profileName against the displayed name to reveal nicked players, pairing results with S02PacketChat join lines. Rise 6.1.30 and 6.2.4 StaffDetector keep a hardcoded staff list, but the S38 handler is commented out in both builds, leaving only the PreMotion decay counter live. Sigma 4.11 AntiVanish reads UPDATE_LATENCY and REMOVE_PLAYER to catch vanished players, and FriendAlert notifies when an ADD_PLAYER name matches the friend list.

Exploit surface

The ADD_PLAYER payload is the richest unencrypted metadata stream in the protocol: the full GameProfile including signed skin properties, which Denicker turns into an identity oracle that nick plugins do not scrub. UPDATE_LATENCY is a ping heartbeat that enables vanish detection: a vanished player stops appearing, and AntiVanish also flags latency updates for UUIDs absent from the player info map. No anti-cheat polices the packet; the countermeasures are tab-list plugins that strip or re-sign properties.

Server-Side Handling

ServerConfigurationManager sends ADD to everyone when a player joins and REMOVE on quit; the joining player additionally receives ADD records for everyone already online. onTick broadcasts UPDATE_LATENCY for the whole list every 600 ticks. The channel is broadcast-only: the server never validates what the client does with the data, and there is no clientbound acknowledgment.

Protocol Analysis

The action is a VarInt enum. Record layout depends on action; the widest is ADD_PLAYER: UUID, name capped at 16 chars, VarInt property count, then per property name, value and optional signature strings with a boolean flag, then gamemode VarInt, ping VarInt and an optional chat component. Property strings cap at 32767 bytes. UPDATE_LATENCY entries are only UUID plus ping VarInt, which is why ping refreshes stay cheap.

Anti-Cheat Landscape

Not a detection surface; no anti-cheat measures tab list traffic. The realistic risks are social and structural: Denicker's un-nicking fails when servers strip profileName from the textures payload, and vanish alerts are defeated by networks that keep vanished players in the tab list, which is exactly why Sigma hard-disables AntiVanish on hypixel, hive and mineplex via a server-IP check.

implementation Implementation Cases

The tab list state machine and the most information-dense clientbound metadata channel: ADD_PLAYER carries full GameProfiles with signed skin properties. Four corpus modules live on it: Rise 5.99 Denicker decodes skin payloads to un-nick players, Rise 6.x StaffDetector carries a disabled S38 hook, and Sigma 4.11 AntiVanish and FriendAlert track the latency heartbeat and join records.

Denicker (Rise 5.99)

Reveal the real identity of nicked players by decoding the signed skin texture payload from ADD_PLAYER records.

On PacketReceiveEvent, an ADD_PLAYER S38 is read: the first AddPlayerData's GameProfile is taken, the textures property is base64-decoded into JSON, and the embedded profileName is compared with the displayed name. Mismatches are queued as realName=nickedName pairs; S02PacketChat join messages are then scanned on a background thread, and a matching nick triggers a notification plus a log4j chat rewrite when overlay support is on.

AntiVanish (Sigma 4.11)

Detect vanished players by watching UPDATE_LATENCY and REMOVE_PLAYER records that reference UUIDs absent from the tab list.

On EventPacket (incoming), UPDATE_LATENCY records are checked against mc.getNetHandler().getPlayerInfo(uuid): a latency update for a UUID with no player info entry is flagged as a vanished player and added to a watch list. On the update event, any watched UUID that later gains a player info entry is reported as un-vanished. A REMOVE_PLAYER branch prints the removed display name. A server-IP guard auto-disables on hypixel, hive and mineplex.
