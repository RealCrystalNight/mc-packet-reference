Deep Dive

Role in the protocol

S32PacketConfirmTransaction is the server's reply to each serverbound C0F click confirmation: byte windowId, short actionNumber, boolean accepted. The action number is a per-container short counter the client increments on every click and echoes back; the server replies true when the number matches its own expectation and false when it does not. A false reply marks the window desynced and triggers a full S30 resync. The pair is also the de facto latency probe on post-2018 anti-cheats, which is why it is the most exploited clientbound packet in the Rise 6.x corpus.

Vanilla handling

NetHandlerPlayServer.processConfirmTransaction (lines 886-893 in the bundled sources) compares the echoed action number against the container's expected value: a match replies S32(windowId, action, true), a mismatch replies false and pushes S30 to force the client revert. NetHandlerPlayClient.handleConfirmTransaction resolves the container by window id and treats accepted=false as an order to re-read the window, which is how the server undoes any client-side inventory manipulation.

Why clients touch it

Seven distinct uses in the 10-client corpus. Rise 6.x WatchdogDisabler cancels negative-action S32 confirmations and replays the buffered C0F confirms a second later, a ping-spoof disabler. The 6.2.4 velocity modes (VulcanVelocity, WatchdogVelocity, WatchdogPredictionVelocity) cancel S32 on hit and answer with a deliberately corrupt C0F to desync transaction accounting around knockback. Timer queues S32 while its Watchdog timer mode runs behind a 9,999,999 ms ping spoof. InventorySync rewinds the container transaction counter from S32 values so spoofed clicks keep valid action numbers. Debugger prints every action number. November Recode 2.0's VelocityModule GRIM mode cancels S32 after a velocity cancel, queues the action numbers, and drops the matching C0F on send, a transaction-desync knockback bypass. LiquidSense Dev overwrites handleConfirmTransaction to auto-ack rejected windows through its own send-queue mixin.

Exploit surface

The action counter is a short and the server only checks equality, so fabricating C0F replies is trivial; the subtlety is timing. Buffering C0F and cancelling S32 breaks the correlation the anti-cheat builds between server time and client time, which is the entire point of the Watchdog-era disabler. Cancelling an accepted=false S32 also prevents the inventory revert, which is what keeps ghost-item states alive. The cost is that the server's inventory truth diverges until a legitimate S30 lands, so the exploit is self-limiting.

Server-Side Handling

NetHandlerPlayServer.processConfirmTransaction (lines 886-893) replies S32(windowId, actionNumber, true) when the action matches the container's next expected short, otherwise false followed by updateCraftingInventory, which pushes S30. The container counter is per-window, starts at 0, and must be echoed exactly. The client handler resolves the container by window id; a false reply marks the window desynced and the server's S30 dump reverts the client's slot view.

Protocol Analysis

Wire: byte windowId, short actionNumber, boolean accepted. C0F (serverbound) and S32 (clientbound) share windowId and actionNumber semantics; negative action numbers are legal and several anti-cheats use them as markers, which is why WatchdogDisabler specifically buffers transactions with actionNumber < 0. The pair doubles as a latency reference on Verus and Watchdog-class anti-cheats, so ping spoofers buffer C0F and S32 together with keepalives and flush them as one batch.

Anti-Cheat Landscape

Verus and Watchdog-class anti-cheats fold C0F gaps into their latency model for movement checks. WatchdogDisabler's ping-spoof mode (cancel negative S32, replay all C0F confirms after 1s) and Spicy's Disabler (cancel every C0F, replay one every 500-1250ms) inflate measured ping and break that model. VulcanVelocity cancels S32 only when hurtTime == 10 and answers with a corrupt C0F, a Vulcan-specific knockback desync. The detection risk is not the packet itself but the divergence it causes: servers that resync on rejection eventually expose any client that keeps clicking stale windows.

anticheat Anti-Cheat Checks

S32 is the server's transaction confirmation, the oldest reliable latency probe in the protocol: the server sends a transaction id, the client echoes it back, and the round trip is the ping. Modern anticheats have turned the echo into a transaction clock (Grim sends a transaction before and after sensitive packets, Hydro schedules work on frames), while classic anticheats use it as a ping spoof detector by comparing transaction latency against keep-alive latency. Because the client must echo the exact id, S32 is also where ping-spoof disablers attack the anticheat.

PacketPingListener (Grim) (GrimAnticheat-Grim)

Runs the transaction clock: sends transaction ids the client must echo, tracks send and receive order, and fires the transaction events the whole anticheat schedules on.

On the OUT side, records each sent window-confirmation (negative ids Grim generates, and the ping packet on modern versions) into a sent-map and increments lastTransactionSent. On the IN side, only accepts replies whose id was actually sent, marks the transaction valid, cancels the echo to keep packet limiters happy, and fires the send/receive events that checks, setback teleports and velocity handlers all schedule against.

Detects: Ping-spoof disablers that echo fake transaction ids, and any client that reorders or drops transaction confirmations.

TransactionTracker (Hydro) (Incognitolol-Hydro)

Schedules anticheat work on the transaction confirmations using Pledge frames, and kicks on frame errors.

Registers pre and post actions against Pledge frame ids: confirmPre schedules work on the first id of a frame, confirmPost on the second. When a transaction frame arrives, the tracker runs every action scheduled for that id; missing or incomplete frames are handled as error events that kick the player.

Detects: Transaction desync and confirmation manipulation: a client that drops or reorders confirmations produces missing or incomplete frames.
