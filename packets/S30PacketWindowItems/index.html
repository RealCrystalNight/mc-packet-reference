Notes

For windowId=0, this updates the entire player inventory (45 slots: 9 hotbar + 36 main). For chests, this is sent immediately after S2DPacketOpenWindow. When a C0E click is rejected (S32 accepted=false), the server re-sends S30 to force the client to revert its inventory.

Deep Dive

Role in the protocol

S30PacketWindowItems is the full-window sync packet: an unsigned byte window id, a short slot count, then every slot encoding in order. The server sends it when a container opens (right after S2D PacketOpenWindow), when the player joins or respawns, and as the recovery path when a click transaction is rejected (S32 accepted=false). It is the server's authoritative statement of window contents, and the client applies it wholesale, replacing the container's slot list.

Vanilla handling

NetHandlerPlayClient.handleWindowItems maps windowId 0 and the player inventory window to inventoryContainer and everything else to the open container, then overwrites every slot via putStacksInSlots. EntityPlayerMP.updateCraftingInventory (line 773) builds the list from inventorySlots and sends S30 on every full sync. Because the client trusts the dump completely, S30 is both the sync primitive and the revert mechanism: any client-side inventory manipulation is undone the moment the server decides to re-send.

Why clients touch it

Only Rise uses S30 as a module surface in the corpus. Rise 5.99 Stealer treats it as the go signal: gotItems flips true when the chest contents land, and the steal loop only starts clicking after that flag, with a randomized per-click delay and auto-close. Rise 5.99 Aura resets its blocking flag on S30, since a full window sync invalidates the client's assumption that the sword is still blocking. Rise 6.x AdaptiveRefreshRateComponent counts S30 among the significant packets that dirty the HUD cache.

Exploit surface

S30 is the correction mechanism that makes S2F cancellation a short-horizon trick: one rejected transaction and the server pushes a full dump that reverts any ghost slot. For stealers the ordering constraint is the exploit surface: clicking before S30, or after a rejected click, races the resync and produces the visible pattern (clicking a slot whose content the server already changed) that chest-stealer heuristics flag. The packet is also the largest inventory packet on the wire, so a server that rejects transactions in a loop can force repeated full dumps, a bandwidth tax with no client-side mitigation in the corpus.

Server-Side Handling

EntityPlayerMP.updateCraftingInventory (line 773) serializes the container's inventorySlots into a List and sends S30(windowId, list) on open, respawn, and after rejected clicks. NetHandlerPlayServer.processClickWindow validates the action number; on mismatch it calls updateCraftingInventory so the client receives a corrected dump. The client handler resolves the window by id (0 and the player window map to inventoryContainer, otherwise the open container) and overwrites all slots.

Protocol Analysis

Wire: unsigned byte windowId, short count, then count Slot encodings (short id, byte count, short damage, optional NBT). Slots are ordered container-first, then player inventory 9-35, then hotbar 0-8. The cursor is not included; it is synced separately by S2F(-1,-1). A chest open produces S2D then S30 back to back, which is why inventory modules gate on S30 instead of the GUI opening event: the screen renders before the server contents arrive.

Anti-Cheat Landscape

No anti-cheat measures S30 itself; it is authoritative recovery data. The heuristics that matter sit on the clicks around it: a stealer that fires before S30, or after a rejected transaction, clicks against stale content and produces the tell-tale sequence (C0E immediately followed by the server's S30 correction). Ghost-item exploits depend on S30 never arriving for the manipulated window, so cancel-happy modules trade durability: the longer the manipulation, the more likely a full dump reverts it.

implementation Implementation Cases

The full-window sync and the revert path for rejected clicks. Rise 5.99's Stealer uses it as the trigger to start clicking chests, Aura resets its block state on it, and Rise 6.x treats it as a HUD-significant packet. Every other client in the corpus reaches it only through the vanilla handler.

anticheat Anti-Cheat Checks

The window-items packet dumps the full contents of an inventory window, and for simulation anticheats it is the authoritative recovery data that resyncs the compensated inventory after rejected transactions or open-window changes. Grim consumes it in two places: the inventory mirror applies every server slot to its storage, and the entity replication listener uses window-id-0 dumps to detect held-item and offhand changes. Intave's nayoro stack models the same send as a WindowItemsEvent. No anticheat treats S30 as a detection surface on its own.

Window-items inventory sync (Grim) (GrimAnticheat-Grim)

Keep the compensated copy of the player inventory aligned with the server after every full window-items send.

CompensatedInventory is a Check that listens on both directions. On WINDOW_ITEMS it wraps the packet, marks each server slot as corrected in the inventory storage, and when the window id is 0 (the player inventory) forces the packet-inventory mode back on and syncs the slot list. It tracks the open window id and the packet-sending inventory size, and falls back to the platform inventory for held item, offhand and armor reads when the packet stream is unsupported (modded menus).

Detects: Slot desync between the client's claimed inventory and the server's authoritative dump. The mirror is the basis for inventory-aware checks such as NoSlow and item-use validation.

Window-items event (Intave) (intave-intave)

Model the server's window-items send as a typed nayoro event so Intave's inventory tracking can react to full window dumps.

WindowItemsEvent carries the window id, the slot count, and a map of slot to item. It is one of the event types dispatched through the nayoro EventSink visitor, and the protocol layer registers it in the event registry. The class also handles item serialization for the nayoro wire format.

Detects: None directly: it is event plumbing that mirrors server inventory state into the monitoring stack that backs Intave's inventory and movement checks.
