Deep Dive

Role in the protocol

Scoreboard team management. The action byte drives five modes: 0 create, 1 remove, 2 update info, 3 add players, 4 remove players. Info fields for actions 0 and 2 are display name (32-char cap), prefix (16), suffix (16), a friendly-fire byte, the nametag visibility string (32), and a color byte indexing EnumChatFormatting. Player lists follow for actions 0, 3, and 4 as a VarInt count of 40-char names. Team color drives the nametag color in the client renderer, which makes this packet the surface for team-colored nametag features.

Vanilla handling

handleTeams creates or fetches the team by registered name, applies the info fields for actions 0 and 2, then adds or removes memberships for actions 3 and 4. The client stores teams in its scoreboard; the nametag renderer reads team color and visibility per player each frame. ServerConfigurationManager replays existing teams to a joining player with action 0.

Why clients touch it

Only Rise 6.x. StaffDetector carries a fully commented-out S3EPacketTeams branch that would scan team members for staff names and trigger an auto-leave (/hub) after six hits; the live module relies on the S38 player-list scan instead. The commented block proves the teams surface was tried and abandoned in favor of S38. Rise also registers the class in the script API. No client colors ESP by team here: nametag coloring is left to vanilla rendering.

Exploit surface

The color byte is server-controlled; a client cannot push team colors back because S3E is clientbound. Nametag-visibility abuse (hiding tags via team properties) is a server-side decision. The interesting angle is staff detection: team rosters leak staff membership on servers that place staff in teams, and the Rise staff list plus a six-hit counter is the pattern. It is entirely client-side reading and undetectable.

Server-Side Handling

ServerScoreboard broadcasts S3E on team create (0), remove (1), info update (2), player add (3), and player remove (4). ServerConfigurationManager sends a create replay to each joining player so the client knows existing teams and their colors before the world settles. All sends go through sendPacketToAllPlayers or the per-player handler.

Protocol Analysis

Wire order: team name (16-char cap), action byte, then for actions 0 and 2 the info block, then for actions 0, 3, and 4 a VarInt count of 40-char member names. The packet constructors throw IllegalArgumentException for player actions with empty member lists, and the read path trusts the action byte to choose which trailing fields exist.

Anti-Cheat Landscape

Not monitored. The team color byte feeds EnumChatFormatting.func_175744_a, so a malformed color renders garbage but cannot crash. StaffDetector's commented branch is the only staff-detection use of teams in the corpus, and it never runs.

implementation Implementation Cases

Team management and nametag color. Rise 6.x StaffDetector contains the only module reference, and it is commented out: the teams scan was replaced by the S38 player-list scan. Everything else is vanilla plus the script API table.

anticheat Anti-Cheat Checks

S3E is the one scoreboard packet anticheats actually consume and produce. Grim reads the outbound team stream into per-entity team state that its collision predicates use; intave rewrites the collision rule on outbound team packets and emits team packets to hide fake-player nametags; Shard's monitor emits team packets to render the target name tag and watches for conflicting team traffic. Photon's Teaming is the only flagging check in the domain and it is driven by Bukkit events, not the packet. The rest of the corpus is noise: Rammelkast and AntiCheatPlus match the 'AntiCheat Team' license header on every file, NCP's CollisionUtil reads the Bukkit scoreboard API, and Negativity plus Artemis only register the packet class.

TeamHandler (Grim) (GrimAnticheat-Grim)

Keep a transaction-ordered mirror of the client's team state so entity checks know the collision and push rules between players and entities.

TeamHandler is a PacketSendListener on PacketType.Play.Server.TEAMS. On each S3E it wraps the packet, reads the team name, and schedules a real-time task at the last transaction id so the update applies at the same tick the client processes it. CREATE builds a new EntityTeam, REMOVE drops it, and the other modes update the stored team with the collision rule from the packet. EntityTeam maps members to the team by UUID, and MovementTicker plus EntityPredicates consult it to decide whether an entity can push the player.
