Deep Dive

Role in the protocol

Combat tracker state machine. The server announces combat tag transitions through ENTER_COMBAT and END_COMBAT, with a third variant ENTITY_DIED defined for death broadcasts. EntityPlayerMP sends ENTER_COMBAT from func_152111_bt when combat starts and END_COMBAT from func_152112_bu when it ends; END_COMBAT carries the fight duration in ticks and the tracked entity's ID. Only the clientbound direction exists: the client never acknowledges combat state.

Vanilla handling

The client handler func_175098_a resolves the tracked entity by ID and feeds Twitch streaming metadata: END_COMBAT becomes a MetadataCombat with a negative timestamp derived from the duration (1000 * duration / 20), and ENTITY_DIED becomes a MetadataPlayerDeath carrying the victim, the killer entity and the death message. Nothing in the handler touches the death screen, the health bar or the tab list; those are driven by the client's own entity state.

Why clients touch it

No module in the 8 clients references S42. This is the natural home for death-event hooks (AutoGG, kill counting, KillAura target cleanup), yet the corpus shows none: AutoGG modules in these clients key off S02PacketChat death-message patterns instead, and KillAura cleanup keys off S13PacketDestroyEntities. The structural reason is that the vanilla server never sends ENTITY_DIED: EntityPlayerMP.onDeath broadcasts the death message through ServerConfigurationManager chat (becoming S02PacketChat on the client), and only ENTER_COMBAT and END_COMBAT are ever constructed. The ENTITY_DIED branch of the client handler is dead code in vanilla 1.8.9.

Exploit surface

readPacketData dispatches on a VarInt enum; an out-of-range value deserializes to null (readEnumValue returns null past the last ordinal) and the handler's event comparisons then NPE. The death message is read as a length-prefixed UTF-8 string capped at 32767 bytes, not a chat component, so no JSON component parsing happens here. END_COMBAT writes the tracked entity ID as a plain 4-byte int while ENTITY_DIED writes the killer as a VarInt and the victim as an int: the mixed widths are a known 1.8 protocol quirk.

Server-Side Handling

EntityPlayerMP.func_152111_bt and func_152112_bu wrap the combat tag transitions and send the packet with the current CombatTracker; END_COMBAT fills the duration from CombatTracker.func_180134_f and the tracked entity ID from func_94550_c. Player deaths do not produce this packet: onDeath routes the death message through ServerConfigurationManager chat broadcast, so the ENTITY_DIED variant is only reachable from plugin or modded servers that construct it directly.

Protocol Analysis

Event enum is a VarInt (readEnumValue). END_COMBAT: duration VarInt plus tracked entity ID as a full int. ENTITY_DIED: killer entity ID as VarInt, victim as int, then a String (not IChatComponent, despite the metadata table) capped at 32767 bytes. ENTER_COMBAT carries no payload. readEnumValue returns null for out-of-range values, which reaches the handler as a null eventType.

Anti-Cheat Landscape

Anti-cheats do not use S42 for validation: it is clientbound, and combat tag state is tracked server-side from attack packets (C02) and damage events. Server plugins that expose combat tags rely on ENTER_COMBAT and END_COMBAT, not on client acknowledgements, so there is nothing to spoof or cancel from the client.

implementation Implementation Cases

Combat tag transitions from the server's CombatTracker. ENTER_COMBAT and END_COMBAT are the only variants the vanilla server constructs; ENTITY_DIED exists on the wire but is dead code in vanilla 1.8.9, which is why none of the 8 clients hooks it. Client-side the handler only feeds Twitch streaming metadata.

anticheat Anti-Cheat Checks

The combat event packet carries combat tag transitions: enter combat, end combat, and entity died. Server-side anticheats do not use it for reach or killaura validation, because combat state is tracked from attack packets, but two anticheats consume it for state: Grim reads the death combat event to track whether the client's death screen is showing, which anchors its respawn-alive check, and Intave registers a packet reader that exposes the two entity id fields for substitution. Artemis and Negativity only name the packet in registries.

Respawn alive / death screen state (Grim BadPacketsM) (GrimAnticheat-Grim)

Flag a PERFORM_RESPAWN status request sent while the player is alive and no death screen is showing.

BadPacketsM listens on both directions. On the server side it wraps DEATH_COMBAT_EVENT and COMBAT_EVENT (ENTITY_DEAD) for the player's own entity id and, transaction-sandwiched, marks the menu state from showsDeathScreen. On the client side, a PERFORM_RESPAWN action while the compensated self is not dead and no menu is recorded flags the player. Change-game-state win events and respawns grant short exemptions for the client's own menu toggling.

Detects: Respawn-while-alive exploits, death-screen spoofing, and clients that send respawn without the server having announced their death.

Combat event reader (Intave) (intave-intave)

Expose the combat event packet's two integer entity fields to Intave's packet pipeline so they can be read or substituted.

CombatEventReader is registered in PacketReaders for COMBAT_EVENT. It reads the first two integers of the packet through a substitution iterator: the iterator writes back to the same integer fields, which lets the pipeline rewrite entity references carried by combat events.

Detects: None directly; it is packet plumbing that lets entity-tracking code see and optionally rewrite the entity id fields carried by combat events.
