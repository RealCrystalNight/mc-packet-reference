Notes

Only works in spectator mode. Used by servers when a player enters spectator and clicks on an entity. Freecam modules may use this to switch camera target. No module in the examined client sources directly targets this packet.

Deep Dive

Role in the protocol

Spectator camera switching. EntityPlayerMP sends it whenever its spectatingEntity changes (line 1084 in the MCP builds, 1057 in Rise), which happens when a spectator clicks an entity, cycles targets, or returns to their own body. The single VarInt entity ID is resolved client-side against the entity list, and the handler then reparents the render view to that entity. It is the only packet that moves the camera independently of the player's own position.

Vanilla handling

The client handler func_175094_a calls packet.func_179780_a(world) to resolve the entity ID, and only if the entity is non-null calls gameController.func_175607_a (setRenderViewEntity). The null guard means a bogus ID silently leaves the camera unchanged. The server side only ever sends the packet in spectator mode, after validating the target through EntityPlayerMP's spectator logic.

Why clients touch it

Exactly one module in the 8 clients: Tenacity 6.0's AntiExploit (dev/tenacity/module/impl/misc/AntiExploit.java) cancels S43 when the local player is not a spectator. The rationale is the classic 1.8 camera exploit: a malicious server can force the render view onto an arbitrary or fast-moving entity even while the player is in survival, producing unusable camera motion or a client crash. The check mirrors the server's own precondition, so legitimate spectator flow is never blocked.

Exploit surface

The packet is one VarInt with zero client-side validation of game state. The abuse is a server-side precondition failure: vanilla only sends it to spectators, so any S43 arriving at a non-spectator client is by definition hostile. Beyond Tenacity's check, none of the 8 clients rate-limits or sanity-checks it. Freecam-style modules move the render view locally and never touch this packet, which is why no Freecam or spectate module appears in the corpus.

Server-Side Handling

EntityPlayerMP tracks a spectatingEntity field and sends new S43PacketCamera(spectatingEntity) on every change. The server-side precondition is spectator game mode; the client cannot verify that, so it must trust or filter. The packet is also sent to restore the camera to the player when spectating ends.

Protocol Analysis

Single VarInt entity ID. The client resolves it with WorldClient.getEntityByID; a missing entity yields null and the camera is left untouched thanks to the handler's null check. 1.8.9 uses readVarIntFromBuffer. Play state only; no ordering constraints beyond the entity's spawn packet having arrived, otherwise the resolve fails silently.

Anti-Cheat Landscape

Not an anti-cheat surface. The packet is clientbound and carries no data the server re-validates. Server-side plugins that support spectator mode do not measure camera behaviour. The relevant threat model is malicious-server-to-client, which is exactly what Tenacity's AntiExploit addresses; cancelling it cannot produce a flag because nothing serverbound is modified.

implementation Implementation Cases

Spectator-mode camera reparenting: one VarInt entity ID, resolved and applied by the client handler with a null guard. Only Tenacity 6.0's AntiExploit touches it in the 8 clients, cancelling the packet for non-spectators to block the camera crash exploit.

anticheat Anti-Cheat Checks

The camera packet is clientbound and server-authoritative, so anticheats see it only on send. Exactly two consumers act on it: Grim's CompensatedCameraEntity records which entity the server ordered the client to spectate, and intave's AbilityTracker marks the player as having a view entity so its movement checks treat spectator camera motion as legitimate. The rest of the corpus is keyword noise: Photon's CanSee family and TruthfulAC's AimB mention cameras in the ESP raycast and aim domains without touching the packet, and Artemis and Negativity only register the packet type.

CompensatedCameraEntity (Grim) (GrimAnticheat-Grim)

Track the spectated entity id from the camera packet so entity checks keep measuring against the right body.

A PreVia packet send listener on the CAMERA packet. It reads the camera entity id from the S43 packet, sends a transaction, and on the next real-time task resolves the id against the compensated entity map, keeping a single-entry queue of possible camera targets. isSelf() reports whether the view is back on the player's own body and getPossibilities() exposes the candidates to other checks.

Detects: Nothing directly. It is state sync: the spectated entity becomes the reference body for entity-dependent checks while the player's view is attached elsewhere.

AbilityTracker.receiveCamera (intave) (intave-intave)

Record when the server moves the player's view onto another entity, so movement checks exempt spectator camera motion.

A CAMERA packet subscription on the abilities tracker module. receiveCamera reads the entity id from the packet and schedules a tick-synchronized update that sets hasViewEntity to true when the id differs from the player's own entity id. AbilityMetadata.isSpectatorLike() (line 311) returns true for a player whose game mode is spectator or whose hasViewEntity is set, which movement checks use to skip flags that would otherwise fire for spectator motion.

Detects: Nothing directly. It prevents false positives: the view-entity flag keeps spectator camera movement out of the normal movement checks.
