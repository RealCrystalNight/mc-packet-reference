Deep Dive

Role in the protocol

The scoreboard objective lifecycle packet. A byte action drives it: 0 creates an objective, 1 removes it, 2 updates its display name and render type. Wire fields are the objective name (16-char cap), the action byte, then conditionally for actions 0 and 2 the display name (32-char cap) and the render type string ('integer' or 'hearts'). Objectives are containers; the visible rows arrive separately via S3CPacketUpdateScore and the display slot binding via S3DPacketDisplayScoreboard. ServerScoreboard broadcasts S3B to all players on objective creation, removal, and display-name change.

Vanilla handling

NetHandlerPlayClient.handleScoreboardObjective creates a ScoreObjective with the DUMMY criteria on action 0, sets display name and render type, removes the objective on action 1, and applies display name and render type on action 2. The client scoreboard is the only consumer: the HUD sidebar renders whatever objective the S3D binding points at, populated by S3C rows. Because S3B never carries row data, cancelling it produces an objective-less board, not a blank one.

Why clients touch it

The landscape is thin across the 8 clients. Spicy's HideName imports the class but its EventPacket handler never branches on it: the import is dead weight from a name-hiding feature that actually rewrites S3C rows. Rise 6.1.30 and 6.2.4 register the class in the script API NetworkAPI table so JavaScript scripts can construct or match it. No client cancels S3B. The scoreboard-blocking modules that exist in the wider ecosystem (Gugustus Scoreboard, AntiScoreboard) sit outside this corpus, so none of the 8 reference clients carries an objective-blocker.

Exploit surface

Cancelling S3B is client-visual only. Blocking action 0 leaves rows orphaned, which renders as a sidebar with no header; blocking action 1 freezes a stale objective. The server never learns, because S3B is one-way clientbound and the server does not track which objectives a client holds. Anti-cheats in the corpus never measure scoreboard packets: they carry display strings and no timing or movement state. The only abuse value is a clean HUD, and none of the 8 clients bothers.

Server-Side Handling

ServerScoreboard emits S3B on objective creation (action 0), removal (action 1), and display name or render type updates (action 2), fanned out with sendPacketToAllPlayers. The server never reads S3B back; the packet is strictly clientbound in PLAY state, registered in EnumConnectionState alongside the rest of the scoreboard family. There is no client-to-server scoreboard acknowledgement in the protocol.

Protocol Analysis

readPacketData reads the objective name with a 16-char cap, then the action byte, then only for actions 0 and 2 the 32-char display name and the render type string, mapped through EnumRenderType.func_178795_a. writePacketData mirrors this, so a create packet missing the trailing fields desyncs the stream. Action 1 sends name plus action byte only.

Anti-Cheat Landscape

No anti-cheat in the corpus inspects S3B. It carries display strings only, no timing, position, or movement content. The only measurable effect of tampering is client-side rendering, which server-side anti-cheat cannot observe. Any module touching it is doing cosmetic work with zero detection risk.

The objective lifecycle packet. Across the 8 reference clients it is only an import (Spicy HideName) and a script API registration (Rise 6.x). Nobody cancels or mutates it, because the visible rows travel in S3C and the slot binding in S3D.

anticheat Anti-Cheat Checks

S3B carries scoreboard objective lifecycle state, and only Shard touches it. The monitor HUD system consumes and emits the packet family: ScoreboardSlotObserver reads S3B REMOVE actions and S3D display binds to detect when its claimed sidebar slot is displaced, and ScoreboardPacketBridge builds the S3B objectives, S3D display binds and S3C score rows that render the monitor sidebar. Everything else in the corpus is plumbing or sibling-family noise: Negativity's SCOREBOARD_OBJECTIVE constant and Artemis' four scoreboard wrapper interfaces with their PacketRepository entries register the family, intave's ScoreboardAccessor and EntityCollisionDisabler build and read PacketPlayOutScoreboardTeam (S3E), NCP's CollisionUtil uses the Bukkit scoreboard API for team-collision lookups, and BetterAnticheat's ReloadCommand hits on a comment.

ScoreboardSlotObserver (Shard) (KaelusAI-Shard)

Watches the scoreboard objective and display streams so the monitor HUD notices when its claimed sidebar slot is taken over or its objective is removed by the server or another plugin.

MONITOR-priority PacketSendEvent listener active only while the slot registry holds claims. For S3B it wraps the event as WrapperPlayServerScoreboardObjective and, when the mode is REMOVE and the objective name matches a claim, fires the claim's onSlotLost callback; for S3D it compares the display slot against the claim and fires onSlotLost with a DISPLACED reason when a foreign objective binds there. The callback is deferred through tasksAfterSend onto the main thread.

Detects: None; it is a coordination observer. It detects slot loss so the monitor view can re-assert its sidebar or fall back.
