Notes

Time values: 0=dawn, 6000=noon, 12000=sunset, 18000=midnight. When all players sleep, time jumps to 0 (dawn). S03 is used by modules to calculate server TPS (ticks per second) by measuring the time between S03 updates.

Deep Dive

Role in the protocol

Two longs, totalWorldTime and worldTime, broadcast by MinecraftServer to every player in a dimension once per second (tickCounter % 20 == 0, line ~701 in the MCP builds) and re-sent on player join by ServerConfigurationManager (line ~787). worldTime is the day/night counter the client renders modulo 24000: 0 dawn, 6000 noon, 12000 sunset, 18000 midnight. The constructor folds the doDaylightCycle gamerule into the wire format by negation: when the rule is off the server transmits -worldTime, so the sign bit is the freeze flag and the boolean never exists as a packet field.

Vanilla handling

NetHandlerPlayClient.handleTimeUpdate runs on the main thread via PacketThreadUtil and performs two writes: theWorld.setTotalWorldTime(packet.func_149366_c()) and theWorld.setWorldTime(packet.func_149365_d()). Between corrections the client advances time-of-day itself in its tick loop, so the packet is a periodic correction, not the clock source. That is the property the Ambiance family exploits: cancel the correction and the locally pinned time holds until the next one would have arrived.

Why clients touch it

The Ambiance family spans Memeware 7.3, Rise 5.99, Rise 6.1.30 and Rise 6.2.4, and Tenacity 6.0 ships the same idea as AlwaysNight. All five cancel S03 on the receive event and overwrite world time on a per-frame hook: Memeware writes 0 or 20000 depending on a Morning/Night mode, Rise 5.99 writes time + elapsed * timeSpeed, Rise 6.x adds weather forcing, Tenacity writes a configurable value defaulting to 12000. Notably absent is Fullbright: it is a gamma/lighting override that never touches this packet, and no TPS estimator in the corpus derives server lag from S03 deltas even though the two longs are a natural clock.

Exploit surface

Cosmetic only and invisible to the server, because the client never reports displayed time back. Observers see the desync side effects: a pinned clock shows a frozen sky on the client's own screen, and when all players sleep and the server jumps time to 0 the module visibly fights the correction. No anti-cheat measures this packet. The only hazard is a module that writes worldTime unclamped, which can push the negative freeze encoding into the local renderer and break the sky shader path.

Server-Side Handling

MinecraftServer broadcasts S03PacketTimeUpdate(totalWorldTime, worldTime, doDaylightCycle) to all players in the dimension every 20 ticks (line ~701), and ServerConfigurationManager sends a fresh copy on player join (line ~787). When doDaylightCycle is false the server negates worldTime before sending; the constructor also maps a negated 0 to -1 so the freeze flag survives the zero case. The server never validates or rates the packet stream because it is the sole author.

Protocol Analysis

Two raw longs on the wire; the third constructor argument (doDaylightCycle) is encoded by negation, so worldTime < 0 means the day/night cycle is frozen server-side and the client should display abs(worldTime) without local advancement. Clients that only read the longs (all 5 module implementations here) are unaffected by the sign trick. The packet is sent in the PLAY state and is dimension-scoped, so it stops at the dimension boundary and a fresh one arrives on respawn.

Anti-Cheat Landscape

No anti-cheat flags time manipulation: the client clock is cosmetic, server-authoritative only in the sense that the server periodically corrects it, and nothing gameplay-relevant derives from it. The modules are undetectable from the wire because cancellation happens before the packet reaches the vanilla handler and no corresponding serverbound traffic exists.

implementation Implementation Cases

Once-per-second world-clock correction (two longs, doDaylightCycle encoded as a sign bit). Five modules across the 8 clients cancel it and pin the client clock locally, all with the same two-step shape: cancel on receive, rewrite on frame. Pure client-side cosmetics with zero server visibility.

Ambiance / Ambience (Memeware 7.3, Rise 5.99, Rise 6.1.30, Rise 6.2.4)

Pin the client's day/night clock to a fixed value by cancelling server time corrections.

A receive-side packet event cancels every S03PacketTimeUpdate, then a per-frame hook rewrites the world clock: Memeware 7.3 sets 0 (Morning) or 20000 (Night) on UpdateEvent; Rise 5.99 computes time + elapsedMillis * timeSpeed on Render3D; Rise 6.x does the same and additionally forces weather by cancelling S2BPacketChangeGameState states 1 and 2. The cancel prevents the server value from ever landing, so the local write is the only clock.

AlwaysNight (Tenacity 6.0)

Hold the client's world time at a configurable value (default 12000, midnight) by cancelling server time updates.

A PacketReceiveEvent handler cancels S03PacketTimeUpdate; onEnable and a render-tick listener write the configured value into the world, and onDisable restores time 0. The number setting accepts any value in 0..24000 in 1000-step increments, so the module is a general time pin despite the AlwaysNight name.
