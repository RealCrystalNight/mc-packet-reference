Deep Dive

Role in the protocol

Single-row scoreboard mutation. Fields are the score name (40-char cap), an action enum (CHANGE or REMOVE), the objective name (16-char cap), and for CHANGE a VarInt value. The server emits one S3C per row update: value change, row removal, removal scoped to one objective, and full replay during objective creation and on join. It is the most frequently emitted scoreboard packet: a 15-row sidebar refresh is 15 packets.

Vanilla handling

handleUpdateScore resolves the objective by name, then either sets the score points (CHANGE) or removes the row (REMOVE). A REMOVE with an empty objective name removes the row from every objective. The client scoreboard then re-renders whichever slot binds the objective. The value field is only present for CHANGE, so the read path is action-dependent.

Why clients touch it

Two Spicy files rewrite this packet, both for name visibility. HideName replaces the session username with a chosen alias in both the objective name and the row name fields, so sidebar kill feeds and stats boards stop showing the real name. Account.java does the inverse for alt accounts: it appends the real account name in green so the user can tell which identity is live. Both mutate the decoded packet inside EventPacket pre, before the vanilla handler runs. Rise 6.x only registers the class in the script API.

Exploit surface

Name rewriting here is invisible to the server: S3C is clientbound, and the rewrite happens after decode and before the client scoreboard consumes it. Anti-cheats never see the mutation. HideName stays consistent by applying the same alias to chat (S02PacketChat) and scoreboard rows, so the client-side story matches everywhere. There is no server-side state to desync because the scoreboard lives only on the client.

Server-Side Handling

ServerScoreboard emits S3C on score value changes, row removal, and removal scoped to one objective, plus full replays during objective creation and join. All sends go through sendPacketToAllPlayers. The packet is clientbound only; the server never validates or receives score state back from the client.

Protocol Analysis

readPacketData order: score name (40-char cap), action enum via readEnumValue, objective name (16-char cap), then the VarInt value only when the action is CHANGE. REMOVE rows omit the value, keeping the packet short. The enum has exactly two members, CHANGE and REMOVE; there is no separate add action.

Anti-Cheat Landscape

Nothing flags S3C abuse in the corpus. It carries display strings and a display integer, no timing or movement content. Rewriting name fields is purely cosmetic client-side work that server-side anti-cheat cannot detect.

implementation Implementation Cases

The only scoreboard packet the 8 clients actually mutate. Spicy's HideName swaps the player's username for an alias in score rows; Spicy's Account.java appends the real alt name in green. Both rewrite the decoded packet before the vanilla handler, which the server cannot see.

anticheat Anti-Cheat Checks

S3C is the single-row scoreboard mutation, and no anticheat flags it.
