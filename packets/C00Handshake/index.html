Deep Dive

Role in the protocol

The handshake is the first packet of every connection: a single serverbound C00PacketHandshake carrying the protocol version, the server address as a length-prefixed string, the destination port, and an int state (1 = status, 2 = login). It is sent exactly once, before any encryption, and its state field selects which protocol machine the server runs next. Nothing in the 8 reference clients constructs or intercepts it at runtime; the MCP code path that builds it lives in GuiConnecting.attemptHandshake and the integrated-server path skips it entirely.

Why clients do not touch it

grep of all 8 reference sources (Memeware 7.3, Nekoware v1 private, Rise 5.99, Rise 6.1.30, Rise 6.2.4, Sigma 4.11, Spicy, Tenacity 6.0) returns zero module references to C00PacketHandshake. The reasons are structural: it is sent once before the game world exists, so there is no per-tick module hook active; the vanilla client builds it from GuiConnecting state that modules never influence; and the server trusts its fields for routing only. The one place clients historically touch it is a server-list pinger spoofing protocol version 1 (or 0) to enumerate servers, which these 8 clients do not implement.

Vanilla handling

NetHandlerHandshakeTCP.processHandshake reads the state int. State 1 routes the connection to the status handler (NetHandlerStatusServer), state 2 to the login handler (NetHandlerLoginServer). Mojang's version of the packet also carries a second address string (the 'hostname the client thinks it is connecting to'), which proxies and BungeeCord-style setups use for server routing. The server compares the protocol version against its own and answers with a disconnect or LoginDisconnect if the client is too old or too new.

Exploit surface

Because the packet is unencrypted and fully client-controlled, its real abuse is server-side: protocol-version lying (clients claiming an older version than they speak), hostname injection for proxy routing, and state-flip confusion (sending state 1 then 2) which some anti-bot plugins used to fingerprint scanners. For a client cheat, the packet is a dead end: no timing, no per-tick value, no server-side math to abuse. This is why every one of the 8 clients leaves it to vanilla.

Server-Side Handling

NetHandlerHandshakeTCP.processHandshake validates the protocol version against the server's registered versions and selects the next state machine from the state int (1 = status, 2 = login). A mismatched version produces an immediate disconnect (S00PacketDisconnect in login state) or a protocol-error kick. The embedded hostname is used by proxy frontends to route the connection; vanilla singleplayer and most offline servers ignore it.

Protocol Analysis

Wire format: VarInt protocol version, String server address (VarInt length prefix), Unsigned Short port, VarInt next state. Sent over an unencrypted, uncompressed channel. The 1.8.9 protocol version is 47. After this packet the connection switches state machines, and the next serverbound packet must match the chosen state.

Anti-Cheat Landscape

Anti-cheats almost never inspect the handshake because it arrives before the play state and before any player entity exists. The relevant detection is proxy/ban management: plugins (AntiVPN, server-list bots) fingerprint scanners by protocol-version lies or by abnormal status-then-login sequences. None of the 8 clients participate in that game.
