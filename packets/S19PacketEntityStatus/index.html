Deep Dive

Role in the protocol

S19PacketEntityStatus carries a single opcode byte for one entity: the client-bound event channel for hurt (2), death (3), wolf taming, hearts, wither spawn and a dozen more codes. The server broadcasts it through WorldServer.setEntityState, which routes to the entity tracker (corpus line 880), and EntityPlayerMP sends code 9 to the player itself (line 893). For a cheat client the only actionable signal is the hurt/death transition of the local player, which is why the sole module consumer is a velocity module.

Vanilla handling

NetHandlerPlayClient.handleEntityStatus (Memeware 7.3 bundle, line 897) special-cases opcode 21 (guardian sound) and otherwise forwards the code to entity.handleHealthUpdate, which plays the hurt/death sounds, wolf effects, totem-like particles and so on. The handler is a pure dispatch table: no state is stored, no position is involved.

Why clients touch it

The corpus has exactly one module consumer: Rise 6.x GrimVelocity, in both 6.1.30 and 6.2.4, which uses opcode 2 (hurt) on the local player as the precondition for cancelling the following S12 velocity. Rise's NetworkAPI whitelists the packet for scripts in both versions. Memeware, Nekoware, Sigma, Spicy and Tenacity reference it only through the vanilla handler. The thinness is structural: the packet has no position or rotation data, so movement, render and combat modules have nothing to consume; only the hurt-to-knockback contract matters.

Exploit surface

The S19(2) then S12 pairing is the knockback contract: the server announces damage, then the velocity that results from it. Cancelling S12 after seeing the hurt status is the classic velocity bypass, and GrimVelocity hardens it by sending a C07 dig packet at the player's own position on the next PreUpdate, so the server observes a legitimate block interaction on the damaged tick instead of a missing motion change. Anticheats that detect velocity cancel measure the absent motionY after a confirmed hurt status; the dig packet is the counter because it gives the server an acceptable action to attach the tick to.

Server-Side Handling

Clientbound only. WorldServer.setEntityState broadcasts the opcode through the entity tracker to every tracking player; EntityPlayerMP sends code 9 (the eating effect) to the player directly. The client dispatch is entity.handleHealthUpdate with a special case for 21. There is no per-player state kept on either side; the packet is a one-shot event.

Protocol Analysis

VarInt entityId plus one unsigned byte opcode. The opcode set is defined by Entity.handleHealthUpdate: 2 = hurt, 3 = death, 6 = taming, 7 = tamed, 8 = wolf shaking, 9 = eating, 10 = wolf smoke, 11 = accept, 12 = wither spawn, 15 = redstone torches, 16 = iron golem, 17 = sheep eating, 19 = enderman scream, 20 = zombie villager cure, 21 = guardian elder, 22 = pet wolf, 24 = arrow count, 26 = thorns, 27 = snow particles, 28 = shulker teleport, 29 = iron golem rose. The opcode for the local player arrives on the same connection as the S12 that follows.

Anti-Cheat Landscape

Velocity detection is the only anticheat interaction: the hurt status confirms damage, and the subsequent S12 must produce the expected motion change. Cancelling S12 without a substitute is the classic flag; GrimVelocity's substitute is the C07 dig at the player's own position, which the server processes as a normal block interaction. Server anticheats cannot see the client's S19 handling at all, so the entire exploit surface is the S12 side of the pairing.

implementation Implementation Cases

The status opcode channel is nearly invisible to the 8 clients: one module, GrimVelocity in Rise 6.x, uses opcode 2 as the trigger for a velocity bypass, and the script API whitelists it. Everything else in the corpus is the vanilla dispatch handler.

GrimVelocity (Rise 6.1.30, Rise 6.2.4)

Grim-targeted velocity bypass: cancel the knockback S12 after confirming the hurt status, then emit a benign C07 dig so the damaged tick still carries a legitimate server action.

A VERY_LOW priority PacketReceiveEvent handler checks S19PacketEntityStatus first: when the entity is the local player and the opcode is 2, it sets realVelocity. The next S12PacketEntityVelocity for the local player is then cancelled, realVelocity clears and velocity is set. On the following PreUpdateEvent, if velocity is set, it sends C07PacketPlayerDigging (START_DESTROY_BLOCK while looking at a block and swinging, otherwise STOP_DESTROY_BLOCK) at the player's own position and clears the flag.
