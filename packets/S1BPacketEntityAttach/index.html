Deep Dive

Role in the protocol

S1BPacketEntityAttach is the mount and leash state channel. Opcode 0 attaches an entity to a vehicle (vehicleId -1 detaches), opcode 1 manages leash knots. The corpus server senders: EntityTrackerEntry broadcasts (0, trackedEntity, ridingEntity) when a tracked entity enters range and on mount changes (lines 166, 387), EntityPlayerMP sends (0, self, ridingEntity) when the player mounts (line 630), and EntityLiving broadcasts (1, self, leashedToEntity) on leash attach and detach (lines 991, 1016). The wire format is three ints: leash code, entityId and vehicleId.

Vanilla handling

NetHandlerPlayClient.handleEntityAttach (Memeware 7.3 bundle, line 852) resolves both entities and branches on the code. For code 0 it clears the boat empty flag for the local player, shows the 'mount.onboard' sneak hint when the player mounts a vehicle, and calls mountEntity(vehicle). For code 1 it calls setLeashedToEntity or clearLeashed on the living entity. The handler is a pure state mirror: the client applies whatever the server announces.

Why clients touch it

Zero module hits in the 8-client corpus. The only non-vanilla reference is Rise 6.x NetworkAPI, the script packet whitelist, in both 6.1.30 and 6.2.4; no module in any client branches on S1B. The structural reason: attach state is fully client-rendered and server-authoritative, and the movement exploits that involve vehicles (boat fly, entity control) act on the serverbound side, on C03 positions sent while riding and on local rider physics, not on this clientbound announcement. There is nothing to gain by intercepting a state change the client must apply verbatim.

Exploit surface

The packet is a clientbound state mirror with no acknowledgement, so the abuse direction is server to client: a malicious server can spam attach packets to desync mount state or flip the client's ridingEntity, which corrupts the movement code path (client movement while riding uses the vehicle's physics). Anti-cheats flag vehicle abuse on the serverbound side: impossible vertical C03 deltas while the player's ridingEntity is set server-side. No cheat in the corpus interacts with this packet, and none needs to.

Server-Side Handling

Clientbound only. The server emits it from EntityTrackerEntry on tracking start and mount/leash changes, from EntityPlayerMP when the player mounts, and from EntityLiving on leash transitions. The client applies mountEntity or setLeashedToEntity/clearLeashed and shows the onboarding hint for the local player. No validation, no rate limit, no serverbound counterpart.

Protocol Analysis

Three ints: code (0 = riding, 1 = leash), entityId, vehicleId (-1 or null entity for detach/clear). The boat empty flag is a client-side convenience derived from the local player's mount state, not part of the wire format. The packet is sent once per state transition, not continuously; movement while riding travels through the S14/S18 stream of the vehicle entity.

Anti-Cheat Landscape

No anticheat inspects S1B because it is clientbound. Vehicle exploits are detected from the serverbound stream: boat fly produces C03 deltas inconsistent with the mounted entity's physics, and entity-control exploits abuse C09 slot changes. The packet matters to anti-cheat designers only as the trigger for the server-side riding state that those checks key on.

implementation Implementation Cases

The mount/leash packet is the one clientbound entity packet with no module consumers in the 8 clients: the only non-vanilla reference is the Rise 6.x script API whitelist. Vehicle movement exploits live entirely on the serverbound C03 side, so this announcement is left to vanilla.

anticheat Anti-Cheat Checks

S1B is clientbound mount and leash state, and the corpus shows three real consumers: Grim converts the 1.8 attach into its 1.9+ mount format inside PacketEntityReplication, Artemis folds the player's attach into the prediction vehicle under a transaction confirmation, and Intave registers an AttachEntityReader plus an entity-tracker hook. The remaining hits are noise: NCP's attach terms are listener and block-attachment bookkeeping, Argus's CheckAttachedModules is its own client-module report channel, and Negativity, FlopAC and Artemis contribute constants and wrappers. The flagging side of vehicle exploits stays on the inbound C03 stream; these checks exist to keep the simulated vehicle state honest.

Attach replication (Grim) (GrimAnticheat-Grim)

Mirror the server's mount state into the compensated entity tracker so movement and vehicle checks know what the player and tracked entities are riding.

PacketEntityReplication parses WrapperPlayServerAttachEntity on the ATTACH_ENTITY send, ignores it on 1.9+ servers (replaced by SET_PASSENGERS), and for non-leash attaches converts the 1.8 format into handleMountVehicle: vehicleId -1 dismounts using the stored legacyPointEightMountedUpon, otherwise the mount pair is recorded. An attach naming an untracked entity logs a warning because the client itself would ignore it. SetbackTeleportUtil sends the matching detach during teleport setbacks so a player cannot re-enter a vehicle to keep a cheat active.

Detects: Nothing directly: state replication. It removes mount-state desync as a variable when movement checks evaluate vehicle motion, and the setback-time detach closes the vehicle-reentry bypass during lag-backs.
