Notes

The JSON response includes: version (name + protocol number), players (max + online + optional sample list), description (MOTD ChatComponent), and optionally favicon (base64-encoded PNG with 'data:image/png;base64,' prefix). For modded servers, may include Forge mod info.

Deep Dive

Role in the protocol

The STATUS-state reply to C00PacketServerQuery. NetHandlerStatusServer.processServerQuery answers with sendPacket(new S00PacketServerInfo(this.server.getServerStatusResponse())); the payload is one String holding the full ServerStatusResponse JSON: version name and protocol number, online/max player counts with an optional sample list, the MOTD as a serialized ChatComponent, an optional base64 favicon data URI, and the Forge mod list on modded servers. It is the only clientbound STATUS packet that carries data; S01PacketPong carries only a timestamp echo.

Vanilla handling

NetHandlerStatusClient.handleServerInfo is reached through the anonymous INetHandlerStatusClient that OldServerPinger installs per ping. It stores the parsed ServerStatusResponse into the ServerData entry (serverMOTD, gameVersion, playerList), records the current system time, and immediately sends C01PacketPing with that timestamp. The connection is then driven toward close: S01PacketPong returns, the latency is computed, and the channel closes with "Finished". RealmsServerStatusPinger uses the same handler shape for the Realms list.

Why clients touch it

None of the 8 reference clients touches it. Every corpus hit for S00PacketServerInfo is a net/minecraft vanilla file (OldServerPinger, EnumConnectionState registration, INetHandlerStatusClient, the packet class, RealmsServerStatusPinger, NetHandlerStatusServer). The reason is structural: the STATUS handshake runs before the module system exists, mc.thePlayer is null, and the 8 clients dispatch module events only in the PLAY state. Server detection in these clients (Hypixel checks, brand sniffing) happens later via ServerData after the list entry is filled by the vanilla handler, or in PLAY state via S02PacketChat.

Exploit surface

There is no timing or state abuse available to a client here: the server builds the response, the client renders it. The interesting abuse runs the other direction. A malicious server can stuff the JSON with oversized favicon data (bandwidth cost per ping), hostile chat JSON, or a protocol number far from 47 to force the incompatibility screen. Vanilla 1.8.9 rate-limits nothing on processServerQuery, which is why proxy plugins and BungeeCord fronts exist to absorb ping floods. Anti-cheats have no stake in the STATUS state; the packet is invisible to movement checks.

Server-Side Handling

NetHandlerStatusServer.processServerQuery responds to every C00PacketServerQuery with new S00PacketServerInfo(this.server.getServerStatusResponse()). getServerStatusResponse caches the JSON string until the next tick; favicon and player-sample data are rebuilt on the server tick. There is no per-connection rate limit in the vanilla handler; a flood of queries simply gets a flood of responses, which is why ping-protection plugins and proxy fronts intercept the STATUS state.

Protocol Analysis

Wire format: one String (VarInt length prefix + UTF-8) containing the JSON. The protocol number inside version.protocol must match the client's protocol (47 for 1.8.9) or the client shows an incompatibility screen before the MOTD renders. Ordering: the server sends S00 only in reply to the query; the client then sends C01PacketPing; S00 and S01 are not required to be adjacent, but vanilla always answers them in order. The favicon is a data URI ('data:image/png;base64,...') so the JSON length cap of 32767 bytes applies to the whole response.

Anti-Cheat Landscape

None. The STATUS state precedes encryption, authentication, and world state, so no anti-cheat measures this packet. The practical constraints are plugin-side: ping limits (per-IP query caps), MOTD/favicon validation, and protocol-version gating. A client module gains nothing by intercepting this packet, and none of the 8 clients does.

implementation Implementation Cases

The STATUS-state server info reply. All 8 reference clients are byte-identical vanilla here: the corpus contains zero module files for this packet because the STATUS handshake runs before any module system loads. Server detection that these clients do perform happens later, in PLAY state.

All 8 clients ship the stock 1.8.9 handler tree unchanged: identical OldServerPinger anonymous handler, identical EnumConnectionState registration at clientbound id 0, identical RealmsServerStatusPinger. No client has forked any of these files.

anticheat Anti-Cheat Checks

The STATUS-state server info reply is invisible to server-side anticheats: it predates encryption and world state, and the corpus shows only registration and wrapper plumbing. Artemis maps the packet in its repository and wraps PacketStatusOutServerInfo for its packet library, Negativity lists SERVER_INFO in its packet type registry, and NoCheatPlus keeps deprecated protect-clients MOTD config constants that never became checks. Nothing client-controlled flows through the response, so there is no detection surface.
