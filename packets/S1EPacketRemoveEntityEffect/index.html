Deep Dive

Role in the protocol

S1EPacketRemoveEntityEffect clears one effect from one entity. The only server send site in the corpus is EntityPlayerMP.removePotionEffect, which fires when an effect expires naturally, is cured (milk), is overwritten by a higher-tier re-application, or is stripped on death/respawn. Wire layout is entityId VarInt plus effectId byte. It is the mirror image of S1D: where S1D pushes a full PotionEffect, S1E carries only the potion ID and the client derives everything else from its stored effect.

Vanilla handling

NetHandlerPlayClient.handleRemoveEntityEffect resolves the entity and calls removePotionEffectClient(effectId) on EntityLivingBase. That deletes the map entry, re-applies the entity's attribute modifiers (an expired speed effect removes its movement bonus) and triggers the potion expiry render path. The HUD and effect icons update from the map, so removal needs no separate notification. Unknown entity IDs and unknown effect IDs are ignored without error.

Why clients touch it

No module in the 8 reference clients hooks S1E. The only non-vanilla corpus hit is the Rise 6.1.30/6.2.4 NetworkAPI registration (clientbound index 73) for script use. Effect-removal timing is irrelevant to these clients: HUDs redraw from the entity's potion map, and nothing needs to know the exact tick an effect ended because the client never sends effect state back to the server.

Exploit surface

Cancelling S1E in a receive event leaves the effect visible client-side while the server has already removed it. Because attributes are re-derived server-side, the client keeps stale visuals only: a cancelled speed-removal leaves the speed icon but not the speed, which is the classic tell of a sloppy client-side potion bypass. Anti-cheats ignore the packet entirely; the abuse surface is purely cosmetic and self-reporting.

Server-Side Handling

EntityPlayerMP line 932 sends S1E to the affected player whenever removePotionEffect is called on the server-side entity. EntityTrackerEntry does not broadcast removals to watchers in 1.8.9: other players learn about the change through the next attribute or metadata update, which is why effect removal is a per-player packet. There is no server-side inbound handler, as the packet is clientbound.

Protocol Analysis

Two fields only: entityId VarInt and effectId byte, no duration, no amplifier, no flags. The client must have received the matching S1D earlier; an S1E for an effect never applied is a no-op. Ordering relative to S1D matters: a remove arriving before the apply is silently dropped, so the effect sticks until its natural expiry.

Anti-Cheat Landscape

Nothing flags S1E. Movement effects are enforced from server-side state, so a client that ignores removals can never outrun the server's speed model. Plugin-side detection would require a client state query that 1.8.9 does not define.

implementation Implementation Cases

Effect removal is a two-field state push with zero module usage across the 8 reference clients. The only non-vanilla reference is Rise 6.x NetworkAPI registering the class for scripts; everything else is the vanilla handler.

None of the 8 clients register a packet receive handler for S1E. Rise 6.x exposes the class through NetworkAPI's clientbound table for script injection only.
Memeware 7.3, Nekoware v1 private, Sigma 4.11, Spicy and Tenacity 6.0 keep the vanilla handler. Rise 6.1.30/6.2.4 add the NetworkAPI registration; no other client code touches the packet.

anticheat Anti-Cheat Checks

The remove-effect packet is the mirror image of S1D: it deletes one potion from one entity. Anticheats that replicate effect state on the server (Grim, Artemis, BetterAnticheat) handle it in the same tracker as the apply packet, with the same transaction confirmation, because an effect that outlives its removal in the simulation keeps inflating the allowed speed and jump envelope. Tecnio whitelists both effect classes in its network filter so the pipeline can route them. No anticheat flags S1E directly: the packet carries only an entity id and an effect id, and the interesting state change happens on the entity, not in the packet.

Remove-effect replication (Grim) (GrimAnticheat-Grim)

Drop the potion from the compensated entity at the tick the client processes the removal, so the simulation stops crediting the effect's speed or jump bonus.

The REMOVE_ENTITY_EFFECT branch of PacketEntityReplication decodes the entity id and potion type, forces a transaction when the removal targets the player, and schedules entity.removePotionEffect at the transaction's real-time position. The apply branch in the same listener mirrors the add.

Detects: No cheat directly. A removal that lands late in the simulation keeps the effect's multipliers active too long and desyncs flight and speed checks.
