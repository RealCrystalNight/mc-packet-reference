Deep Dive

Role in the protocol

C10 is the creative-mode inventory writer: a short slot id plus an ItemStack. Slot -1 addresses the cursor stack, slots 1 through 44 the survival inventory grid. The server only enters the handler when the player's gamemode is creative, and inside it applies its own bounds check: flag1 is true only for slots 1 to 44 inclusive, so slot 0, armor slots and the cursor path all fall through to a different branch. In vanilla it is emitted by PlayerControllerMP whenever the creative inventory GUI places or drops an item.

Vanilla handling

processCreativeInventoryAction first, and before any slot validation, inspects the incoming stack's NBT: if it carries a BlockEntityTag with x/y/z keys, the server reads the tile entity at that position and rewrites the tag from the live tile entity NBT. Only then does it validate: flag1 (slot bounds), flag2 (item id non-null), flag3 (metadata >= 0, stackSize 1..64). Valid inventory slots go through putStackInSlot; the cursor branch (slotId < 0) drops the item as an EntityItem with creative despawn age and increments itemDropThreshold by 20, capped at 200. Everything is skipped entirely for non-creative players.

Why clients touch it

None of the original 8 clients ships an inventory-scripting or ItemSpoof module that drives C10 directly; LiquidSense Dev's InventoryUtils.updateInventory does: it re-sends the full 44-slot main inventory as creative actions to force the server's copy back in sync. The remaining corpus hits are infrastructure. Rise 5.99 Crasher uses it in Window mode to inject a book with a deeply nested JSON page into slot 0. Rise 5.99 Freecam allow-lists C10 so creative actions keep working with a detached camera, and Tenacity 6.0's PacketUtil.isClientPacket whitelists it for the silent send helpers. That is the entire module surface.

Exploit surface

The handler's ordering is the interesting part: BlockEntityTag processing runs before slot bounds, so a crafted stack forces a tile entity lookup even when the slot is invalid. Slot 0 and the cursor branch bypass putStackInSlot entirely, which means a creative client can push arbitrary NBT-bearing items at the server without them landing in inventory. Anti-cheats with creative checks (NCP's inventory heuristics, custom gamemode guards) flag C10 sent while the server-side gamemode is not creative; the packet is a silent no-op there, so the main abuse channel is the NBT payload itself.

Server-Side Handling

processCreativeInventoryAction: gamemode gate, BlockEntityTag sync, then flag1/flag2/flag3 validation. Slots 1..44 go through putStackInSlot, slot -1 drops the item as a creative-despawn EntityItem (itemDropThreshold +20 per drop, max 200), everything else is ignored. ItemStacks are not re-serialized against an item registry beyond getItem() != null, so crafted NBT survives to any plugin that reads the slot.

Protocol Analysis

short slotId (signed) + Slot-encoded ItemStack (short item id, byte count, short damage, optional NBT). Sent in PLAY state only. The client never sends it in survival: PlayerControllerMP.windowClick paths to C0EPacketClickWindow instead, so a survival server receiving C10 is already anomalous.

Anti-Cheat Landscape

Anti-cheats that mirror the server gamemode flag C10 from a survival player as an inventory exploit attempt. Creative-gamemode servers rarely monitor it, which is exactly why crash payloads ride this packet: the handler still parses and processes NBT before the gamemode logic can matter to plugins.

implementation Implementation Cases

BadPacketsD (LightAntiCheat) (tiredvekster-LightAntiCheat)

Flag creative-slot packets sent by players who are not in creative mode.

On SET_CREATIVE_SLOT, the check skips when the player is already creative or changed gamemode less than 500 ms ago, so a fresh switch to creative does not false-flag. It re-checks the condition one tick later to ride out lag, then flags.

Detects: Clients that send creative inventory packets in survival, which is the primitive behind item-spoof and creative-give exploits.
