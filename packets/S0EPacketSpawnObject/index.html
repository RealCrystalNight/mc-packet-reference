Deep Dive

Role in the protocol

The spawn packet for every non-living entity: item drops (type 2), boats (1), minecarts (10), TNT (50), ender crystals (51), arrows and spectral arrows (60/91), snowballs (61), eggs (62), fireballs and small fireballs (63/64), ender pearls (65), wither skulls (66), fishing hooks (90), falling blocks (70), item frames (71), armor stands (78) and more. The server's EntityTrackerEntry.getPacket builds it with the EntityList type code, fixed-point position (x32), byte rotations (x256/360) and short velocity (x8000), and the third constructor argument packs a per-type data int: the shooter entity id for arrows and fireballs, the block state id for falling blocks, the minecart type for carts, the facing index for item frames.

Vanilla handling

NetHandlerPlayClient.handleSpawnObject reads the entity id, type byte, position, three rotations, the three velocity shorts and the trailing DataWatcher, then creates the entity through EntityList.createEntityByID and applies the transform. For projectile types the data int is used to look up the throwing entity so the client can attribute the projectile. Server side, the same packet class is the output of EntityTrackerEntry.getPacket, which is why the type codes and the data int semantics are defined by the server's tracking code, not by the packet class itself.

Why clients touch it

None of the 8 reference clients hook S0E in any module. The corpus shows only vanilla files plus Rise 6.1.30/6.2.4 NetworkAPI.java, which lists S0EPacketSpawnObject in the packet registry that the scripting API exposes to scripts. The absence is structural: ESP, Tracers and KillAura in these clients iterate world.getLoadedEntityList on render ticks instead of hooking spawn packets, so they never see S0E, and the throwable-specific combat modules of the wider ecosystem (AntiFireball-style projectile attackers, item ESP) are not present in this corpus.

Exploit surface

The packet is server-trusted end to end, so the attack surface is client-side robustness: extreme velocity shorts, bogus type codes and oversized DataWatcher payloads are the classic crash vectors, and armor stand floods (type 78) were the 1.8-era lag exploit. For anti-cheat work the interesting field is the data int: a projectile carrying the player's entity id as owner is the standard signal AntiFireball-style modules use, and servers that simulate projectiles server-side validate the owner id against the tracker. Anti-cheats that replay or predict projectile trajectories reconstruct them from S0E position and velocity, so the packet is a timing reference for those checks.

Server-Side Handling

EntityTrackerEntry.getPacket switches on the tracked entity class and returns S0E with a type code from EntityList, position x32, yaw/pitch byte rotations and motion x8000 shorts. The third constructor int is type-specific: shooter entity id for arrows and fireballs (0 when the shooter is gone), block state id for falling blocks, minecart type id for carts, facing horizontal index for item frames. The client handler creates the entity and applies the transform; for arrows the data int resolves the thrower so the client can render the correct owner.

Protocol Analysis

Entity id and type are VarInt/unsigned byte; position is three ints at x32, rotations are three bytes at x256/360 (yaw, pitch, head pitch), velocity is three shorts at x8000. A DataWatcher block terminates the packet only when the entity has metadata; most non-living types send an empty watcher. The same type codes are shared with the 1.8 EntityList server-side table, so a mismatch between client and server entity registries despawns the entity silently.

Anti-Cheat Landscape

Nothing client-controlled is flaggable here because the packet is purely clientbound and server-authored. Anti-cheats use it indirectly: projectile simulation checks reconstruct arrow and fireball paths from S0E and replay them to catch players who dodge impossibly, and servers rate-limit object spawns to stop item/armor stand flood lag exploits. No reference client touches it, so there is no bypass trade-off to document beyond the generic entity-spawn flood mitigations.

implementation Implementation Cases

anticheat Anti-Cheat Checks

S0E spawns a generic entity (item, TNT, boat, arrow) with a type id, position and velocity, and is the most common spawn packet in the protocol. Server-side anticheats treat the spawn-object family as the feed for their entity replication: every spawn registers an entity in the compensated world so reach and killaura checks can measure vectors to real targets, and fake-entity bait mechanisms reuse the same family to lure auras. The corpus hits on S0E are therefore the spawn listeners themselves (Grim PacketEntityReplication, Hydro EntityTracker, Kauri PacketHandler, FlopAC WrappedOutSpawnEntityPacket) plus the anti-aura bait code that reuses spawn packets (Kauri FakeMob, Peyang NPC, Shard ViewTrackingObserver).

PacketEntityReplication (Grim) (GrimAnticheat-Grim)

Replicate every server-side entity spawn, including the S0E spawn-object packet, into the simulated world that reach and hitbox checks run against.

PacketSendListener handles SPAWN_ENTITY (S0E), SPAWN_LIVING_ENTITY, SPAWN_PLAYER and SPAWN_PAINTING, calling addEntity with the id, uuid, type and position; subsequent relative moves, teleports, rotations, metadata and equipment updates are applied inside latency-compensated realtime tasks, and despawns are queued per transaction. It also blocks ViaVersion's faked levitation effects and drives the spawn-teleport acceptance state used by setbacks.

Detects: Reach and killaura cheats are measured against the replicated boxes, so the check is the data foundation rather than a flag; it keeps the anticheat from being fooled by spoofed spawn state.

EntityTracker (Hydro) (Incognitolol-Hydro)

Keep a transaction-synced map of every spawned entity so reach and aura checks can query positions and distances.

The outgoing pre-handler processes the spawn family (living entities and players) plus relative moves, teleports and destroys; entity positions are only mutated inside transaction-confirmed tasks, and post-transaction updates refresh the list. Exposes distance, closest-entity and within-distance queries used by the combat checks.

Detects: Supplies the target positions for Hydro's hitbox and reach checks; a client that fakes entity state cannot alter the server-derived list.
