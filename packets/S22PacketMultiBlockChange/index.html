Deep Dive

Role in the protocol

S22PacketMultiBlockChange batches block updates for one chunk. PlayerManager's chunk update tick collects changed positions into a short[] and sends a single packet: chunkX int, chunkZ int, record count VarInt, then per record a short crammed position and a VarInt block state id. The crammed short packs y in the low 8 bits, x in bits 12-15 and z in bits 8-11 (y | x<<12 | z<<8). It is the batched sibling of S23PacketBlockChange and the only efficient way the server pushes many block edits in one tick.

Vanilla handling

NetHandlerPlayClient.handleMultiBlockChange iterates the BlockUpdateData array and calls world.func_180503_b(position, state) for each record, a no-notify setBlockState. The chunk must already be loaded; the packet never triggers a chunk load. Render updates are not batched here, so rapid multi-block streams can cost a client more in re-renders than in parsing.

Why clients touch it

None of the 8 reference clients hook S22 in a module; the only non-vanilla hit is Rise 6.1.30/6.2.4 NetworkAPI registering the class (clientbound index 77). FastBreak-style sync modules (which wait for the server's block-change echo to confirm a broken block) exist in other clients but have no corpus presence here. Block-scanning features re-scan the loaded world rather than parse per-packet records, so the packet stays vanilla.

Exploit surface

Dropping or rewriting S22 records desyncs the client's block map from the server's. Scaffold and FastBreak flows depend on the S22 echo to re-sync ghost blocks; a client that ignores it keeps stale visuals and can misplace subsequent placements. The server never validates application, so the desync is invisible in the packet stream. The crammed short encoding is the one real parsing hazard for any module that does touch this packet.

Server-Side Handling

PlayerManager line 460 (Memeware/Nekoware/Sigma corpus) sends S22 with the tick's accumulated numBlocksToUpdate and locationOfBlockChange array to every player watching the chunk. Records carry the block state id resolved from Block.BLOCK_STATE_IDS at construction. There is no inbound handler: the packet is clientbound and the server never learns whether the client applied the changes.

Protocol Analysis

Record count is a VarInt; each record is a short crammed as y | x<<12 | z<<8 (x and z 4 bits each, y 8 bits) followed by a VarInt block state id. The short encoding is why records are bounded to 4096 per chunk. Arrival order within the packet is the order the server collected the edits; the client applies them sequentially with no sorting.

Anti-Cheat Landscape

No anti-cheat measures S22. Server-side block verification (NCP's 'block' checks) operates on the server's own world model and the player's dig/place packets, so client-side application of S22 is never audited. The practical detection surface is gameplay-based: a client that desyncs from S22 places ghost blocks that staff can see in replays.

implementation Implementation Cases

Batched block-change delivery with no module usage in the 8 reference clients. The only non-vanilla reference is the Rise 6.x NetworkAPI script registration; block-aware features re-scan the loaded world instead.

No module in the 8 clients registers a receive handler for S22. The only non-vanilla reference is the NetworkAPI class table entry in Rise 6.1.30 and 6.2.4.
All 8 clients keep the vanilla handler. Rise 6.x adds the NetworkAPI registration; Memeware, Nekoware, Sigma, Spicy and Tenacity differ only by vanilla source revision.

anticheat Anti-Cheat Checks

S22 batches up to 4096 block changes into one chunk-section update, the form the server uses for explosions, pistons and large world edits. Server-side anticheats treat it as a compensated-world mutation: the changed blocks must be applied to the replicated cache before any movement or visibility check runs, otherwise phase, scaffold and ray-trace checks would judge the player against a stale world. The corpus for S22 is the block-change pipeline (Grim CompensatedWorld, NCP BlockChangeTracker and BlockChangeListener, Hydro WorldTracker, Kauri BlockUpdateHandler, Intave MultiBlockChangeReader), all feeding the same cache that xray and phase detection query.

BlockChangeTracker and BlockChangeListener (NoCheatPlus) (Updated-NoCheatPlus-NoCheatPlus)

Compensated block cache: record every server block change, including S22 multi-block updates, with validity intervals so movement checks can tell whether a block existed at the time the player used it.

BlockChangeListener registers Bukkit events (piston extend and retract, redstone, entity block change, block form, player interact) and forwards each change into BlockChangeTracker.addBlockChange with a change id, tick and direction. The tracker stores per-coordinate linked lists of BlockChangeEntry objects that expire by tick; movement checks (SurvivalFly, Passable, Visible) query getBlockChangeEntry and matchBlockChange with a BlockChangeReference to test whether the block was solid at the player's position at move time.

Detects: Feeds ground and passable decisions; prevents false flags when a block was legitimately changed by an explosion or piston between the client's view and the server's world.

Apply S22 multi-block and S23 single-block changes to Grim's compensated world with transaction accuracy.

Detects: Keeps phase, ground-spoof and scaffold checks honest by presenting the block state the client actually had instead of the server's current state.

MultiBlockChangeReader (Intave) (intave-intave)

Decode the S22 packet into absolute block positions and block data for Intave's block update tracker.

CompiledPacketReader that reads either the 1.16.2+ section-relative encoding (section position plus 12-bit relative coordinates) or the legacy MultiBlockChangeInfo array, and exposes blockPositions() and blockDataList() to the BlockUpdateTracker, which applies them to the block cache and acknowledges the sequence number.
