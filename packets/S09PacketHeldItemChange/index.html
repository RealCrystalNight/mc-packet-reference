Notes

This is the server echo of C09PacketHeldItemChange. The client uses this to stay in sync with the server on which hotbar slot is selected.

Deep Dive

Role in the protocol

S09 is the server echo of the client's C09PacketHeldItemChange: one byte, the hotbar slot 0-8. ServerConfigurationManager sends it to a player on join (with the current slot) and on every accepted slot change, so client and server agree on the held item. It is a confirmation, not a command, which is why module interest is nearly zero: there is nothing to spoof, cancel or time.

Vanilla handling

NetHandlerPlayClient.handleHeldItemChange bounds-checks the slot (>= 0 and < InventoryPlayer.getHotbarSize()) and assigns inventory.currentItem. An out-of-range echo is silently ignored, so a corrupted slot value cannot desync the hotbar. The client's own C09 send path is separate: EntityPlayerSP switches slots locally and the server confirms with S09.

Why clients touch it

Two real references in the corpus. Rise 6.x PingSpoofComponent lists S09 in its teleports class tuple next to S08 and S39: when a disabler arms spoofing with the teleports tuple, S09 is intercepted and delayed like the stateful packets, because a slot echo released out of order desyncs the hotbar. Rise 5.99 Aura and Sigma 4.11 InventoryManager import S09 without handling it: both do silent slot switching on the C09 side and the import is dead in the shipped builds.

Exploit surface

There is no exploit surface worth the name. Delaying S09 through PingSpoofComponent is the only manipulation in the corpus, and it is collateral of the C00/C0F buffering rather than a slot attack: the delay window is the same amount used for keepalive and transaction spoofing. Anti-cheats do not measure slot echoes, and no module in the 8 clients reads S09 to detect forced slot changes.

Server-Side Handling

ServerConfigurationManager sends S09 to the player on join (line 166 in the Memeware copy) and after every accepted C09 slot change (line 802), always with playerIn.inventory.currentItem. The server never validates the echoed value because the client is the source of truth for its own hotbar; the packet is purely informational.

Protocol Analysis

Single byte field, hotbar index 0-8. Sent in PLAY state, clientbound only. The pairing with C09 is asymmetric: C09 carries the requested slot, S09 confirms it, and the client applies the confirmation unconditionally within bounds. Because S09 is a broadcast to the player only, silent-switch modules depend on the server never echoing a slot they did not send.

Anti-Cheat Landscape

No anti-cheat measures S09. Slot-change rate is governed by the C09 side (inventory clicking and silent switch modules), and the echo adds nothing measurable. The only detection-adjacent use is PingSpoofComponent's ordering constraint: releasing a delayed S09 after the server already moved on would desync the hotbar visually, so the component holds and releases it with the buffered batch.

implementation Implementation Cases

The server echo of the held-slot change: one byte, bounded to 0-8, applied straight to inventory.currentItem. Module interest is minimal: only Rise's PingSpoofComponent treats S09 as state that must be buffered with the teleport class of packets, and the Aura and InventoryManager references are dead imports.

PingSpoofComponent (Rise 6.2.4, Rise 6.1.30)

Treat S09 as server state that must be held and released with the buffered keepalive and transaction batch when a disabler arms the teleports tuple.

The teleports tuple lists S08, S39 and S09. While enabled and the tuple is armed, any matching packet is cancelled on the receive event and parked in the timed queue, then released via PacketUtil.queue after the configured delay from PostMotionEvent.
