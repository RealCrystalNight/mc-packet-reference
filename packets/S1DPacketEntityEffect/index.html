Deep Dive

Role in the protocol

S1DPacketEntityEffect applies one potion effect to one entity. The server has three send sites: EntityTrackerEntry broadcasts an entity's new effect to every player watching it, EntityPlayerMP.addPotionEffect and refreshActivePotionEffect send it to the affected player directly, and ServerConfigurationManager replays effects (beacon, team) on respawn and on player join. Wire layout is entityId VarInt, effectId byte, amplifier byte, duration VarInt in ticks, hideParticles boolean. In 1.8.9 the effect is a full state push: the client stores it in the entity's active potion map and the server never asks for confirmation.

Vanilla handling

NetHandlerPlayClient.handleEntityEffect runs on the client thread via PacketThreadUtil, resolves the entity with getEntityByID, and for EntityLivingBase targets builds a PotionEffect(effectId, duration, amplifier, false, hideParticles), calls setPotionDurationMax(duration), then addPotionEffect. From that point every renderer (armor, HUD, particles, the player's own effect tab) reads the entity's activePotionMap. Effects on non-living entities are silently dropped, and an unknown entityId does nothing.

Why clients touch it

None of the 8 reference clients hook S1D in a module. The only non-vanilla corpus hit is Rise 6.1.30 and 6.2.4 NetworkAPI.java, which registers S1DPacketEntityEffect in the clientbound class table (index 72) so scripts can build and inject it via receivePacket. Effect-aware features in these clients (effect HUD rows, potion ESP) poll the entity's active potion map after vanilla applies the packet, or render from EntityLivingBase state, so no packet interception is needed. The PotionHUD/AntiPotion entries in older packet docs come from Sigma 3.9, which is not part of the reference set; Sigma 4.11's corpus has no S1D hit.

Exploit surface

Cancelling S1D in a receive event is a client-side potion bypass: the server keeps applying the effect and its movement math, the client simply never renders or stores it. That grants nothing for movement because speed, jump and health attributes are server-authoritative. Anti-cheats never measure this packet; it is one-directional cosmetic state. The only bandwidth note is that EntityTrackerEntry sends one S1D per effect per tracked entity on the tracking loop, so rapid effect churn is amplification surface for griefing plugins, not for cheat modules.

Server-Side Handling

EntityTrackerEntry line 418 sends S1D to each playerNetServerHandler in the watching list when a tracked entity gains an effect; EntityPlayerMP lines 922/927 send it to the affected player for addPotionEffect and refreshActivePotionEffect; ServerConfigurationManager lines 193/509 replay active effects on respawn and join. The server does no validation on the receiving side: there is no processX handler because the packet is clientbound only.

Protocol Analysis

The amplifier byte is the level minus one (0 means level I). Duration is in ticks on the wire; the client stores it as the effect duration and also as durationMax, so the potion icon countdown and the expiry timestamp both come from this single value. hideParticles maps to the PotionEffect showParticles flag; an S1D with the same effectId overwrites the previous entry in the active potion map rather than stacking.

Anti-Cheat Landscape

No anti-cheat in the 1.8.9 ecosystem flags S1D handling. Movement-relevant effects (speed, jump boost, slowness) are validated from server-side attribute and motion math, so a client that drops the packet only sees wrong visuals. Servers that want to detect a modified client would have to query the client for its potion state, which vanilla 1.8.9 has no packet for.

implementation Implementation Cases

Effect application is a pure server-to-client state push with no module interest in the 8 reference clients. Every effect-aware feature reads the entity's potion map after vanilla applies the packet, and the sole non-vanilla corpus hit is Rise 6.x NetworkAPI registering the class for script injection.

No module in the 8 clients registers a packet receive handler for S1D. The only hook surface that exists in the corpus is Rise 6.x NetworkAPI, which exposes clientbound packets to JavaScript scripts by class-table index.
Memeware 7.3, Nekoware v1 private, Sigma 4.11, Spicy and Tenacity 6.0 ship the vanilla handler byte-for-byte. Rise 6.1.30 and 6.2.4 additionally register the class in NetworkAPI (script/api/NetworkAPI.java), the only place any of the 8 clients references the packet outside net/minecraft.

anticheat Anti-Cheat Checks

Server-side anticheats treat the entity-effect packet as state synchronization, not a cheat signal. The corpus splits into packet-driven potion trackers (Grim, Artemis, BetterAnticheat, Kauri, Intave) that decode S1D and mirror the effect onto their simulated player or entity, and Bukkit-polling checks (FlopAC, Hydro, Frequency) that read getActivePotionEffects and only see the effect after the server applies it. The trackers matter because movement checks must know the exact speed, jump and slowness multipliers the client has; a potion state mismatch causes false flags in speed and flight checks, so the apply packet is transaction-confirmed before the effect lands in the simulation.

Effect state replication (Grim) (GrimAnticheat-Grim)

Keep the compensated entity's potion state in sync with the server so movement predictions apply the same speed, jump and slowness multipliers the client sees.

PacketEntityReplication listens on the packet-send side. For ENTITY_EFFECT it decodes the potion type and amplifier, cancels the packet when ViaVersion would fake an effect the client version does not support, forces a transaction when the effect targets the player, and schedules entity.addPotionEffect on the compensated entity at the transaction's real-time position. The remove branch in the same listener mirrors this with entity.removePotionEffect.

Detects: No cheat directly. It is state replication: speed, jump boost and levitation modifiers on the simulated entity must match the client's, or flight and speed checks misjudge legitimate motion.
