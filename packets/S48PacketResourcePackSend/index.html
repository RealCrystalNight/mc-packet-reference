Deep Dive

Role in the protocol

The server orders the client to load a resource pack. Two strings travel: the URL and a SHA-1 hash used for integrity. The vanilla flow downloads the pack, applies it and answers with C19PacketResourcePackStatus (ACCEPTED, DECLINED, FAILED_DOWNLOAD, SUCCESSFULLY_LOADED). The level:// scheme is the sharp edge: vanilla maps level://name to a file inside the local saves directory, so the URL doubles as a local file path.

Vanilla handling

handleResourcePack branches on the scheme. level:// URLs resolve against mcDataDir/saves: if the file exists the pack loads and ACCEPTED then SUCCESSFULLY_LOADED are sent; if not, FAILED_DOWNLOAD. HTTP(S) URLs go through the resource pack repository asynchronously, with a GUI prompt unless the server's resource mode is ENABLED or DISABLED.

Why clients touch it

Three defensive implementations in the corpus. Rise 6.1.30 and 6.2.4 run ResourcePackCheck as a SecurityFeature: it validates the scheme, decodes the level:// path, and rejects any URL containing ".." or not ending in /resources.zip, answering with C19 FAILED_DOWNLOAD. Tenacity's AntiExploit module cancels the packet and sends FAILED_DOWNLOAD for the same classes of malicious URLs. LiquidSense Dev injects MixinNetHandlerPlayClient with a HEAD-cancellable @Inject on handleResourcePack that performs the identical scheme and level:// checks, replying C19 FAILED_DOWNLOAD and cancelling the vanilla handler on failure. All three target the level:// traversal that reads arbitrary files from the saves folder.

Exploit surface

A level:// URL with ../ segments walks out of the saves directory into other local files, which the client then loads as a resource pack; vanilla does not verify the hash for level:// packs. Replying FAILED_DOWNLOAD keeps the server's state machine consistent so it stops waiting for a status, which is why both defenses send C19 rather than silently dropping the packet.

Server-Side Handling

Server side, the packet is built by EntityPlayerMP.loadResourcePack or sendResourcePack with an arbitrary URL and hash supplied by plugins or server config. The server waits for a C19 status before re-prompting; a client that never replies eventually stops receiving pack offers. The hash is echoed back verbatim in C19.

Protocol Analysis

Two strings: URL and SHA-1 hash. The level:// scheme is special-cased client-side, and the hash is ignored for level:// packs in vanilla. C19 carries the same hash back, so the status reply identifies which offer it answers. The packet id 0x48 is clientbound-only in PLAY state.

Anti-Cheat Landscape

Not a movement or combat surface: no anti-cheat measures S48 traffic. The defense angle is client security (file disclosure via level://), and both corpus implementations are client-side self-defense rather than anti-cheat bypasses.

implementation Implementation Cases

The resource pack push. Rise 6.x defends it as a SecurityFeature (ResourcePackCheck), Tenacity as an AntiExploit module, and LiquidSense Dev as an @Inject guard on MixinNetHandlerPlayClient; all three reject level:// path traversal URLs and reply C19 FAILED_DOWNLOAD to keep the server's status state machine moving.

ResourcePackCheck (Rise 6.2.4, Rise 6.1.30)

Block malicious resource pack offers, specifically level:// URLs that read local files, before the vanilla download flow runs.

A SecurityFeature (not a toggleable module) whose handle() inspects every packet: for S48 it takes the URL and hash, and only acts on level:// URLs. The URL is parsed as a URI, the scheme must be http, https or level, and a decoded level path containing ".." or not ending in /resources.zip is rejected with C19 FAILED_DOWNLOAD. The attempted path is printed to stdout.

anticheat Anti-Cheat Checks

Artemis is the only anticheat with logic on the send side of the resource-pack flow. Its PingSpoofProtocol pushes a fake S48 offer whose URL encodes a keepalive id and validates the client's C19 FAILED_DOWNLOAD reply, and ResourcePackTickHandler uses a level:// offer with a numeric hash as a tick-confirmation channel. These are the OUT-side arms of the same two checks documented on the C19PacketResourcePackStatus page. FlopAC's WrappedOutResourcePackSend and the Negativity RESOURCE_PACK_SEND constant are wrappers and registrations only.

PingSpoofProtocol (Artemis) (artemisac-artemis-minecraft-anticheat)

Detect ping spoofing with a resource-pack offer as the probe: the server sends S48 with an id-encoded URL and verifies the client's C19 answer.

On 1.9 and older servers the check builds a GPacketPlayServerResourcePackSend whose URL is a generated numeric id (line 175) and pushes it to the client. It then expects the C19 response: FAILED_DOWNLOAD with a matching numeric URL, followed by the next keepalive echo. Missing, out-of-order or non-numeric responses log violations. On 1.10+ it switches to fake teleports because the packet's hash field was removed there.

Detects: Ping spoofers that suppress or reorder keepalives, and clients that answer resource-pack offers they were never sent.

ResourcePackTickHandler (Artemis) (artemisac-artemis-minecraft-anticheat)

Use a level:// resource-pack offer as a tick-confirmation channel on 1.8 servers.

On 1.8.9 and below it sends a GPacketPlayServerResourcePackSend whose hash encodes a numeric tick id (line 57), then accepts only C19 FAILED_DOWNLOAD replies whose URL is numeric and contains the player name. The parsed id is stored as the player's resourcePackTick and feeds the tick-confirmation infrastructure other Artemis checks use to measure connection state.

Detects: Nothing directly. It feeds connection-state measurement rather than flagging a behavior.
