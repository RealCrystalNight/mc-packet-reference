Notes

This is the SERVER→CLIENT version. The server sends this when the player's abilities change. The CLIENT→SERVER version is C13PacketPlayerAbilities (which only carries the isFlying flag).

Deep Dive

Role in the protocol

Server-to-client capability sync: one flags byte (0x01 invulnerable, 0x02 flying, 0x04 allowFlying, 0x08 creative), then fly speed and walk speed floats. The server pushes it on join, on every capabilities change, and as part of the login burst alongside S01, S37 and S38. Its serverbound mirror C13PacketPlayerAbilities carries only the isFlying flag, so S39 is the only place the client learns the full authoritative set.

Vanilla handling

handlePlayerAbilities copies all four flags and both speeds into thePlayer.capabilities, and the movement code then obeys them: fly speed scales creative flight, walk speed scales ground speed. Server side, processPlayerAbilities (C13) flips only isFlying and only when allowFlying is true, so the server stays authoritative and re-broadcasts the corrected state via S39 whenever it disagrees with the client. The client handlers are behaviorally identical across all 8 corpus clients.

Why clients touch it

Three Rise 6.x surface areas. CreativeFlight, a mode of the Flight module, rewrites the received packet in place: wrapper.setFlying(mc.thePlayer.capabilities.isFlying) so the server's flying flag can never desync the client while the mode force-flies the player at timer speed 3. Debugger carries an Abilities toggle that prints fly speed, allowFlying and isFlying to chat for protocol inspection. PingSpoofComponent classifies S39 as a teleport-class packet, so when a spoof window is active, held S39 packets flush together with S08 teleports and S09 held-item changes rather than being held with regular traffic.

Exploit surface

The packet is clientbound, so the server cannot see mutations; the risk is desync rather than detection. CreativeFlight's rewrite makes local capabilities authoritative and hides the server's corrections, viable only while the server does not re-send S39 faster than the module rewrites it. The packet also constrains packet-holding systems: because S39 arrives on gamemode and flight changes, holding it across an S08 teleport would leave the client's flag state and position inconsistent, which is why the component groups the three packet classes.

Server-Side Handling

EntityPlayerMP re-sends S39 whenever the capabilities setter path detects a change, and ServerConfigurationManager sends it once on join. C13 processing is the only serverbound input and it gates flying on allowFlying; the server's S39 responses are the corrective loop that keeps the client honest about permission.

Protocol Analysis

One flags byte then two raw 32-bit IEEE floats with no quantization: 0.05 default fly speed, 0.1 default walk speed. Bit 0x02 is current flying, 0x04 is permission to fly; creative players get both set, survival players neither unless a plugin grants flight. The same byte layout is reused by C13, which zeroes the unused fields.

Anti-Cheat Landscape

Anti-cheats infer flight from movement and C13, not from S39, but the packet is a synchronization oracle for them: a client that never confirms flying while the S39 stream says flying is on is not mirroring state, and the movement that follows is what actually flags. CreativeFlight's rewrite exists to keep that mirror consistent. Holding components treat S39 as teleport-adjacent because a held S39 crossing a held S08 desyncs flags and position, a failure mode that correlates with timer and fly flags.

implementation Implementation Cases

The authoritative capability sync packet: flags byte plus fly and walk speeds, mirrored by a single-flag serverbound C13. Three Rise 6.x surface areas in the corpus: CreativeFlight rewrites the received S39 to claim flying, Debugger prints its fields for protocol inspection, and PingSpoofComponent treats it as teleport-class traffic so held S39 flushes with S08.

Hold and replay latency-sensitive packets; S39 is classified as teleport-class so it flushes together with S08 rather than with regular traffic.

The component owns five class tuples (regular, velocity, teleports, players, blink, movement) plus per-tuple enable flags set by spoof(). Grouping matters because holding an S39 across an S08 would desync flag state from position. The component is the shared engine behind PingSpoof, CreativeFlight and the blink modes.
Vanilla hook: PacketReceiveEvent, PacketSendEvent, PostMotionEvent, WorldChangeEvent.
Holding S39 is not itself detectable, but the desync it prevents is: a held S39 crossing a held S08 would leave flag state and position inconsistent, a correlation anti-cheats can use. The teleport grouping exists to keep that ordering intact.
Variations: Rise 6.2.4 ships the identical component under Client-release2/Client/src/main/java; both versions are driven by the same spoof() and blink() entry points.
PacketReceiveEvent is the common surface; CreativeFlight mutates the packet object on the event, Debugger reads it, PingSpoofComponent cancels and queues it.
Rise 6.x uses the component system for holding; the 6.1.30 and 6.2.4 trees are functionally identical. The other six clients carry only the vanilla handler and have no S39 modules.
