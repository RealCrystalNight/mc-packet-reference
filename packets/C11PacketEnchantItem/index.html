Deep Dive

Role in the protocol

C11 selects an enchantment option in an open enchanting table: a byte window id and a byte button (0 top, 1 middle, 2 bottom). It is the only serverbound packet whose sole effect is triggering Container.enchantItem, and it is sent from the vanilla GUI through PlayerControllerMP.enchantItem. The server replies with S2FPacketSetSlot carrying the enchanted result plus XP and lapis deltas.

Vanilla handling

processEnchantItem gates on three conditions: the packet's window id must equal the player's openContainer.windowId, the container must report canCraft, and the player must not be a spectator. Only then does it call enchantItem(playerEntity, button), which re-derives the enchantment from the table's seed, validates the lapis and level cost against the real player state, applies the enchantment and calls detectAndSendChanges. Every cost check is server-side; the packet carries nothing but the two bytes.

Why clients touch it

There is no AutoEnchant module in the corpus; the hits are all plumbing. Rise 6.1.30 and Rise 6.2.4 expose sendEnchantItem in the script PacketAPI, Tenacity 6.0 lists C11 in PacketUtil.isClientPacket, and November Recode 2.0 maps C11PacketEnchantItem to wire id 0x11 in LuaEventPacket so its Lua scripting API can identify the packet by id instead of by class. Enchanting in all of these clients goes through the vanilla GUI, so the packet is never intercepted for spoofing.

Exploit surface

The server re-validates everything, so the packet itself cannot grant free enchants; the historical abuse is ordering, not content. A client that clicks an enchant and a C0E window action in the same tick can race the slot sync, which is the dupe-era vector. Because the button byte indexes the table's three server-side options, sending a button with no matching cost is harmless: enchantItem simply fails the level check. Anti-cheats ignore C11 entirely.

Server-Side Handling

processEnchantItem: window id match, canCraft check, spectator rejection, then Container.enchantItem which re-validates lapis and XP server-side. detectAndSendChanges pushes S2FPacketSetSlot with the enchanted stack. No rate limit beyond the container state machine.

Protocol Analysis

byte windowId + byte button on the wire. Valid only while an EnchantmentTable container is open; any other container makes the window id check fail. The button maps to the table's three server-side options, which are deterministic from the world seed and player position.

Anti-Cheat Landscape

No anti-cheat measures C11; the packet is fully server-validated and carries no movement or timing signal. The only server-side observable is the ordering relative to C0E transactions during rapid enchanting.

implementation Implementation Cases

The enchanting-table selection packet. Zero modules in the corpus drive it; the hits are the Rise 6.x script PacketAPI enchant bridge, Tenacity's silent-send whitelist and November Recode 2.0's Lua packet-id map.

LuaEventPacket (script bridge) (November Recode 2.0)

Expose the serverbound packet id space to the Lua scripting API: scripts receive a numeric packet id instead of the raw class.

A static block maps every serverbound play packet class to its 1.8.9 wire id, C11PacketEnchantItem to 0x11. The constructor resolves the id from the EventPacket payload via getOrDefault (falling back to -1) and stamps a direction string ('out' for EventPacket.Out, 'in' otherwise); Lua event wrappers then pass the id and direction to scripts. The source comment explains the map exists because runtime obfuscation would break reflection-based lookups.
