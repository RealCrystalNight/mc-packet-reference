Requests the client to enable encryption by sending the server's RSA public key, a verify token (random challenge), and server ID for Mojang session auth.

Notes

After receiving this, the client generates a random AES shared secret, encrypts it + the verify token with the server's public key, and sends them back in C01PacketEncryptionResponse. Also authenticates with Mojang's session server using the serverId hash.

Deep Dive

Role in the protocol

The LOGIN-state RSA challenge. NetHandlerLoginServer sends it once the client has identified itself with C00PacketLoginStart: new S01PacketEncryptionRequest(this.serverId, this.server.getKeyPair().getPublic(), this.field_147330_e). It carries the server's DER-encoded RSA public key, a random 4-byte verify token, and a server id that is empty in 1.8.9 because authentication hashes the key material itself. Receiving it is the client's first proof that the server runs online mode; offline-mode servers skip encryption and go straight to S02PacketLoginSuccess.

Vanilla handling

NetHandlerLoginClient.handleEncryptionRequest generates a fresh AES secret (CryptManager.createNewSharedKey()), computes the server-hash sha1(serverId + DER key + secret) as a hex BigInteger, and calls the session service's joinServer with the profile, token, and hash. On success it replies with C01PacketEncryptionResponse(secret, key, token) and, via the packet's GenericFutureListener, calls networkManager.enableEncryption(secret) so the stream switches to AES/CFB8 on flush. Failure paths close the channel with disconnect.loginFailedInfo variants.

Why clients touch it

No module in any of the 8 clients references it. The full corpus for S01PacketEncryptionRequest is vanilla files: NetHandlerLoginClient, EnumConnectionState registration, INetHandlerLoginClient, the packet class, and NetHandlerLoginServer. The practical reason: online-mode detection does not need the packet. A client learns the server is offline when the login state ends without this packet, and both outcomes are visible through the vanilla login handler before any module event bus exists. None of the 8 clients instruments the LOGIN state at all.

Exploit surface

The crypto handshake is where session security lives, and it is unauthenticated: 1.8.9 validates neither the certificate chain nor key size, so a MITM proxy that terminates TLS and re-encrypts with its own key can read and rewrite everything, including harvesting the joinServer call. The verify token exists to prove the server holds the private key matching the public key it sent; a proxy must replay it. Server-side, a malicious server can only force a client to do a session-server round trip per join. No client-side abuse is present in the corpus.

Server-Side Handling

NetHandlerLoginServer.func_147326_c runs the handshake: if the server is online-mode and the connection is not already local, it stores the verify token and sends S01PacketEncryptionRequest. The login state has a timeout; a client that never answers with C01PacketEncryptionResponse is dropped by the network read timeout. After processing the response, the server decrypts with its private key, verifies the token, joins the session server with the hashed server id, and only then proceeds to compression and S02PacketLoginSuccess.

Protocol Analysis

Wire layout: String serverId, then VarInt length + RSA public key bytes (X.509 DER), then VarInt length + verify token bytes (4 random bytes). The client's reply C01PacketEncryptionResponse carries the same key and token encrypted with the server's public key plus the AES secret encrypted the same way. Encryption starts after the response flushes, so the first encrypted frame is the next packet after C01. Compression, when enabled, is negotiated separately in login state via S03PacketEnableCompression.

Anti-Cheat Landscape

None. This packet predates world state and is identical for every legitimate client; the only players here are the session server and the Mojang account backend. For cracked servers the whole exchange disappears. The realistic threat model is impersonation of the server (unvalidated public key), which is a network-level problem, not a module-level one.

implementation Implementation Cases

The LOGIN-state encryption challenge. Zero module hits in all 8 clients: every corpus reference is vanilla login plumbing. Online-mode detection in these clients is implicit (the packet simply never arrives on cracked servers) and happens in the vanilla handler, not in module code.

All 8 clients ship the stock 1.8.9 NetHandlerLoginClient unchanged. Rise 6.x renames the fields (verifyToken instead of field_147330_e) but the behavior is identical: same shared-secret generation, same joinServer call, same enableEncryption-on-flush listener.
