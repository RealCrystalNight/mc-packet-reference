Notes

Sent immediately after C00Handshake (with state=LOGIN). The GameProfile has a username but the UUID is null — the server fills in the UUID from Mojang's auth servers and returns it in S02PacketLoginSuccess. This is the first step of the login handshake after the initial HANDSHAKING state.

Deep Dive

Role in the protocol

C00PacketLoginStart is the first packet of the LOGIN state, sent immediately after C00Handshake with nextState=2. It carries a GameProfile whose username is the only meaningful field; the UUID is null at this stage and the server fills it in from the session service. The vanilla client fires it from three places: GuiConnecting on connect, Minecraft.java's direct networkmanager path, and RealmsConnect for realm joins. The server answers with S01PacketEncryptionRequest on online-mode servers or S02PacketLoginSuccess on offline-mode servers. Everything after this packet is gated on the server's decision in processLoginStart.

Vanilla handling

NetHandlerLoginServer.processLoginStart validates the currentLoginState is HELLO via Validate.validState, stores the profile, then branches on server.isServerInOnlineMode() and whether the channel is local. Online mode moves to KEY state and sends S01PacketEncryptionRequest; offline mode jumps straight to READY_TO_ACCEPT. The username arrives as a VarInt-length-prefixed UTF-8 string; the client enforces the 16-character limit at the login screen, and the packet itself does no re-validation beyond reading the string.

Why clients touch it

Two families in the 8 clients reference this packet, and neither spoofs the name. Rise 6.1.30 and 6.2.4 BlinkComponent list C00PacketLoginStart in a five-class exemption set that is returned untouched by the blink buffer. Spicy Blink, Fly and BackupFly use an identical three-way guard (C00PacketKeepAlive, C00Handshake, C00PacketLoginStart) in their EventSendPacket handlers so the handshake always flows while the module cancels everything else. No name-spoof module exists in this corpus: the old Gugustus NameSpoof pattern is absent from all 8 clients, which instead treat the packet as untouchable plumbing.

Exploit surface

The packet is sent before encryption, so the username is visible to any MITM during login, and on offline-mode servers the name is trust-on-first-use: impersonation is a server configuration weakness, not a packet bug. Client-side abuse is limited to cancellation, which stalls the login at HELLO until the server's connection timeout fires. The only real engineering concern for module authors is accidental swallowing: a blink module that buffers C00PacketLoginStart breaks every future join, which is exactly why both Rise's component and Spicy's modules hard-code the exemption.

Server-Side Handling

NetHandlerLoginServer.processLoginStart: Validate.validState(HELLO), store loginGameProfile, then either send S01PacketEncryptionRequest and move to KEY (online mode, non-local channel) or move straight to READY_TO_ACCEPT (offline mode or local channel). No username validation beyond the wire read; the server trusts the client's login-screen limit of 16 chars.

Protocol Analysis

Sent in LOGIN state only, id 0x00. Single String field: VarInt length + UTF-8 bytes. UUID in the GameProfile is null until the server resolves it via the session service. State must be LOGIN after the C00Handshake; a C00PacketLoginStart in any other state is a protocol violation that the server's Validate check rejects.

Anti-Cheat Landscape

No anti-cheat parses this packet: it carries no position, timing, or interaction data and the player entity does not exist yet. Serverside plugins and proxies (auth plugins, BungeeCord) consume the name for pre-auth bookkeeping, but nothing in the 8 clients interacts with that. The packet is a non-surface for flagging, which is why modules only need to avoid breaking it.

implementation Implementation Cases

The login opener: username-only GameProfile sent right after the handshake. No module in the 8 clients spoofs or cancels it; BlinkComponent (Rise 6.x) and Spicy's Blink/Fly/BackupFly merely exempt it from packet buffering so the handshake survives while they hold everything else.

BlinkComponent (Rise 6.1.30, Rise 6.2.4)

Exempt C00PacketLoginStart (and the other four pre-play serverbound packets) from blink buffering so the login handshake always reaches the server while blink is active.

A PacketSendEvent listener at VERY_LOW priority returns without cancelling when the packet is C00Handshake, C00PacketLoginStart, C00PacketServerQuery, C01PacketPing or C01PacketEncryptionResponse. Any other packet is parked in the static queue and cancelled, unless it matches the per-module setExempt list. The queue flushes via PacketUtil.sendNoEvent when a C03PacketPlayer arrives, the player dies, or the world changes.

Blink / Fly / BackupFly (login allowlist) (Spicy)

Keep the handshake alive while the module cancels and buffers all other serverbound packets, so blink and Hypixel-mode fly cannot kill the login sequence.

EventSendPacket pre handler returns early when the packet is C00PacketKeepAlive, C00Handshake or C00PacketLoginStart. Every other packet is added to a static ArrayList and cancelled. Blink flushes the queue through mc.getNetHandler().addToSendQueue on disable; Fly's Hypixel mode applies the same guard before rewriting C03PacketPlayer fields and parking packets in its own buffer.

anticheat Anti-Cheat Checks

LoginStart is invisible to server-side anticheats: the player entity, world and timing state do not exist yet, and the packet carries only the username. The two corpus hits are packet-library plumbing: FlopAC ChannelHandlerAbstract and intave TinyProtocol both declare the PACKET_LOGIN_IN_START class constant and route it through their channel handlers, and intave's handleLoginStart dispatcher serves the plugin's own cloud-control channel, not a check on the Minecraft login packet. No anticheat flags anything on it.
