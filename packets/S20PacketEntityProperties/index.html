Notes

Attribute keys: generic.movementSpeed, generic.maxHealth, generic.knockbackResistance, generic.followRange, horse.jumpStrength, zombie.spawnReinforcements, etc. Movement speed can be read to predict horse speeds or detect speed-modified players.

Deep Dive

Role in the protocol

S20PacketEntityProperties is a full attribute snapshot for one entity: entityId VarInt, property count int, then per property a String key, double base value, modifier count, and per modifier a UUID, name, amount and operation byte. The server sends it from EntityTrackerEntry when an entity's attributes change (line 267/311 in the corpus) and to new watchers when they start tracking (line 329/374). This is the only channel by which the client learns other entities' movement speed, knockback resistance, max health and attack damage.

Vanilla handling

NetHandlerPlayClient.handleEntityProperties resolves the entity and throws IllegalStateException if it is not EntityLivingBase ('Server tried to update attributes of a non-living entity'). It then walks the snapshot list: unknown attribute keys are registered on the fly as RangedAttribute with the full double range, setBaseValue is applied, all modifiers are removed and re-added from the wire. EntityLivingBase reads these attributes for its own speed, health and knockback math, so the packet directly drives client-side entity physics.

Why clients touch it

Rise 6.1.30 and 6.2.4 PingSpoofComponent include S20PacketEntityProperties in the 'players' class tuple: when a module enables players=true spoofing, incoming S20 packets are cancelled and released late. Rise 6.x NetworkAPI also registers the class (clientbound index 75). Memeware, Nekoware, Sigma, Spicy and Tenacity carry only the vanilla handler; the AntiBot/TargetInfo attribute-reading modules from older docs have no corpus hits in the reference set.

Exploit surface

The interesting abuse is buffering, not reading: PingSpoofComponent holds S20 for other entities so their attribute snapshots arrive after their position updates, keeping the client's view of entity speeds consistent with frozen positions during blink windows. Delaying entity-state packets does not touch the player's own server-authoritative motion, so no anti-cheat flags it. A client that reads S20 precisely could predict player speeds for aim/velocity math, but none of the 8 clients does.

Server-Side Handling

EntityTrackerEntry sends the full attribute map on change (line 267/311) and on watcher start (line 329/374). The packet carries base values plus modifiers, so the client rebuilds the complete attribute state from scratch on every arrival; there is no delta encoding and no inbound handler. Server-side validation is absent by design: the packet is clientbound.

Protocol Analysis

The property count is a plain int, not a VarInt, unlike most 1.8.9 counts. Attribute keys are the unlocalized names ('generic.movementSpeed', 'generic.knockbackResistance', 'generic.maxHealth', 'generic.attackDamage', 'horse.jumpStrength', 'zombie.spawnReinforcements'). Modifier operation is a byte (0 add, 1 multiply, 2 multiply-base). The client registers unknown keys as RangedAttribute with near-infinite bounds, so a server can push arbitrary named attributes.

Anti-Cheat Landscape

Entity attribute state is derived server-side, so anti-cheats never validate S20 traffic. The only observable effect of buffering it is delayed visual entity speed, which looks like normal lag. This is why PingSpoofComponent can park S20 for hundreds of milliseconds without risk.

anticheat Anti-Cheat Checks

The attribute snapshot packet is the server's only channel for entity attribute state, and anticheats treat it as authoritative input for movement simulation. Trackers capture the movement-speed attribute and its modifiers (Hydro, AntiHaxerman, intave), Grim clamps attribute values to the wiki-defined client bounds and excludes the sprinting modifier from the base value, TruthfulAC records attribute snapshots from the Bukkit API that mirrors the S20 state, and Photon rewrites the max-health attribute. Knockback resistance is present in the packet but no check in the corpus consumes it.

ValuedAttribute (attribute range validation) (GrimAnticheat-Grim)

Model one server-sent attribute with wiki-defined min/max bounds and recompute its value from the S20 property, so the simulation never trusts an out-of-range base or modifier sum.

with() recomputes the value as (base + addition sum) x (1 + multiply-base sum) x product of (1 + multiply-total) and clamps to [min, max]; the sprinting modifier is removed first because Grim tracks sprint separately in CompensatedEntities. requiredVersion gates value changes behind a client version, and setRewriter/getRewriter adapt the value per client and server version. The constructor rejects defaults outside the range.

Detects: Attribute abuse where the server sends values the client would clamp, and version-dependent attribute quirks that would otherwise desync the simulation.

AttributeEngine (simulation attribute history) (TawnyE-TruthfulAC)

Record walk speed, gravity, jump strength, step height, movement efficiency and potion levels over a 1.5 second window so the simulation checks bound their physics assumptions.

updateStateCache in PlayerData reads the Bukkit attribute API (generic.movementSpeed, generic.gravity, generic.jumpStrength, generic.stepHeight, generic.movementEfficiency, player.sneakingSpeed) and potion levels, then calls attributeEngine.record. The engine keeps a timestamped deque, exposes max walk speed, min gravity, max jump strength and step height, and hasAttributeTransition detects attribute changes within the window. The debug tags (ATTR_LOW_GRAVITY, ATTR_SPEED, ATTR_JUMP, ATTR_STEP) label the active conditions.

Detects: Physics assumptions violated by attribute changes; the recorded history lets the simulation checks tolerate legitimate speed and jump changes instead of flagging them.
