Deep Dive

Role in the protocol

S0D plays the item pickup animation: a VarInt item-entity id and a VarInt collector-entity id. The server emits it from EntityLivingBase.onCollideWithPlayer, which sends up to three tracking broadcasts per pickup depending on the item-count branch. The client spawns the collect particles, plays the sound and removes the item entity. It is a pure presentation packet.

Vanilla handling

NetHandlerPlayClient.handleCollectItem removes the item entity by id, spawns the pickup particles and plays the collect sound. Nothing on the client validates the collector id; the animation is cosmetic. The server side is equally dumb: three sendToAllTrackingEntity calls in onCollideWithPlayer with no rate limiting.

Why clients touch it

Almost nobody. The single functional hit is Rise 6.x AdaptiveRefreshRateComponent, which uses S0D as a cheap game-activity signal: an item pickup forces the HUD cache dirty for 5 ticks so the adaptive refresh rate does not sleep through pickups. Everything else in the corpus is vanilla. The ItemESP and ItemStealer families that one might expect to care about pickups do not hook S0D in these clients: they track item entities directly on the entity list.

Exploit surface

None. S0D carries two entity ids and drives only particles and a despawn. There is no state, no timing heuristic and no anti-cheat that measures pickups, so modules have nothing to cancel, spoof or time. The honest assessment is that S0D is the least interesting packet in this range: its only corpus use is a HUD perf component treating it as an activity tick.

Server-Side Handling

EntityLivingBase.onCollideWithPlayer sends S0D through the entity tracker in three branches covering the pickup conditions, each a sendToAllTrackingEntity with the item entity id and the collector's own id. No server-side rate limit or validation exists.

Protocol Analysis

Two VarInts: collected item entity id first, collector player id second (the vanilla constructor takes (collectedItemEntityId, entityId)). Clientbound in PLAY state. The collector id is not required to be the local player, which is why the packet also animates other players' pickups.

Anti-Cheat Landscape

Nothing to flag. No anti-cheat measures item pickups, and the packet carries no position or timing data. The only ecosystem interaction is visual: a client that suppresses S0D would still receive the items in inventory, so even packet-cancelling modules would gain nothing.

implementation Implementation Cases

The pickup animation packet: item entity id plus collector id, driving particles, sound and a despawn. Module interest is essentially zero: the only functional use in the whole corpus is Rise's AdaptiveRefreshRateComponent, which treats S0D as a game-activity signal to keep the HUD refresh awake.

AdaptiveRefreshRateComponent (Rise 6.2.4, Rise 6.1.30)

Keep the HUD refresh awake around pickups: an S0D forces the HUD cache dirty for 5 ticks so the adaptive refresh does not sleep through game activity.

On PacketReceiveEvent, S0D sets disabledFor = 5, which disables the adaptive refresh for that many ticks in PreMotionEvent; S02 chat, S30 window items and S2F slot updates drive the same dirty path. The component runs at component level in the HUD module tree.
