Deep Dive

Role in the protocol

The living-entity counterpart of S0E: mobs, animals and monsters spawn through S0F instead of S0E. EntityTrackerEntry.getPacket returns it for every EntityLivingBase; the payload carries the entity id, the EntityList type code (50=creeper up through 120=villager), fixed-point position (x32), yaw/pitch/head rotations (x256/360), velocity shorts (x8000) and a full DataWatcher block. The metadata is what renders health, potion effects and nametags without follow-up packets, which makes S0F one of the heaviest spawn packets on the wire.

Vanilla handling

handleSpawnMob creates the living entity through EntityList.createEntityByID, sets position and rotations, applies the velocity and reads the DataWatcher. Server side, EntityTrackerEntry deliberately suppresses the velocity-update packet on the spawn tick: the sendVelocityUpdates branch skips entities that just arrived via S0F because the spawn packet already carries the initial motion, avoiding a redundant S12 immediately after spawn.

Why clients touch it

No user-facing module in the 8 clients references S0F. Mob ESP, KillAura target lists and Tracers here iterate the loaded entity list each render frame rather than hooking spawn packets, so they consume the spawned EntityLivingBase objects after vanilla handling instead of the packet itself. The only non-vanilla client code is Rise's TranslationComponent (the PacketType enum's SPAWN_MOB entry decodes the fixed-point coordinates into the entity-position map used by the Translation bypass) and the NetworkAPI script registry listing the class.

Exploit surface

The DataWatcher is the attack surface: a crafted metadata block can declare absurd health, invisible flags or armor values, and mob spawn floods are the classic lag vector. The type byte is unvalidated by the client, so a proxy-crafted id despawns the entity silently. For bypass engineering the interesting property is that S0F is the only clientbound packet that fully defines an entity's state at once, which is why the Translation component hooks it: rewriting the spawn position desyncs the client's rendering from the server's simulation without emitting a single movement packet.

Server-Side Handling

EntityTrackerEntry.getPacket returns new S0FPacketSpawnMob((EntityLivingBase) trackedEntity) for any tracked living entity, and the sendVelocityUpdates branch skips S12 on the same tick the mob spawns because the spawn packet already carries initial velocity. The packet constructor snapshots position, rotations, velocity and the full DataWatcher at tracking time. The client handler reverses this: create entity, set transform, apply motion, read metadata.

Protocol Analysis

Same fixed-point layout as S0E: VarInt entity id, unsigned byte type, three x32 ints, three rotation bytes, three x8000 velocity shorts, then the DataWatcher block which is mandatory for living entities and can run to dozens of bytes. Because the type id is the EntityList id and not the entity class, the client must have a matching entity registry or the spawn is dropped.

Anti-Cheat Landscape

Anti-cheats use S0F as a state anchor: knockback checks know the mob's spawn velocity, and bot-detection heuristics on some servers correlate S0F rate with chunk activity. The Translation-style spawn repositioning is a rendering-layer desync, invisible to server-side movement checks but detectable by servers that verify client-reported entity positions. No reference client ships a module that abuses it; the corpus hit is purely the component infrastructure.

implementation Implementation Cases

The spawn packet for every living mob, carrying a full DataWatcher. No module in the 8 clients hooks it: ESP and KillAura read the world entity list instead. The one piece of real client code is Rise's TranslationComponent, whose PacketType enum decodes S0F spawn coordinates into the position map that powers its spawn-repositioning bypass.

anticheat Anti-Cheat Checks

The living-entity spawn packet carries the full state of a mob: type, position, rotations, velocity and the DataWatcher. Anticheats consume it on the send side to learn entity ids and types before any reach or hitbox measurement: Photon caches the entity type per id, TruthfulAC snapshots the spawn box into its compensation history, and Grim replicates the entity into the simulation used by reach and knockback checks. The type byte matters because hitbox dimensions depend on it, and a spawn without a tracker entry would leave every later entity packet orphaned.

Living-entity id lookup (Photon) (Photon-GitHub-AntiCheatAddition)

Cache the entity type for every spawned living entity so later modules can resolve an entity id to its type without Bukkit lookups.

LivingEntityIdLookup registers a PacketSendEvent listener for SPAWN_LIVING_ENTITY, wraps the packet as WrapperPlayServerSpawnLivingEntity and stores (entityId, entityType) in a Guava cache capped at one million entries with a five-second default expiry. A delayed task pre-warms the cache from all loaded worlds at startup, and getEntityType serves id-to-type lookups for modules that need hitbox or behavior data.

Detects: Nothing: it is a utility cache. Modules such as the DamageIndicator and information hider consume it.

Spawn compensation (TruthfulAC) (TawnyE-TruthfulAC)

Snapshot every spawned entity's position and hitbox into the compensation history so reach checks can backtrack against it.

TruthfulPacketListener routes SPAWN_ENTITY (the 1.19+ living spawn) into CompensationTracker.handleSpawn, which stores a CompensatedEntity keyed by id with a ring of up to 30 tick snapshots and a base reach taken from the entity type (3.0 for players, 1.5 boats, 4.5 shulkers). handleEntitySnapshot re-stamps live Bukkit entities each tick, and getEntityData serves the backtracking reach check with up to 8 ticks of history.
