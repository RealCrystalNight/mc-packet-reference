Deep Dive

Role in the protocol

Server-initiated window close. It carries a single unsigned byte windowId and tells the client to tear down the open container and re-sync the held item. Server-side, EntityPlayerMP.closeScreen sends it when the server decides the player's window must close, which happens on death, teleport, dimension change, and anti-cheat interventions. The client counterpart C0DPacketCloseWindow is the player-initiated echo; the S2E path is always server-driven.

Vanilla handling

NetHandlerPlayClient.handleCloseWindow calls thePlayer.func_175159_q(), which resets the carried item and closes the current screen. It does not check the windowId against the open container: any S2E closes whatever GUI is up. Server-side, EntityPlayerMP.closeScreen sends S2E with openContainer.windowId and closes the container. The asymmetry is the hook: a server can yank any GUI, and the client obeys blindly.

Why clients touch it

One module family: NoGuiClose, present in Rise 5.99, 6.1.30 and 6.2.4. It cancels S2E so servers cannot close the player's GUI. Rise 5.99 defaults the Chat Only setting on, meaning the cancel only applies while the chat screen is open, which preserves the ability to type while a container stays open. Rise 6.2.4 defaults it off, blocking every server close. The other five clients in the corpus have no S2E module reference at all.

Exploit surface

The unguarded close is the surface: servers close windows to interrupt chest-stealing macros and inventory manipulation, and NoGuiClose defeats that by holding the GUI open. The cost is protocol desync: the server has closed its container while the client still shows it, so later clicks (C0E) reference a dead window. This is safe only while the player does not actually interact; the Chat Only mode exists precisely to limit the desync window to chat-while-looting use. Vanilla's failure to validate windowId on S2E also means a server can send a mismatched id to force-close anything.

Server-Side Handling

EntityPlayerMP.closeScreen sends S2E with the current openContainer.windowId, then closes the server-side container and re-syncs the held item. NetHandlerPlayClient.handleCloseWindow runs func_175159_q() unconditionally: it resets the carried item and closes whatever screen is active, ignoring the packet's windowId entirely. Because the client never validates the id, the packet is a blind close lever from the server's perspective.

Protocol Analysis

Encoding: single unsigned byte windowId. It is one of the smallest packets in the play state. The client handler performs no id comparison against openContainer.windowId, which is the load-bearing detail for NoGuiClose: cancelling the packet has no side effects beyond keeping the GUI open. The windowId matters only for server bookkeeping, since the client close path is unconditional.

Anti-Cheat Landscape

Anti-cheats flag the desync NoGuiClose creates: a window the server closed but the client keeps open will eventually produce clicks (C0E) against a dead windowId, which window-state checks flag as inventory manipulation. The Chat Only default in Rise 5.99 keeps the desync window small (chat open while looting); blocking every S2E (6.2.4 default) widens it and increases the flag surface. This is a utility module with a real anti-cheat cost, unlike the purely cosmetic filters elsewhere in this group.

implementation Implementation Cases

The server-driven window close, and the target of the only cross-version module in this packet group: NoGuiClose in all three Rise releases. It cancels S2E so a server cannot yank the player's GUI, with a Chat Only mode in 5.99 to limit the desync. The other five clients never touch the packet outside vanilla.

NoGuiClose (Rise 5.99, Rise 6.2.4, Rise 6.1.30)

Cancel server window-close packets so the player's GUI cannot be yanked away.

A PacketReceiveEvent handler cancels any S2E, gated by a Chat Only setting: when enabled, the cancel only fires while mc.currentScreen is a GuiChat. Rise 5.99 defaults Chat Only to true (onPacketReceive + event.setCancelled), Rise 6.2.4 defaults its chatonly value to false (Listener with event.setCancelled).

The chatOnly setting defaults to true in 5.99, limiting the cancel to chat-open moments; 6.2.4 inverts the default to false.
